Overview

One of the next axes for scaling inference is coordination, with many agents working together on long-horizon and very difficult tasks. A main agent breaks the problem into pieces, hands them to tens or hundreds of sub-agents, and puts their work back together.

For this to scale, delegation cannot be the bottleneck. The work should finish sooner, because the sub-agents run at the same time. It should also be at least as correct, and on long tasks more correct, because each sub-agent works on a smaller piece with a fresh context. SubAgentBench measures both, and finds where delegation breaks down in today's models and harnesses.

We propose a new metric for this, the SubAgentBench score. It runs from 0 to 1 and multiplies the accuracy of a run by its delegation efficiency. Efficiency compares the run's time with the ideal, where a task with k independent parts finishes in 1/k of the time one agent needs. A model that solves every task with all of its parts done at once would score 1.

What we found

    Tasks

    SubAgentBench has seven coding tasks, each based on a popular open-source Python library. Each task asks for a feature with several parts, and hidden tests check every part and how the parts fit together. What changes from task to task is how much code the parts have in common, which decides how much the sub-agents can work without getting in each other's way.

    Each result is the SubAgentBench score on that task, from 0 to 1. Hover a result for its accuracy and efficiency.

    How the tasks are built

    Every task starts from a pinned release of the library. Next to the feature request, the repository has a stub or an empty module for each part, so a sub-agent can work on its part without editing the library's own code.

    The hidden tests run after the agent stops. They check each part on its own and the whole feature end to end. Some tasks, e.g., ruamel, also run the library's public API tests, so a run cannot pass by breaking behavior that already worked.

    Scoring

    Each model gets one score from 0 to 1. It rewards two things at once, solving the task and finishing it faster by delegating.

    S=A×E
    A, accuracy
    The mean hidden-test score of the runs with sub-agents. A run that the harness cuts off is graded on what it left in the repository, and a run that hits the time limit counts as 0.
    E, efficiency
    How close the run came to the ideal time. If a task has k independent parts, the ideal is for all of them to be built at once, in 1/k of the time the model needs alone. E is that ideal time divided by the actual time, capped at 1.

    For example, mako has five parts, so its ideal time is 0.2 of the solo time. Opus 5.5 on Claude Code finished mako in 0.4 of its solo time, so its efficiency there is 0.2 ÷ 0.4 = 0.50.

    We compute S for each task and average over tasks. A run that takes as long as working alone gets an efficiency of 1/k, about 0.2 on most tasks. The time comes from the same model working alone, so a model is not rewarded for being fast in general, only for how much faster delegation makes it.

    Results

    Speed depends on the type of task

    Sub-agents save time only when they can build their parts at the same time without waiting on each other. That depends on how the parts of a task relate to each other, which is what our three task groups vary.

    • Independent parts. Each sub-agent writes in its own files. Nothing blocks the others, and the merge at the end is simple.
    • Shared code. The parts touch some of the same modules, so sub-agents have to work around each other's changes and the merge has more to reconcile.
    • Single function. Every part edits the same function. The parts cannot really be built apart, so the sub-agents add coordination work and save little time.

    Accuracy

    Delegation instructions on docutils

    docutils is the one task where we ran every arm, so it shows what the instruction about how to delegate does on its own. The task, the repository and the model stay the same, and only that one paragraph changes. In Figure 6, each arrow starts where the model landed working alone and ends where it landed with one of the delegation instructions.

    • Opus 5.5 with sub-agents moved up and to the left. It finished in 23 minutes instead of 34 and scored 0.97 against 0.95, which is what good delegation looks like. It did the same on Codex, 35 minutes instead of 42.
    • Starting all sub-agents at once made GPT-5.6 faster than working alone, 42 minutes instead of 55, at about the same accuracy. The same instruction left GLM-5.2 with an accuracy of 0.08.
    • One sub-agent at a time lifted GLM-5.2 from 0.57 to 0.95, in about 1.8 times the solo time. Here delegation bought accuracy instead of speed.

    No single instruction is best for every model. A model that delegates well would pick the shape that moves it up and to the left on its own, and that choice is what the default arm and the score are meant to capture.

    Cost

    The score leaves out cost, so we track tokens next to it. We have output-token counts for every agent in the run for 16 model, harness and task combinations, most of them Opus 5.5. In those, the tasks where delegation saved the most time also spent the fewest extra tokens, with a rank correlation of 0.79, and no case was slower and cheaper. On docutils, Opus 5.5 with sub-agents on Claude Code finished 11 minutes sooner for about $12 more, or about $1.10 per minute saved.

    How runs fail

    We read the transcripts of the runs with sub-agents to see where the time and accuracy went. The patterns below come from those transcripts and from what each run left in its repository.

    ModelHarnessRuns with sub-agentsDied earlyHit time limit

    The main agent stops while it waits harness and model

    This is the most common failure, and it happened only on Claude Code. The main agent starts its sub-agents, says it will wait, and stops calling tools. If no sub-agent reports back for 10 minutes, the harness ends the run, and any sub-agent still writing code is stopped. We counted it in 5 Opus 5.5 runs, 6 GPT-5.6 runs and 12 GLM-5.2 runs, and the run ended a median of 10 minutes after the waiting message.

    "Four of the five parts (anchors, indent, style, flow) are merged into main. Only the comments worker is still running."

    That is Opus 5.5 on ruamel, 10 minutes before its run ended. All three of its ruamel runs stopped this way with one part missing and scored 0.75, on a task it solves alone at 0.95. The cut-off is the harness's rule, but the wait is the model's choice. In 5 of its 6 cut-off runs, Opus 5.5 set itself a fallback alarm before it stopped, always for 30 or 60 minutes, three to six times longer than the harness would wait.

    Sub-agents share one checkout model

    Sub-agents that edit the same working tree undo each other's work, so each one needs its own copy of the repository. Whether it gets one is the main agent's decision.

    • Opus 5.5 gave every sub-agent its own Git worktree in all 20 of its parallel runs on Claude Code, and named a ready-made worktree in all 21 of its briefs on Codex.
    • GPT-5.6 did the same in all 32 of its parallel runs on Claude Code. On Codex, its briefs told sub-agents to branch inside the shared checkout in 23 of 43 runs. In 18 runs the branches collided, and the main agent stopped every sub-agent and restarted them in separate trees, which about doubled the time.
    • GLM-5.2 gave no sub-agent its own tree in 4 of 17 parallel runs on Claude Code, and 3 of those 4 died early. On Codex its sub-agents worked in the shared checkout in 21 of 24 runs, and in 9 a sub-agent reset or stashed another sub-agent's files.
    "STOP immediately. Do not run more commands or edit/commit. The agents share /app and are colliding."

    That is GPT-5.6's main agent on Codex, 20 seconds after its sub-agents started on docutils. The restart cost the run its lead, and it finished in 39 minutes against 20 alone.

    The merge throws away solved work model

    In one GPT-5.6 run on bs4, every sub-agent did its job and the main agent lost the work. The steps were these:

    1. The main agent split the work sensibly and gave each sub-agent its own worktree. On their own branches, the sub-agents solved 15 items.
    2. One merged branch crashed. Instead of fixing the conflict, the main agent copied that sub-agent's whole files over the merged ones, which erased the code for 12 solved items.
    3. Its final check showed the failures. It blamed the test runner, re-ran the checks in a loop that only looked at exit codes, and reported "All 22/22 tracker items pass".
    4. The hidden tests scored the run 0.45. GPT-5.6 scores 0.97 on the same task alone.

    This was the one clear case of a merge losing solved work. Merge conflicts in general were common, e.g., in 12 of 18 Opus 5.5 runs on Claude Code, and the main agents usually resolved them without losing anything.

    Nobody checks the whole repository after merging model

    ruamel's hidden tests include a check that the library's existing public API still works, and a run that breaks it scores 0. GPT-5.6's merged code broke that check in 9 of 15 runs with sub-agents, against 1 of 6 runs without them. Opus 5.5 never broke it. Each sub-agent tested its own part, and no one tested the existing API after the parts came together. On Codex, GPT-5.6 scored 0.30 on ruamel with sub-agents against 0.95 alone.

    One part takes far longer than the rest model

    On ruamel, Opus 5.5 split the work into equal parts, but the comments part took far longer than the others. On Claude Code, all three runs were cut off while the other sub-agents' work sat merged and waiting for it. On Codex, where nothing cuts the run off, the comments sub-agent ran for over two hours, and the whole run took about three times Opus 5.5's solo time.

    The main agent keeps polling model

    GPT-5.6 on Claude Code avoided the cut-off by staying busy. In 15 of 28 runs it ran sleep commands while it waited, a median of 7 minutes and up to 64, and it listed its running agents and started extra agents to fix, review or audit the merged code. Every polling run finished, and every GPT-5.6 run that died early had not polled. The cost was time, which is why GPT-5.6 has the lowest efficiency on Claude Code.

    Why these failures are trainable

    None of the failures above is a coding failure. The sub-agents usually wrote working code, and the run lost it in the waiting, the merging or the coordination. The same model also scores very differently depending on the harness and on how it is told to delegate, e.g., on docutils one instruction made GLM-5.2 fail completely while another lifted its accuracy from 0.57 to 0.95. Gaps like these point to delegation behavior rather than missing ability.

    The benchmark gives a training run what it needs to target that behavior. Every task has a hidden-test reward, the score charges for both time and accuracy, and the three graded snapshots show whether the work was lost by the sub-agents or by the merge. We have not trained on these tasks yet, so this is the next thing we will test.

    Next steps

    Figure 1, in the overview, shows time to completion against the number of agents. On a task that takes one agent a week, a thousand agents with perfect delegation would finish in about 10 minutes. Our current tasks have too few parts to trace the rest of that curve, so the next version will add these changes:

    • Runs with 1, 2, 4, 8 and 16 agents, and deeper trees where sub-agents hand out work of their own, toward hundreds of agents.
    • Longer tasks that one agent cannot finish in its time budget, so that delegation is the only way to solve them and has to raise accuracy as well as speed.
    • Parts that vary in size and come without stubs, so the main agent has to decide how to divide the work.
    • Claude Fable 5.1 on Claude Code and GPT-6 Astra on Codex.
    • A training run on these tasks, to test whether the delegation failures go away.
