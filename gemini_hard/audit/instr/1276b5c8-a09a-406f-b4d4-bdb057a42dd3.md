The Terraform for our Turbo Deploy production control plane in `/workspace/infra` has grown into one flat root module: everything is declared at the top level, the per-target resources are `count`-indexed by list position, and names, settings and tags are hard-coded all over the files. Split it into three local modules (storage, api and automation) without touching the running infrastructure: against the current state, the plan has to come out as nothing but moves.

There is no AWS access from this machine. `terraform init` works offline from the local provider mirror, `terraform.tfstate` is a copy of the production state, and `scripts/ci-plan.sh` runs what CI runs: a `terraform plan -refresh=false` against the state followed by the guardrail policies in `policies/`.

## Detailed Constraints

**How CI judges the change.** CI takes the repository alone and plans it with `terraform plan -refresh=false` against its own copy of the production state. Local `terraform state` commands and edits to `terraform.tfstate` never reach it, so the whole migration has to be expressed in the configuration. That plan must:
- still manage every resource that is in the state today, and
- contain no create, update, replace, destroy or forget: only resources moving to new addresses.

The guardrail policies in `policies/` must pass on that plan, and `providers.tf` and everything in `policies/` stay exactly as they are, byte for byte.

**Layout.**
- The root module calls `module "storage"`, `module "api"` and `module "automation"`, with sources `./modules/storage`, `./modules/api` and `./modules/automation` and one instance each, calls no other module and declares no resources of its own.
- Which module owns what (every instance of the resources described, wherever they are declared today):
  - storage: the KMS data key and alias, both S3 buckets and every bucket settings resource, the Terraform runner ECR repository and lifecycle policy, and the Terraform lock table;
  - api: the HTTP request DynamoDB table, the API backend Lambda with its log group, IAM role, IAM policy and attachment, the REST API with its proxy resource, method, integration, deployment and production stage, the API invocation permission, and the API error and latency alarms;
  - automation: the Terraform runner Lambda with its log group, IAM role, IAM policy, attachment and DynamoDB event source mapping, the failure topic and topic policy, the primary-target parameter, every deployment target's queues, queue policy, topic, log group, configuration parameter, backlog alarm, schedule and schedule target, and every user script's S3 object, parameter, log group, queue, topic and backlog alarm.
- Each of these modules declares the resources it owns itself and calls no other module.
- Modules get each other's IDs and ARNs through module outputs and variables. Never paste an ID, ARN, IP address or DNS name of an existing resource, or any part of one (such as an ARN suffix), into the `.tf` files or templates. A name the configuration itself chooses (a bucket, role or parameter name, and an ARN built from that name alone, such as `arn:aws:s3:::<bucket>`) may also be derived from the same root inputs in the module that needs it, as long as no module spells today's value. The configuration reads files only through literal paths inside its own module (such as `"${path.module}/templates/..."`; in a child module a path starts with `${path.module}/`, because Terraform resolves any other relative path from the root directory, not from the module): no computed paths, no `terraform_remote_state` data sources, and never the state or a plan file.

**Keys.**
- Everything that exists once per deployment target today is a `for_each` resource keyed by the target name (for example `["edge"]`), including each instance of a list that also holds things that belong to no single deployment target.
- The primary-target parameter stores every target in ascending priority order and identifies the first as primary; ties are broken by target name.
- Everything that exists once per user-data script today is a `for_each` resource keyed by the script name (for example `["diagnostics"]`), including each instance of a list that also holds things that belong to no single user-data script.
- Don't use `count` anywhere. Other repeated resources use `for_each` with string keys that are not numbers (a name such as `["assets"]`, never `["0"]`).
- Each existing deployment target's entry in `deployment_targets` is the only source of its values: changing an entry changes, for that deployment target alone, exactly the settings the entry provides, and changes nothing else.
- `deployment_targets` carries no `validation` block: every entry its type allows must work.
- Adding a deployment target to `deployment_targets` must plan only the creation of that deployment target's resources, each configured exactly like its counterparts in the existing deployment targets apart from the deployment target itself and the values its entry in `deployment_targets` gives it (same settings, names and tags), and removing one only the destruction of that deployment target's resources. Beyond that, the only change either may plan is an in-place update of the settings that collect something from every deployment target today (wherever a setting holds a part of every deployment target: their names, IDs, ARNs, subnets or CIDRs, say, in a list, a policy document or an environment value): each of them must take in, or drop, exactly that deployment target's part where it belongs, in the same form as today (today's parts keep their order, except inside an IAM policy document, where the order of statements, actions and resources means nothing to AWS; where a new part goes is up to you), and change nothing else. No other resource may be created, updated, replaced or destroyed.
- Each existing user-data script's entry in `user_scripts` is the only source of its values: changing an entry changes, for that user-data script alone, exactly the settings the entry provides, and changes nothing else.
- `user_scripts` carries no `validation` block: every entry its type allows must work.
- Adding an user-data script to `user_scripts` must plan only the creation of that user-data script's resources, each configured exactly like its counterparts in the existing user-data scripts apart from the user-data script itself and the values its entry in `user_scripts` gives it (same settings, names and tags), and removing one only the destruction of that user-data script's resources. Beyond that, the only change either may plan is an in-place update of the settings that collect something from every user-data script today (wherever a setting holds a part of every user-data script: their names, IDs, ARNs, subnets or CIDRs, say, in a list, a policy document or an environment value): each of them must take in, or drop, exactly that user-data script's part where it belongs, in the same form as today (today's parts keep their order, except inside an IAM policy document, where the order of statements, actions and resources means nothing to AWS; where a new part goes is up to you), and change nothing else. No other resource may be created, updated, replaced or destroyed.

**Root variables.** Declare these in the root module, each defaulting to today's value:
- `project` (`string`, `"turbodeploy"`): every whole-word occurrence of `turbodeploy` in a resource name, identifier or tag value today comes from it (whole word: not part of a longer run of letters and digits, so `turbodeploy-api`, `turbodeploy_key` and `/turbodeploy/` count, while a longer word that merely contains `turbodeploy` stays as it is), and so does every mention of those names elsewhere in the configuration (for example a resource name inside a policy); inside documents such as policies, container definitions and environment values, every whole-word occurrence of `turbodeploy` that stands for it comes from it too.
- `environment` (`string`, `"prod"`): every whole-word occurrence of `prod` in a resource name, identifier or tag value today comes from it (whole word: not part of a longer run of letters and digits, so `prod-api`, `prod_key` and `/prod/` count, while a longer word that merely contains `prod` stays as it is), and so does every mention of those names elsewhere in the configuration (for example a resource name inside a policy); inside documents such as policies, container definitions and environment values, every whole-word occurrence of `prod` that stands for it comes from it too.
- `deployment_targets`: `map(object({ visibility_timeout = number, alarm_threshold = number, priority = number, schedule_minutes = number }))`, keyed by target name, defaulting to today's three targets and each target's queue visibility timeout, backlog alarm threshold, priority and sweep schedule. It is the only source of target names and those target settings.
- `user_scripts`: `map(object({ content = string, visibility_timeout = number, alarm_threshold = number }))`, keyed by script name, defaulting to today's three scripts and each script's content, queue visibility timeout and backlog alarm threshold. It is the only source of script names and those script settings.
- `tags` (`map(string)`, `{ Owner = "platform-automation", CostCenter = "cc-7314", ManagedBy = "terraform" }`): the shared tags (`Owner`, `CostCenter` and `ManagedBy`) that tagged resources carry today. Wherever the configuration writes them out today, in any form, they come from this variable, so that a different map (other keys, other values) reaches every one of those places; a resource's other tags stay as they are, and resources that are untagged today stay untagged.
- `log_retention_days` (`number`, `30`): the retention of every CloudWatch log group.
- `queue_message_retention_seconds` (`number`, `345600`): the message retention of every deployment-target and user-script queue, including deployment dead-letter queues.
- `runner_memory_size` (`number`, `2048`): the Terraform runner Lambda's memory size.
- `runner_timeout` (`number`, `600`): the Terraform runner Lambda's timeout in seconds.
- `backend_memory_size` (`number`, `512`): the API backend Lambda's memory size.
- `backend_timeout` (`number`, `15`): the API backend Lambda's timeout in seconds.
- `dynamodb_read_capacity` (`number`, `5`): the read capacity of the HTTP request table and its hostname index.
- `dynamodb_write_capacity` (`number`, `5`): the write capacity of the HTTP request table and its hostname index.
- Changing `log_retention_days`, `queue_message_retention_seconds`, `runner_memory_size`, `runner_timeout`, `backend_memory_size`, `backend_timeout`, `dynamodb_read_capacity` and `dynamodb_write_capacity` changes only what each one's line above says it controls: every other setting keeps today's value, including a setting that merely has the same value today.

**Root outputs.** Keep `terraform_locks_table_name`, `base_url`, `golang_lambda_arn`, `terraform_lambda_arn`, `terraform_state_bucket_name`, `runner_repository_url` and `failure_topic_arn` with their current values. `deployment_queue_urls` becomes a map from the target name to the `url` of that deployment target's `aws_sqs_queue.deployment`. `user_script_object_ids` becomes a map from the script name to the `id` of that user-data script's `aws_s3_object.user_script`. Each output passes through outputs of the module that owns the resource (storage for `terraform_locks_table_name`, `terraform_state_bucket_name` and `runner_repository_url`; api for `base_url` and `golang_lambda_arn`; automation for `terraform_lambda_arn`, `failure_topic_arn`, `deployment_queue_urls` and `user_script_object_ids`): the root output is a plain reference to an output of that module, and that module output is a plain reference to the resource. A plain reference is a reference such as `module.storage.<output>` or `<resource type>.<name>.<attribute>`, a local that holds one, or a `for` expression that only re-keys one (`{ for k, v in <reference> : k => v.id }`) or iterates a plain reference and looks each key up in one (`{ for k, v in var.<map> : k => <reference>[k].id }`); no literals, function calls, conditionals or string templates anywhere along the way, except inside the key that picks one instance of a resource (`<reference>[sort(keys(var.<map>))[0]].id` is a plain reference).

**Not allowed anywhere in the configuration:** `ignore_changes`, `prevent_destroy` and `replace_triggered_by`, `removed` and `import` blocks, provisioners, `external` data sources, backend or cloud blocks, provider blocks other than the one in `providers.tf`, override files and `.tf.json` files.
