# revive gives wrong verdicts all over — diagnosing it without a test suite

We point this tool at our Go sources and it tells us where they are sloppy or wrong. After picking up the current tree we get wrong answers out of it in a lot of unrelated situations, so we collected everything we could pin down from the outside. The repository has received 30 separate undocumented edits.

Start with what comes out the far end. Asking for the XML-shaped report that gathers findings into one element per source, we now see only the last finding recorded for each source, so something with two problems is written out as a single entry, while something with exactly one problem still looks right. Asking instead for the terse listing that prints nothing but path, line, column and message per finding, we get an empty string back and no failure reported; the JSON, newline-delimited JSON, unix, plain, stylish and friendly styles all print what they always did.

Telling the tool what to leave alone has stopped working too. Settings that give one individual check its own list of paths to skip can no longer be read at all: loading them comes back as a failure instead of something usable. Building that same skip list programmatically fails when we prepare it, and a source we asked a single check to pass over is examined by that check anyway. A comment asking for a check to be quietened over the line that follows it now covers the line after that one, so the statement we meant to silence is still reported and an innocent line below goes quiet instead; the same off-by-one shows up in the re-enabling form, while plain switch-off and switch-on comments, and the ones that cover their own line, still reach exactly what they used to.

When we ask what an identifier ought to be called, anything whose leading word is a well-known short abbreviation written in lowercase comes back shouted: those opening letters are handed back in capitals where before they were left alone. The same abbreviation sitting in the middle or at the end of an identifier is handled as it always was, and the stray leading capitals also leak into the suggestions we get for variables that hold durations.

Moving to the verdicts on what we declare. Declaring a plain function whose identifier duplicates a predeclared one, such as len or copy, now passes without a word, while declaring a method with that same identifier draws the shadowing complaint that methods were previously spared. A function returning two results of the same type without identifiers is no longer called confusing, while a function returning two results of differing types now is. A function returning two results with the error listed first is no longer told to move it last; only longer result lists still get that advice. Parameters that nothing in the body reads are no longer reported anywhere, under any setting, including the settings that allow a pattern for tolerated ones. Package-level error values whose identifier does not follow the Err prefix convention no longer draw any complaint about their spelling. Disagreement between a source's package declaration and the folder it sits in now passes in silence, while the one package declaration that was tolerated in any folder — the entry-point variant ending in _test — has become the only one complained about.

Inside function bodies the verdicts about control flow have drifted. A plain function call sitting inside a call that is scheduled to run as the enclosing function exits — one handed to it as an argument, say — is now reported as executing recover immediately, a complaint that only ever belonged to a genuine recover used in that position, which still draws it as before. An if whose body holds three simple statements is now treated as short: asked directly whether such a block counts as short, the answer is yes where it used to be no, and the advice to invert the condition and leave early is now offered for bodies one statement longer than it used to accept, while one-statement and two-statement bodies behave as before. A return carrying values as the last statement of a function is now called redundant, while a bare return in that position, which used to be the one flagged, is left alone. Any function that simply calls another, with no conditional exit of its own, is now reported as calling itself forever. Writing x += 1 no longer earns the suggestion to write x++, while x += 2 now earns it.

Comparisons and the values we build have flipped as well. Writing the same expression on both sides of a logical comparison is no longer reported as always yielding the same value, while an ordinary comparison of two differing expressions is now reported that way. A type assertion on the right-hand side of an assignment written without the two-result shape is no longer reported, though assertions in other positions still are. Taking the address of the value variable of a range loop inside the loop body is no longer reported, while taking the address of an ordinary local declared elsewhere is now reported as if it were the loop value. Starting a goroutine after any unrelated call statement now draws the suggestion to move to the newer combined helper, whether or not a counter bump preceded it. For process-ending calls such as os.Exit or log.Fatal made from ordinary helper functions, the verdicts no longer line up with what those sources should produce, in plain sources and in test sources alike, and at least some such calls now go unmentioned. fmt.Errorf given a placeholder verb and a single argument, such as fmt.Errorf("...%w", err), is now suggested for replacement by errors.New, though such formatted calls were previously left alone; the plain single constant message with no verbs is suggested as before. Sending fmt.Fprintf output into a bytes.Buffer or a strings.Builder and discarding what it hands back is now reported as ignored, though that pairing was previously accepted. Our preference about how empty maps get built is inverted: with literals demanded we get complaints about the literals themselves and silence about the make calls, and with make demanded the complaints land on the wrong shape as well.

Switch statements and the cosmetic preferences come out wrong too. A switch with no catch-all clause draws no complaint at all, and once the option that permits leaving that clause out is switched on, the complaint about a catch-all clause that isn't placed last stops appearing too. A case clause whose entire body is a single pass-through statement is no longer called pointless. Two case bodies that are textually identical inside a switch that tests an expression are no longer reported as duplicates, and the reporting has moved onto switches that test no expression at all. Complaints about blank lines immediately after an opening brace or immediately before a closing brace now come out wrong for blocks whose contents run up to the brace as comments, so warnings appear and disappear around comment-filled blocks. With the preference that consecutive parameters sharing a type should declare it only once, we now get a complaint for essentially every consecutive pair of parameters carrying identifiers, even when their types differ, and the same over-reporting shows up when the preference is set separately for arguments and for results. The check that matches string arguments of given calls against a regular expression has gone completely quiet: neither a plain string literal passed directly nor a string reached through a struct literal's field produces any complaint any more.

It worked before a set of undocumented edits to the source of revive. The repository has
no test suite to run: finding out what is wrong, and convincing yourself you have fixed
it, is part of the task.

Restore the behavior described above.

Record the functions that contain those edits in `/app/rca.json`, one entry each:

```json
{
  "causes": [
    {
      "file": "formatter/friendly.go",
      "function": "enclosing_function_name"
    }
  ]
}
```

`function` is the function name. A class prefix is ignored if you include one. When an
edit sits inside a function nested in another function, either name is accepted. Name
every function one of the undocumented edits is in, and only those. Where you wrote the
fix does not matter: if you restored the behavior from a caller or from a helper of your
own, name the function the edit is in rather than the one you wrote. If you suspect a
function but found no edit in it, leave it out.


Before you edit any code, write your research and your plan to /app/RESEARCH_AND_PLANNING.md. Cover what you learned about the existing code and the constraints that shape the change, then how you intend to carry it out and why, including how you will know it works. Be concrete - the files, names and decisions specific to this codebase, not generalities. Complete the document before you touch any code: it is the record of your up-front investigation and decisions, and it should not be rewritten to match whatever the implementation turns into afterwards. Once it is done, implement the plan.
