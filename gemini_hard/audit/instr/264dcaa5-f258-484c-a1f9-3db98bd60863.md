# gh-dash: twenty-seven unrelated misbehaviours to diagnose without a test suite

Since picking up this build, the dashboard goes wrong in a lot of unrelated places, and I have tried to write down each thing I actually did and what came back. The repository has received 27 separate undocumented edits.

Getting it started the way I want it is already wrong. Launching inside a repository that carries its own dashboard settings file skips that file entirely, and I get the groups of entries from my global file instead of the two the repository declares, though the file is there and readable. When nothing anywhere sets one of the numeric limits, what gets loaded comes back carrying 21 where the shipped value is 20, so a freshly loaded setup no longer matches the documented set. The colours I ask for are ignored as well: I set primary text to #FF0000 and the palette in force still shows the built-in colour, and the same happens when I give a plain ANSI index such as 12 instead of a hex value. And a key I bind to a custom action against an inbox entry never gets registered at all — the set of custom bindings stays empty and pressing the key does nothing — while bindings without an action are unaffected.

Running a custom action against an entry fails in three further ways. With no interpreter named in my environment, on Linux and macOS it now tries to launch cmd.exe with a /C argument rather than sh with -c, so nothing ever executes. The placeholder that stands for the repository's local directory, used when I have no directory mapping set up at all, expands to an empty string instead of the directory the dashboard was started from, producing a line that begins with a bare "cd" followed by nothing. When I do set up a mapping with a wildcard entry, the directory it works out keeps the literal asterisk segment in the middle of the path, so instead of a real directory I get something like /path/to/user_2/*/repo123; the exact, non-wildcard entries are fine.

Arranging what sits on screen is off. With the pane that shows the highlighted entry set to closed, it reports one column of usable room rather than none, and a refresh of it is still scheduled and drawn even though nothing is on screen. With that pane placed along the bottom, one row too many is taken away from the entries above it: the room for entries, the pane's height and the divider no longer add up to the space available, both when I ask for 40% and when I ask for a fixed ten rows. The closed case along the bottom adds up as before.

Formatted text no longer displays safely. Opening the detail of a ticket right after launch, before the colour setup has been applied, crashes while drawing the body. Asking for the machinery that draws formatted text when none of its setup has been prepared yet hands back something that blows up on text as simple as a single heading, instead of quietly falling back; and the routine that is supposed to prepare that setup when nothing is available leaves it unprepared, so the situation never repairs itself later.

Writing a comment is unusable. With a set of candidate names available, pressing @ is treated as ordinary text and no popup ever opens. Even when the popup does get a chance, a single matching person is not enough for it to consider that it has anything to offer, so nothing appears unless two or more candidates match. The fragment under the cursor is misidentified in both directions: with the cursor in the middle of plain text like "hello world" an @-fragment is reported where there is no @ at all, while with "hello @octo" and the cursor inside the name nothing is reported. As a consequence, after I clear the field and type an ordinary word, the popup comes back even though there is no @ anywhere in the text. And once I open the comment box on a ticket, the field does take focus but the screen still reports that no comment is being written.

Moving through the inbox goes wrong too. Jumping to the bottom leaves the selection one past the final entry, and when the bottom-most entry then disappears the selection does not settle on the new final one, so the entry reported as selected is not the one highlighted. Coming back up after paging down, the selection reaches the first entry but the visible window does not scroll to reveal it, so the highlighted line sits above what is drawn. An entry with no new comments now shows a plus-count marker in the column that used to be blank for it; entries with one or more new comments still show their count. And where an entry's pills are wider than the column and I have allowed only a single line of them, the output now spills onto a second line and grows an overflow marker instead of staying on one.

Nothing I do to an entry sticks. Pressing dismiss on the highlighted entry does nothing whatsoever: no work is started and no record of the dismissal is written, so the entry stays. When a dismissal does get recorded, it is thrown away far too soon — reloading the recorded set discards entries dismissed as recently as a day ago, where entries up to eighty-nine days old used to be kept, and everything resurfaces. Remembering entries has the same flavour of problem: after marking a couple of them and forcing the remembered set out to disk, the write reports a failure and a later read of that same file comes back without them, including for identifiers containing dashes, dots, colons or slashes.

The links and counts shown on entries are wrong as well. For an enterprise host whose repository address ends in a slash, the link built for a pull request comes out with a doubled slash in it; hosts without the trailing slash are fine. Pulling the identifier out of an address that has just one segment after the slash, like "/123", gives back an empty string, while full addresses still yield theirs. When an alert about an automated build has nothing within an hour of it, the fallback picks the second one in the sequence rather than the newest. A pull request's status summary miscounts: a suite still queued is left out of the in-progress tally, while a completed suite waiting on approval is tallied wrongly, so neither that tally nor the awaiting-approval count matches what is actually shown. And for a local entry that tracks several remotes, the account and project shown come from the second remote, upstream/main, rather than the first, origin/main.

It worked before a set of undocumented edits to the source of gh-dash. The repository has
no test suite to run: finding out what is wrong, and convincing yourself you have fixed
it, is part of the task.

Restore the behavior described above.

Record the functions that contain those edits in `/app/rca.json`, one entry each:

```json
{
  "causes": [
    {
      "file": "internal/config/feature_flags.go",
      "function": "enclosing_function_name"
    }
  ]
}
```

`function` is the function name. A class prefix is ignored if you include one. When an
edit sits inside a function nested in another function, either name is accepted. Name
every function one of the undocumented edits is in, and only those. Where you wrote the
fix does not matter: if you restored the behavior from a caller or from a helper of your
own, name the function the edit is in rather than the one you wrote. If you suspect a
function but found no edit in it, leave it out.


Before you edit any code, write your research and your plan to /app/RESEARCH_AND_PLANNING.md. Cover what you learned about the existing code and the constraints that shape the change, then how you intend to carry it out and why, including how you will know it works. Be concrete - the files, names and decisions specific to this codebase, not generalities. Complete the document before you touch any code: it is the record of your up-front investigation and decisions, and it should not be rewritten to match whatever the implementation turns into afterwards. Once it is done, implement the plan.
