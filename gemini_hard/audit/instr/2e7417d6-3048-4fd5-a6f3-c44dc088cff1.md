The Terraform for our production Snipe-IT asset-management stack in `/workspace/infra` has grown into one flat root module: everything is declared at the top level, the per-AZ resources are `count`-indexed by list position, and names, settings and tags are hard-coded all over the files. Split it into four local modules (network, data, platform and admin) without touching the running infrastructure: against the current state, the plan has to come out as nothing but moves.

There is no AWS access from this machine. `terraform init` works offline from the local provider mirror, `terraform.tfstate` is a copy of the production state, and `scripts/ci-plan.sh` runs what CI runs: a `terraform plan -refresh=false` against the state followed by the guardrail policies in `policies/`.

## Detailed Constraints

**How CI judges the change.** CI takes the repository alone and plans it with `terraform plan -refresh=false` against its own copy of the production state. Local `terraform state` commands and edits to `terraform.tfstate` never reach it, so the whole migration has to be expressed in the configuration. That plan must:
- still manage every resource that is in the state today, and
- contain no create, update, replace, destroy or forget: only resources moving to new addresses.

The guardrail policies in `policies/` must pass on that plan, and `providers.tf` and everything in `policies/` stay exactly as they are, byte for byte.

**Layout.**
- The root module calls `module "network"`, `module "data"`, `module "platform"` and `module "admin"`, with sources `./modules/network`, `./modules/data`, `./modules/platform` and `./modules/admin` and one instance each, calls no other module and declares no resources of its own.
- Which module owns what (every instance of the resources described, wherever they are declared today):
  - network: the VPC and internet gateway; all public, private and database subnets; the NAT gateways and Elastic IPs; every route table, route and route table association; the network ACLs, their rules and subnet associations; the NAT error alarms; and all application, database, filesystem and administration security groups and security-group rules;
  - data: the KMS data key and alias; the EFS filesystem, mount targets and workload access points; the MySQL instance, subnet group and parameter group; the database secret and its version; and every workload's S3 artifact bucket with all bucket settings and DynamoDB lock table;
  - platform: the ECS cluster and workload task definitions; the ECR repositories and lifecycle policies; the application load balancer, listener, workload target groups and listener rules; and every workload's log group, task role and policies, job and dead-letter queues with redrive policies, alert topic, runtime parameter and alarms, together with the cross-workload operations policy, workload catalog parameter and primary-workload parameter;
  - admin: the administration IAM role, instance profile and managed-policy attachment, the SSH key pair, administration log group, launch template and auto scaling group.
- Each of these modules declares the resources it owns itself and calls no other module.
- Modules get each other's IDs and ARNs through module outputs and variables. Never paste an ID, ARN, IP address or DNS name of an existing resource, or any part of one (such as an ARN suffix), into the `.tf` files or templates. A name the configuration itself chooses (a bucket, role or parameter name, and an ARN built from that name alone, such as `arn:aws:s3:::<bucket>`) may also be derived from the same root inputs in the module that needs it, as long as no module spells today's value. The configuration reads files only through literal paths inside its own module (such as `"${path.module}/templates/..."`; in a child module a path starts with `${path.module}/`, because Terraform resolves any other relative path from the root directory, not from the module): no computed paths, no `terraform_remote_state` data sources, and never the state or a plan file.

**Keys.**
- Everything that exists once per availability zone today is a `for_each` resource keyed by the AZ name (for example `["us-east-1a"]`), including each instance of a list that also holds things that belong to no single availability zone.
- Everything that exists once per workload today is a `for_each` resource keyed by the workload name (for example `["web"]`), including each instance of a list that also holds things that belong to no single workload.
- The primary-workload parameter must describe the entry with the lowest `order`; ties are resolved by lexicographically smallest workload name. Adding, removing or changing entries must make that parameter select the resulting winner and copy that entry's name, order, queue name and health path; this parameter's in-place update is an additional permitted change under the add/remove rules below.
- Don't use `count` anywhere. Other repeated resources use `for_each` with string keys that are not numbers (a name such as `["assets"]`, never `["0"]`).
- Each existing availability zone's entry in `availability_zones` is the only source of its values: changing an entry changes, for that availability zone alone, exactly the settings the entry provides, and changes nothing else.
- `availability_zones` carries no `validation` block: every entry its type allows must work.
- Adding an availability zone to `availability_zones` must plan only the creation of that availability zone's resources, each configured exactly like its counterparts in the existing availability zones apart from the availability zone itself and the values its entry in `availability_zones` gives it (same settings, names and tags), and removing one only the destruction of that availability zone's resources. Beyond that, the only change either may plan is an in-place update of the settings that collect something from every availability zone today (wherever a setting holds a part of every availability zone: their names, IDs, ARNs, subnets or CIDRs, say, in a list, a policy document or an environment value): each of them must take in, or drop, exactly that availability zone's part where it belongs, in the same form as today (today's parts keep their order, except inside an IAM policy document, where the order of statements, actions and resources means nothing to AWS; where a new part goes is up to you), and change nothing else. No other resource may be created, updated, replaced or destroyed.
- Each existing workload's entry in `workloads` is the only source of its values: changing an entry changes, for that workload alone, exactly the settings the entry provides, and changes nothing else.
- `workloads` carries no `validation` block: every entry its type allows must work.
- Adding a workload to `workloads` must plan only the creation of that workload's resources, each configured exactly like its counterparts in the existing workloads apart from the workload itself and the values its entry in `workloads` gives it (same settings, names and tags), and removing one only the destruction of that workload's resources. Beyond that, the only change either may plan is an in-place update of the settings that collect something from every workload today (wherever a setting holds a part of every workload: their names, IDs, ARNs, subnets or CIDRs, say, in a list, a policy document or an environment value): each of them must take in, or drop, exactly that workload's part where it belongs, in the same form as today (today's parts keep their order, except inside an IAM policy document, where the order of statements, actions and resources means nothing to AWS; where a new part goes is up to you), and change nothing else. No other resource may be created, updated, replaced or destroyed.

**Root variables.** Declare these in the root module, each defaulting to today's value:
- `project` (`string`, `"snipeit"`): every whole-word occurrence of `snipeit` in a resource name, identifier or tag value today, and the `APP_PROJECT` value the administration launch template's user data writes, comes from it (whole word: not part of a longer run of letters and digits, so `snipeit-api`, `snipeit_key` and `/snipeit/` count, while a longer word that merely contains `snipeit` stays as it is), and so does every mention of those names elsewhere in the configuration (for example a resource name inside a policy); inside documents such as policies, container definitions and environment values, every whole-word occurrence of `snipeit` that stands for it comes from it too, in the case it is written there (where a value spells it `SNIPEIT` and `Snipeit`, it spells the new value the same way); the concatenated project/environment database name and concatenated project/environment IAM policy Sids follow it too; configured policy documents, descriptions, response bodies, SSH public-key comments, secret values and catalog or selection parameter values that contain the project token also follow it.
- `environment` (`string`, `"prod"`): every whole-word occurrence of `prod` in a resource name, identifier or tag value today, and the `APP_ENV` value the administration launch template's user data writes, comes from it (whole word: not part of a longer run of letters and digits, so `prod-api`, `prod_key` and `/prod/` count, while a longer word that merely contains `prod` stays as it is), and so does every mention of those names elsewhere in the configuration (for example a resource name inside a policy); inside documents such as policies, container definitions and environment values, every whole-word occurrence of `prod` that stands for it comes from it too, in the case it is written there (where a value spells it `PROD` and `Prod`, it spells the new value the same way); the concatenated project/environment database name and concatenated project/environment IAM policy Sids follow it too; configured policy documents, descriptions, response bodies, SSH public-key comments, secret values and catalog or selection parameter values that contain the environment token also follow it.
- `vpc_cidr` (`string`, `"10.42.0.0/16"`): the VPC CIDR block and the administration SSH rule's source CIDR; subnet CIDRs do not follow it.
- `availability_zones`: `map(object({ order = number, public_cidr = string, private_cidr = string, database_cidr = string, acl_rule = number }))`, keyed by AZ name, defaulting to today's three AZs, their stable collector order, three subnet CIDRs and network ACL rule number. Each entry's order is also the threshold for that AZ's NAT-error alarm. It is the only source of AZ names, AZ order, subnet CIDRs, per-AZ ACL rule numbers and NAT-error alarm thresholds.
- `workloads`: `map(object({ order = number, container_port = number, cpu = number, memory = number, health_path = string, listener_priority = number, visibility_timeout = number, queue_alarm_threshold = number, cpu_alarm_threshold = number, max_receive_count = number, image_retention_count = number }))`, keyed by workload name, defaulting to today's reports, web and worker workloads with their stable collector order, container port, task CPU and memory, health path, listener priority, queue visibility timeout, queue-depth and task-CPU alarm thresholds, redrive maximum receive count, and retained image count. It is the only source of workload names and all those per-workload settings.
- `tags` (`map(string)`, `{ Owner = "asset-platform", CostCenter = "cc-2718", ManagedBy = "terraform" }`): the shared tags (`Owner`, `CostCenter` and `ManagedBy`) that tagged resources carry today. Wherever the configuration writes them out today, in any form, they come from this variable, so that a different map (other keys, other values) reaches every one of those places; a resource's other tags stay as they are, and resources that are untagged today stay untagged.
- `db_instance_class` (`string`, `"db.t3.medium"`): the MySQL instance class.
- `db_allocated_storage` (`number`, `60`): the MySQL instance's allocated storage in GiB.
- `db_backup_retention` (`number`, `14`): the MySQL instance's backup retention in days.
- `admin_ami_id` (`string`, `"ami-0c02fb55956c7d316"`): the administration launch template's AMI.
- `admin_instance_type` (`string`, `"t3.micro"`): the administration launch template's instance type.
- `admin_max_size` (`number`, `1`): the administration auto scaling group's maximum size.
- `container_image` (`string`, `"linuxserver/snipe-it:version-v6.4.1"`): the image in every workload task definition's container definition.
- `log_retention_days` (`number`, `30`): the retention of the administration log group and every workload log group.
- `artifact_transition_days` (`number`, `30`): the Standard-IA transition age in every workload artifact bucket's lifecycle rule.
- Changing `vpc_cidr`, `db_instance_class`, `db_allocated_storage`, `db_backup_retention`, `admin_ami_id`, `admin_instance_type`, `admin_max_size`, `container_image`, `log_retention_days` and `artifact_transition_days` changes only what each one's line above says it controls: every other setting keeps today's value, including a setting that merely has the same value today.

**Root outputs.** Keep `vpc_id`, `load_balancer_dns_name`, `database_endpoint`, `efs_file_system_id` and `primary_workload_parameter_value` with their current values. `public_subnet_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_subnet.public`. `private_subnet_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_subnet.private`. `database_subnet_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_subnet.database`. `nat_public_ips` becomes a map from the AZ name to the `public_ip` of that availability zone's `aws_eip.nat`. `workload_queue_urls` becomes a map from the workload name to the `url` of that workload's `aws_sqs_queue.jobs`. `workload_bucket_names` becomes a map from the workload name to the `bucket` of that workload's `aws_s3_bucket.artifacts`. `workload_repository_urls` becomes a map from the workload name to the `repository_url` of that workload's `aws_ecr_repository.workload`. `workload_target_group_arns` becomes a map from the workload name to the `arn` of that workload's `aws_lb_target_group.workload`. `workload_runtime_parameter_arns` becomes a map from the workload name to the `arn` of that workload's `aws_ssm_parameter.workload`. `workload_access_point_ids` becomes a map from the workload name to the `id` of that workload's `aws_efs_access_point.workload`. `workload_lock_table_arns` becomes a map from the workload name to the `arn` of that workload's `aws_dynamodb_table.locks`. `workload_alert_topic_arns` becomes a map from the workload name to the `arn` of that workload's `aws_sns_topic.alerts`. `nat_gateway_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_nat_gateway.nat`. `network_acl_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_network_acl.workload`. Each output passes through outputs of the module that owns the resource (network for `vpc_id`, `public_subnet_ids`, `private_subnet_ids`, `database_subnet_ids`, `nat_public_ips`, `nat_gateway_ids` and `network_acl_ids`; data for `database_endpoint`, `efs_file_system_id`, `workload_bucket_names`, `workload_access_point_ids` and `workload_lock_table_arns`; platform for `load_balancer_dns_name`, `workload_queue_urls`, `workload_repository_urls`, `workload_target_group_arns`, `workload_runtime_parameter_arns`, `workload_alert_topic_arns` and `primary_workload_parameter_value`): the root output is a plain reference to an output of that module, and that module output is a plain reference to the resource. A plain reference is a reference such as `module.network.<output>` or `<resource type>.<name>.<attribute>`, a local that holds one, or a `for` expression that only re-keys one (`{ for k, v in <reference> : k => v.id }`) or iterates a plain reference and looks each key up in one (`{ for k, v in var.<map> : k => <reference>[k].id }`); no literals, function calls, conditionals or string templates anywhere along the way, except inside the key that picks one instance of a resource (`<reference>[sort(keys(var.<map>))[0]].id` is a plain reference).

**Not allowed anywhere in the configuration:** `ignore_changes`, `prevent_destroy` and `replace_triggered_by`, `removed` and `import` blocks, provisioners, `external` data sources, backend or cloud blocks, provider blocks other than the one in `providers.tf`, override files and `.tf.json` files.
