The Terraform for our security operations production environment in `/workspace/infra` has grown into one flat root module: everything is declared at the top level, the per-AZ resources are `count`-indexed by list position, and names, settings and tags are hard-coded all over the files. Split it into nine local modules (network, data, workload, identity, logging, response, jump, operations and alerts) without touching the running infrastructure: against the current state, the plan has to come out as nothing but moves.

There is no AWS access from this machine. `terraform init` works offline from the local provider mirror, `terraform.tfstate` is a copy of the production state, and `scripts/ci-plan.sh` runs what CI runs: a `terraform plan -refresh=false` against the state followed by the guardrail policies in `policies/`.

## Detailed Constraints

**How CI judges the change.** CI takes the repository alone and plans it with `terraform plan -refresh=false` against its own copy of the production state. Local `terraform state` commands and edits to `terraform.tfstate` never reach it, so the whole migration has to be expressed in the configuration. That plan must:
- still manage every resource that is in the state today, and
- contain no create, update, replace, destroy or forget: only resources moving to new addresses.

The guardrail policies in `policies/` must pass on that plan, and `providers.tf` and everything in `policies/` stay exactly as they are, byte for byte.

**Layout.**
- The root module calls `module "network"`, `module "data"`, `module "workload"`, `module "identity"`, `module "logging"`, `module "response"`, `module "jump"`, `module "operations"` and `module "alerts"`, with sources `./modules/network`, `./modules/data`, `./modules/workload`, `./modules/identity`, `./modules/logging`, `./modules/response`, `./modules/jump`, `./modules/operations` and `./modules/alerts` and one instance each, calls no other module and declares no resources of its own.
- Which module owns what (every instance of the resources described, wherever they are declared today):
  - network: both VPCs, the solution internet gateway, all subnets, the solution Elastic IPs and NAT gateways, its private route tables, routes and associations, both VPCs' private interface endpoints, the solution S3 gateway endpoint, and the endpoint security groups and ingress rules;
  - data: the evidence S3 buckets and their versioning settings;
  - workload: the ECS cluster, application load balancer, target groups and listeners, ECR repositories, ECS task definitions, runtime catalog parameters, and the load-balancer and workload security groups with all their rules;
  - identity: the ECS execution and task IAM roles, managed-policy attachment and evidence-bucket policy;
  - logging: the solution VPC flow log together with its CloudWatch log group and delivery IAM role and policy;
  - response: the per-AZ network catalog parameters and NAT packet alarms;
  - jump: the jump server with its bootstrap launch template, instance profile, IAM role, policy attachments including its catalog policy, security group and rules;
  - operations: the isolation and forensics security groups with their rules and the shared CloudWatch and incident-context SSM parameters;
  - alerts: the SNS topic, subscription and policy together with the EventBridge rule and target.
- Each of these modules declares the resources it owns itself and calls no other module.
- Modules get each other's IDs and ARNs through module outputs and variables. Never paste an ID, ARN, IP address or DNS name of an existing resource, or any part of one (such as an ARN suffix), into the `.tf` files or templates. The configuration reads files only through literal paths inside its own module (such as `"${path.module}/templates/..."`; in a child module a path starts with `${path.module}/`, because Terraform resolves any other relative path from the root directory, not from the module): no computed paths, no `terraform_remote_state` data sources, and never the state or a plan file.

**Keys.**
- Everything that exists once per availability zone today is a `for_each` resource keyed by the AZ name (for example `["us-east-1a"]`), including each instance of a list that also holds things that belong to no single availability zone.
- Preserve the existing order wherever a setting collects values from every AZ; the legacy private-subnet associations use a different count order from the other AZ resources. Wherever a singleton setting records a primary AZ, it is the available AZ with the lowest `response_rank`, breaking a tie by lexicographically smallest AZ name.
- Everything that exists once per workload today is a `for_each` resource keyed by the workload name (for example `["telemetry"]`), including each instance of a list that also holds things that belong to no single workload.
- Preserve the existing workload order wherever a policy, parameter or other setting collects a part from every workload. Wherever a singleton setting records a primary workload, it is the available workload with the lowest `priority`, breaking a tie by lexicographically smallest workload name.
- Don't use `count` anywhere. Other repeated resources use `for_each` with string keys that are not numbers (a name such as `["assets"]`, never `["0"]`).
- Each existing availability zone's entry in `availability_zones` is the only source of its values: changing an entry changes, for that availability zone alone, exactly the settings the entry provides, and changes nothing else.
- Adding an availability zone to `availability_zones` must plan only the creation of that availability zone's resources, each configured exactly like its counterparts in the existing availability zones apart from the availability zone itself and the values its entry in `availability_zones` gives it (same settings, names and tags), and removing one only the destruction of that availability zone's resources. Beyond that, the only change either may plan is an in-place update of the settings that collect something from every availability zone today (wherever a setting holds a part of every availability zone: their names, IDs, ARNs, subnets or CIDRs, say, in a list, a policy document or an environment value): each of them must take in, or drop, exactly that availability zone's part where it belongs, in the same form as today (today's parts keep their order, except inside an IAM policy document, where the order of statements, actions and resources means nothing to AWS; where a new part goes is up to you), and change nothing else. No other resource may be created, updated, replaced or destroyed.
- Each existing workload's entry in `workloads` is the only source of its values: changing an entry changes, for that workload alone, exactly the settings the entry provides, and changes nothing else.
- Adding a workload to `workloads` must plan only the creation of that workload's resources, each configured exactly like its counterparts in the existing workloads apart from the workload itself and the values its entry in `workloads` gives it (same settings, names and tags), and removing one only the destruction of that workload's resources. Beyond that, the only change either may plan is an in-place update of the settings that collect something from every workload today (wherever a setting holds a part of every workload: their names, IDs, ARNs, subnets or CIDRs, say, in a list, a policy document or an environment value): each of them must take in, or drop, exactly that workload's part where it belongs, in the same form as today (today's parts keep their order, except inside an IAM policy document, where the order of statements, actions and resources means nothing to AWS; where a new part goes is up to you), and change nothing else. No other resource may be created, updated, replaced or destroyed.

**Root variables.** Declare these in the root module, each defaulting to today's value:
- `project` (`string`, `"secops"`): every whole-word occurrence of `secops` in a resource name, identifier or tag value today, and the `PROJECT` value the jump server's user data writes, comes from it (whole word: not part of a longer run of letters and digits, so `secops-api`, `secops_key` and `/secops/` count, while a longer word that merely contains `secops` stays as it is), and so does every mention of those names elsewhere in the configuration (for example a resource name inside a policy); inside documents such as policies, container definitions and environment values, every whole-word occurrence of `secops` that stands for it comes from it too.
- `environment` (`string`, `"prod"`): every whole-word occurrence of `prod` in a resource name, identifier or tag value today, and the `ENVIRONMENT` value the jump server's user data writes, comes from it (whole word: not part of a longer run of letters and digits, so `prod-api`, `prod_key` and `/prod/` count, while a longer word that merely contains `prod` stays as it is), and so does every mention of those names elsewhere in the configuration (for example a resource name inside a policy); inside documents such as policies, container definitions and environment values, every whole-word occurrence of `prod` that stands for it comes from it too.
- `availability_zones`: `map(object({ public_cidr = string, private_cidr = string, endpoint_cidr = string, response_rank = number, nat_alarm_threshold = number }))`, keyed by the solution deployment's AZ name, defaulting to today's three AZs and their public, private and endpoint subnet CIDRs, incident-response rank (also the NAT alarm's evaluation-period count) and NAT dropped-packet alarm threshold. It is the only source of the solution deployment's AZ names and those per-AZ settings.
- `workloads`: `map(object({ port = number, internal_port = number, cpu = number, memory = number, priority = number, health_path = string }))`, keyed by workload name, defaulting to today's three Fargate task-catalog entries and their external load-balancer listener port, internal container port, task CPU, task memory, incident priority and target-group health path. It is the only source of workload names and those per-workload settings.
- `tags` (`map(string)`, `{ Owner = "security-platform", CostCenter = "cc-7310", ManagedBy = "terraform", Compliance = "soc2" }`): the shared tags (`Owner`, `CostCenter`, `ManagedBy` and `Compliance`) that tagged resources carry today. Wherever the configuration writes them out today, in any form, they come from this variable, so that a different map (other keys, other values) reaches every one of those places; a resource's other tags stay as they are, and resources that are untagged today stay untagged.
- `network_cidrs` (`object({ solution = string, security = string })`, `{ solution = "10.0.0.0/16", security = "10.20.0.0/16" }`): the solution and security VPC CIDRs: each field drives its VPC and every security-group rule that intentionally allows that whole range; neither field changes subnet CIDRs.
- `runtime_settings` (`object({ log_retention_days = number, jump_ami_id = string, jump_instance_type = string })`, `{ log_retention_days = 14, jump_ami_id = "ami-0c02fb55956c7d316", jump_instance_type = "t3.micro" }`): the retention of every CloudWatch log group and the security jump server's AMI and instance type.
- Changing `network_cidrs` and `runtime_settings` changes only what each one's line above says it controls: every other setting keeps today's value, including a setting that merely has the same value today.

**Root outputs.** Keep `solution_vpc_id`, `security_vpc_id`, `load_balancer_dns_name`, `alerts_topic_arn` and `jump_instance_id` with their current values. `public_subnet_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_subnet.public`. `private_subnet_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_subnet.private`. `endpoint_subnet_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_subnet.endpoint`. `nat_gateway_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_nat_gateway.solution`. `workload_repository_urls` becomes a map from the workload name to the `repository_url` of that workload's `aws_ecr_repository.workload`. `target_group_arns` becomes a map from the workload name to the `arn` of that workload's `aws_lb_target_group.workload`. `task_definition_arns` becomes a map from the workload name to the `arn` of that workload's `aws_ecs_task_definition.workload`. `evidence_bucket_names` becomes a map from the workload name to the `bucket` of that workload's `aws_s3_bucket.evidence`. `nat_alarm_arns` becomes a map from the AZ name to the `arn` of that availability zone's `aws_cloudwatch_metric_alarm.nat_packets`. `az_catalog_parameter_names` becomes a map from the AZ name to the `name` of that availability zone's `aws_ssm_parameter.az_catalog`. Each output passes through outputs of the module that owns the resource (network for `solution_vpc_id`, `security_vpc_id`, `public_subnet_ids`, `private_subnet_ids`, `endpoint_subnet_ids` and `nat_gateway_ids`; data for `evidence_bucket_names`; workload for `workload_repository_urls`, `target_group_arns`, `task_definition_arns` and `load_balancer_dns_name`; response for `nat_alarm_arns` and `az_catalog_parameter_names`; jump for `jump_instance_id`; alerts for `alerts_topic_arn`): the root output is a plain reference to an output of that module, and that module output is a plain reference to the resource. A plain reference is a reference such as `module.network.<output>` or `<resource type>.<name>.<attribute>`, a local that holds one, or a `for` expression that only re-keys one (`{ for k, v in <reference> : k => v.id }`) or iterates a plain reference and looks each key up in one (`{ for k, v in var.<map> : k => <reference>[k].id }`); no literals, function calls, conditionals or string templates anywhere along the way.

**Not allowed anywhere in the configuration:** `ignore_changes`, `prevent_destroy` and `replace_triggered_by`, `removed` and `import` blocks, provisioners, `external` data sources, backend or cloud blocks, provider blocks other than the one in `providers.tf`, override files and `.tf.json` files.
