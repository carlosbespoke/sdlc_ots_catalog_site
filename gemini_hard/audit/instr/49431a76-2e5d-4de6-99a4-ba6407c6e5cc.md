We generate QR codes inside a C++ tool that can't link Rust, so I need a C++ port of the `houseme/qrcode-rs` crate. The Rust source is in `/app/rust_reference/`. The library itself is under `src/`; the `crates/` folder holds front-ends (CLI, PDF, SVG, image and so on), which you can use for reference but don't need to port. I've laid out the C++ API in `/app/port/crate.hpp` with every signature our code calls, but the bodies are stubs. Could you implement it so it behaves exactly like the Rust crate?
When you're done I'll run the crate's own test suite, ported to C++, against `/app/port`. I'm not including those tests here, so please work from the Rust source and match it closely: error cases, edge cases, masks and version selection, numeric precision and ordering.
Some background on how our test build works, because it explains most of the rules below. The port is header-only C++17. Every test file includes `test_harness.hpp` and `crate.hpp`, all of them are compiled together with `main.cpp` into one program, and each test then runs as its own process: a test passes when its process exits with 0. So:
- Everything defined in your headers must be `inline` (or a template, or a member defined inside its class), and two different things must never share a name. Otherwise the link or the one-definition rule breaks for every test.
- You can split the implementation into extra `.hpp` files included from `crate.hpp`. Only `.hpp` files in `/app/port` are picked up, so don't put code you need in `.h`, `.inc` or `.cpp` files.
- Keep every signature exactly as declared, return types included. The tests read concrete fields and accessor results, enum values among them, and the harness only compares types it knows. Let enums use their built-in comparisons and don't add `operator==`, `operator<` or other comparison operators for them.
- Don't write a `main()` or `TEST(...)` cases, and don't modify or refer to the harness (`th::`, `test_harness`).
- The headers should only compute results when their functions are called. They must not be able to end or replace the process or change its exit status: no `exit`, `_exit`, `_Exit`, `quick_exit`, `abort`, `pthread_exit`, `thrd_exit`, `system`, `popen`/`pclose`, `daemon`, `exec*` (including `execveat`), `posix_spawn`, `dlopen`/`dlsym`, `errx`, `syscall`, raw syscalls or inline assembly, and none of glibc's `argp_parse`/`argp_help`/`argp_state_help`/`argp_error`/`argp_failure`, which exit too. Those names are reserved, so don't use them for your own functions, methods or variables either; call a helper `run_system`, not `system`.
- For the same reason, leave out these headers entirely: `<cstdlib>`, `<stdlib.h>`, `<unistd.h>`, `<csignal>`, `<fstream>`, `<pthread.h>`, `<thread>`, `<threads.h>`, `<csetjmp>`, `<setjmp.h>`, `<spawn.h>`, `<err.h>`, `<error.h>` and `<dlfcn.h>`. Also don't open files (`fopen`, `open`, `openat`, `creat`, `ifstream`, `ofstream`) or read the command line or environment (`/proc/...`, `environ`, `program_invocation_name`, `__libc_argv`, `getpid`). The standard algorithm and container headers cover everything a port needs.
- No code may run before or after `main`. That rules out namespace-scope or static objects whose constructors or destructors do more than set up or release their own data, constructor attributes (`__attribute__((constructor))`, `[[gnu::constructor]]` and the like), `atexit`/`at_quick_exit`/`__cxa_atexit` hooks, and `.init_array`/`.ctors` sections. Ordinary destructors that free what an object owns are fine, and so are plain global lookup tables.
- Prefer `constexpr` constants and inline functions to macros. If you `#define` something, `#undef` it at the end of the file that defines it; normal include guards and feature macros such as `__STDC_FORMAT_MACROS` around a system include are fine. Don't redefine a macro the toolchain, the harness or the tests define, unless it's the identical definition (e.g. `#define _GNU_SOURCE 1`). Never define or undefine a C++ keyword, the harness macros (`CHECK`, `CHECK_EQ`, `CHECK_NEAR`, `CHECK_THROWS`, `TEST`), `assert`, `NDEBUG` or anything starting with `MIG_`. Also leave out `#line`, `%:` digraph directives and the `push_macro`/`pop_macro`/`redefine_extname`/`GCC system_header` pragmas, and don't use `push_macro` or `pop_macro` as identifiers.
- Only open `namespace std` to specialize `std::hash`, `std::less` or `std::equal_to` for a type you define. Any other template specialization or out-of-line member definition has to belong to a class, struct, union, enum or namespace your own code defines with a body.
The tests are built at `-O0` on a 2-vCPU machine (each compiler process gets about 6 GB). Each test gets 75 seconds and a 2 GB address-space limit, so skip giant constant tables and heavy compile-time computation.
