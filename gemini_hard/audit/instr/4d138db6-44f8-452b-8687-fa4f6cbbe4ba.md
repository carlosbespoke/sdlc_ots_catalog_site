# leafwiki: widespread quiet misbehaviour, diagnosed without a test suite

A self-hosted server for a hierarchy of written documents, each with its own files, history and full-text lookup, is now quietly wrong across a wide spread of everyday operations. Nothing about the protocol, the stored data or the callers changed. The repository has received 28 separate undocumented edits. What follows is everything that has been observed from the outside, described by what someone was doing at the time.

Someone tidying up a document and the files hanging off it runs into trouble at almost every step. A file uploaded to a document still answers 201 and its bytes land on disk, but asking the server for that document's files comes back as a failure rather than the expected single-entry listing. Renaming one of those files through the API answers with an error status too, while uploading and deleting a single file still return 2xx and still write a history entry crediting the signed-in account. Asking for every file of a document to be removed reports success and removes nothing — a listing afterwards still shows the file that was uploaded. Duplicating a document that has one image hanging off it creates the copy, but the copy ends up with no files at all. Reordering the children of an ordinary parent no longer takes effect: submitting an explicit order for two children either fails outright or leaves them in their original order when reloaded. A document named Alpha can now be moved under a parent that already holds a child named alpha instead of being refused as a duplicate, the clash being noticed only when the two spellings match letter for letter. And when a move fails partway because the child ordering file cannot be written, the error is reported but nothing is undone: the moved file stays at the destination, the source parent has lost its entry, and the destination keeps a child it should never have gained.

Someone looking at the site in a browser sees several things come back wrong. Uploading a replacement of the picture that identifies the site no longer succeeds, so that picture can never be fetched back afterwards with a 200 and a header telling the client not to cache it. After uploading a custom small square image for the browser tab, requesting its URL no longer returns the uploaded bytes. An account that has starred exactly one document gets an empty answer when it asks for what it has starred, because the first entry is dropped; an account that has starred nothing still correctly gets nothing. Results of a full-text query are still escaped as expected, with angle brackets in a title coming back as entities, but the placeholder markings that should become bold tags are left in the output as raw control characters, so the matching term is never wrapped.

Someone loading a batch of content from an uploaded archive finds the job unreliable end to end. Preparing the work from the archive still lists the expected items, but the run started from it never reaches a completed state with its items counted, because the progress of a run in flight is no longer written out for the polling endpoint to read. In content that did land, cross-references between documents are left unresolved for one document of the batch: the first document is dropped while the mapping from paths to identifiers is built. Cancelling prepared work, which used to answer 200 with an empty body and make a later fetch of it answer 404, now comes back with an error status. And on a server configured with a small maximum upload size for files attached to documents, an archive containing a file over that limit no longer ends with that one item skipped and reported as too large.

Someone taking a backup and later putting it back finds neither half trustworthy. Writing a backup into a directory that already holds an archive named for the same timestamp no longer produces the expected name with a -2 suffix. Worse, a backup taken while the file holding long-lived access keys is present does not contain that file at all, so a key that was valid when the backup was made cannot be resolved after that backup has been put back. Putting a data directory back from an archive with nothing else running reports success but performs no swap whatsoever: the document from the archive never appears and the content that was live beforehand is still in place. Doing the same thing through the live machinery ends with an error status instead of completing, because reading a stored long-lived access key back out of its table now reads the wrong columns and the lookup fails. That same path also no longer takes the key database out of service while the swap happens — the handle stays open, the one held in memory is never cleared, and lookups against a supposedly stopped handle keep succeeding instead of failing as unavailable, and a second request to stop it is no longer a harmless no-op. One of the components assembled at startup is built without a logger argument and no longer falls back to the process-wide default, so it is left holding none. And asking the process to relaunch itself in place does nothing at all: the call returns success without ever replacing the running process with the current program, its arguments and its environment, and a permission error from the attempt is reported as success too.

Someone making ordinary requests against a running instance also sees several answers change. A state-changing POST whose token header does not match the token cookie is let through with 200 instead of being refused with 403 and an error body. Behind a proxy that advertises the forwarded protocol as HTTPS in uppercase, requests are rejected with 400 as though they had arrived unencrypted, while the same request with that value in lowercase, or as a full https:// URL, is accepted. A plain GET against the status endpoint of a freshly started instance no longer answers 200, for two independent reasons: the verdict about the data location is inverted, so that check counts as a problem exactly when it reports everything is fine, and the tally of documents that could not be made available to lookup is judged a failure even when that tally is zero, which is the normal state of a new instance. Counting how many accounts exist returns an error rather than a number, so a count taken after two accounts are created fails, and reopening a storage directory that has already been migrated once fails at that same counting step, while dropping the on-disk copy of a document's text once nothing references it reports success while the file stays on disk, the same stale file also surviving when a quick follow-up edit is folded into the earlier entry.

It worked before a set of undocumented edits to the source of leafwiki. The repository has
no test suite to run: finding out what is wrong, and convincing yourself you have fixed
it, is part of the task.

Restore the behavior described above.

Record the functions that contain those edits in `/app/rca.json`, one entry each:

```json
{
  "causes": [
    {
      "file": "internal/core/auth/apikey_service.go",
      "function": "enclosing_function_name"
    }
  ]
}
```

`function` is the function name. A class prefix is ignored if you include one. When an
edit sits inside a function nested in another function, either name is accepted. Name
every function one of the undocumented edits is in, and only those. Where you wrote the
fix does not matter: if you restored the behavior from a caller or from a helper of your
own, name the function the edit is in rather than the one you wrote. If you suspect a
function but found no edit in it, leave it out.


Before you edit any code, write your research and your plan to /app/RESEARCH_AND_PLANNING.md. Cover what you learned about the existing code and the constraints that shape the change, then how you intend to carry it out and why, including how you will know it works. Be concrete - the files, names and decisions specific to this codebase, not generalities. Complete the document before you touch any code: it is the record of your up-front investigation and decisions, and it should not be rewritten to match whatever the implementation turns into afterwards. Once it is done, implement the plan.
