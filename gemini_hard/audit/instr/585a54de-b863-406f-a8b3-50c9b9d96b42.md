A Woodpecker server restart currently forgets workflows already assigned to agents. Their cancellation signal can disappear, and a workflow abandoned by a dead agent can remain running indefinitely. Fix this across the server queue/scheduler, agent RPC lifecycle, and local-backend runner in `/app`.

- Keep assigned workflows, agent ownership, lease deadlines and dependency ordering durable in PostgreSQL. On server restart, a still-running agent retains its work; renewals prevent reassignment. A silent agent's work is re-queued for another agent or reaches `error` within 45 seconds of recovery; nothing remains `running` forever.
- A workflow with `depends_on` never starts before its dependency finishes. Two agents running separate workflows across a restart finish each workflow once, with no duplicate step execution or cross-agent completion.
- Server lease duration is configured with `WOODPECKER_TASK_LEASE` (Go duration; default one minute); agents renew at one third of that duration. A healthy 60-second workflow with a 15-second lease is not re-queued.
- After restart, cancellation through `POST /api/repos/{repo_id}/pipelines/{number}/cancel` stops the local-backend shell step within 10 seconds and leaves the pipeline `killed`, never `success`. A running agent reconnects to retain its lease and receive cancellations.
- Preserve `POST /api/repos/{repo_id}/pipelines/{number}` restarting a stored pipeline to `success`, cancellation without a restart, ordered dependencies, and complete step logs at `GET /api/repos/{repo_id}/logs/{number}/{step_id}`.

The container has PostgreSQL, the server and agent sources, and offline Go dependencies. Start PostgreSQL with `sudo service postgresql start`; the local backend runs shell steps with `skip_clone: true` and `image: /bin/sh`. Build from `/app` with `go build -tags external_web ./cmd/server ./cmd/agent` (the offline web placeholder is at `/app/.sd-web`). Only one server instance is in scope.
