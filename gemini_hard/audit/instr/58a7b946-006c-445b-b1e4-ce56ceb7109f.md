Chunked OCI pushes currently keep their in-progress bytes on the receiving Gitea instance. A request sent to another instance cannot resume the upload, and a retried range can corrupt it. We need uploads that remain correct when either instance handles the next request or one dies mid-request.

To close this out:

- For `POST /v2/{owner}/{image}/blobs/uploads/`, `PATCH`, `GET`, `PUT`, and `DELETE` at the returned upload URL, committed bytes and offsets must be shared between instances. `GET` reports the committed `Range`; a successful `PUT ?digest=sha256:...` produces that exact blob, fetchable through either instance. A process killed during a streaming PATCH loses no committed chunks; its incomplete chunk is not included in `GET` and can be retried.
- Conflicting or repeated ranges, including a stalled writer that finishes after another instance committed the range, cannot change committed bytes: answer `416` with the current `Range` (or `409` for a concurrent loser). An expired, aborted, finished or pre-upgrade local-file session answers `404` with OCI code `BLOB_UPLOAD_UNKNOWN` on PATCH or PUT; it cannot be revived.
- Account for committed package bytes and bytes held by active uploads for the same owner across instances. With `[packages] LIMIT_TOTAL_OWNER_SIZE = 100 MB`, two simultaneous 60 MB chunk uploads cannot both be accepted. Refuse an over-limit PATCH with `403` and OCI code `DENIED`, before committing its bytes. Add `GET /api/v1/packages/{owner}/usage` with integer byte fields `limit`, `used`, `reserved` (the configured owner limit, committed bytes and active holds). Deleting or finishing an upload releases its hold. Abandoned holds expire after configurable `[packages] UPLOAD_IDLE_TIMEOUT = 20s`; their objects and holds disappear within 45 seconds, and a late request cannot revive them.

Keep existing container blob GET and upload DELETE responses working. PostgreSQL, Redis and MinIO are shared across two Gitea processes; start the configured services with Docker Compose outside the agent container. Build from `/app` with `go build ./...` (offline). The solver container cannot run Docker itself.
