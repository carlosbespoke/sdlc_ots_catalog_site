The Terraform for our ecspresso production Fargate platform in `/workspace/infra` has grown into one flat root module: everything is declared at the top level, the per-AZ resources are `count`-indexed by list position, and names, settings and tags are hard-coded all over the files. Split it into four local modules (network, platform, workloads and observability) without touching the running infrastructure: against the current state, the plan has to come out as nothing but moves.

There is no AWS access from this machine. `terraform init` works offline from the local provider mirror, `terraform.tfstate` is a copy of the production state, and `scripts/ci-plan.sh` runs what CI runs: a `terraform plan -refresh=false` against the state followed by the guardrail policies in `policies/`.

## Detailed Constraints

**How CI judges the change.** CI takes the repository alone and plans it with `terraform plan -refresh=false` against its own copy of the production state. Local `terraform state` commands and edits to `terraform.tfstate` never reach it, so the whole migration has to be expressed in the configuration. That plan must:
- still manage every resource that is in the state today, and
- contain no create, update, replace, destroy or forget: only resources moving to new addresses.

The guardrail policies in `policies/` must pass on that plan, and `providers.tf` and everything in `policies/` stay exactly as they are, byte for byte.

**Layout.**
- The root module calls `module "network"`, `module "platform"`, `module "workloads"` and `module "observability"`, with sources `./modules/network`, `./modules/platform`, `./modules/workloads` and `./modules/observability` and one instance each, calls no other module and declares no resources of its own.
- Which module owns what (every instance of the resources described, wherever they are declared today):
  - network: the VPC and internet gateway, all public and private subnets, the NAT gateways and Elastic IPs, public and private route tables, routes and associations, the private network ACLs with their associations and rules, and the S3 gateway endpoint with all of its route table associations;
  - platform: the ALB and its HTTP listener, the ALB and ECS security groups with all of their rules, the ECS cluster, the shared task execution IAM role and managed-policy attachment, the KMS key and alias, both S3 buckets and all bucket settings, the DynamoDB deployments table, the alerts SNS topic, and all three SSM parameters;
  - workloads: every workload service's ECR repository and lifecycle policy, CloudWatch log group, task IAM role and inline policy, main and dead-letter SQS queues, ALB target group and listener rule, and ECS task definition;
  - observability: the VPC flow log with its CloudWatch log group, IAM role and inline policy, and every per-service CPU and queue-depth CloudWatch alarm.
- Each of these modules declares the resources it owns itself and calls no other module.
- Modules get each other's IDs and ARNs through module outputs and variables. Never paste an ID, ARN, IP address or DNS name of an existing resource, or any part of one (such as an ARN suffix), into the `.tf` files or templates. A name the configuration itself chooses (a bucket, role or parameter name, and an ARN built from that name alone, such as `arn:aws:s3:::<bucket>`) may also be derived from the same root inputs in the module that needs it, as long as no module spells today's value. The configuration reads files only through literal paths inside its own module (such as `"${path.module}/templates/..."`; in a child module a path starts with `${path.module}/`, because Terraform resolves any other relative path from the root directory, not from the module): no computed paths, no `terraform_remote_state` data sources, and never the state or a plan file.

**Keys.**
- Everything that exists once per availability zone today is a `for_each` resource keyed by the AZ name (for example `["us-east-1a"]`), including each instance of a list that also holds things that belong to no single availability zone (the S3 endpoint's associations with private route tables are per AZ; its association with the public route table is not per AZ).
- Everything that exists once per workload service today is a `for_each` resource keyed by the service name (for example `["web"]`), including each instance of a list that also holds things that belong to no single workload service.
- The primary-service SSM parameter holds the service with the lowest `workload_priority`; ties are broken by service name. The service-catalog SSM parameter preserves today's relative order among existing services regardless of `workload_priority` changes; a newly added service may appear anywhere while existing services retain their relative order.
- Don't use `count` anywhere. Other repeated resources use `for_each` with string keys that are not numbers (a name such as `["assets"]`, never `["0"]`).
- Each existing availability zone's entry in `availability_zones` is the only source of its values: changing an entry changes, for that availability zone alone, exactly the settings the entry provides, and changes nothing else.
- `availability_zones` carries no `validation` block: every entry its type allows must work.
- Adding an availability zone to `availability_zones` must plan only the creation of that availability zone's resources, each configured exactly like its counterparts in the existing availability zones apart from the availability zone itself and the values its entry in `availability_zones` gives it (same settings, names and tags), and removing one only the destruction of that availability zone's resources. Beyond that, the only change either may plan is an in-place update of the settings that collect something from every availability zone today (wherever a setting holds a part of every availability zone: their names, IDs, ARNs, subnets or CIDRs, say, in a list, a policy document or an environment value): each of them must take in, or drop, exactly that availability zone's part where it belongs, in the same form as today (today's parts keep their order, except inside an IAM policy document, where the order of statements, actions and resources means nothing to AWS; where a new part goes is up to you), and change nothing else. No other resource may be created, updated, replaced or destroyed.
- Each existing workload service's entry in `services` is the only source of its values: changing an entry changes, for that workload service alone, exactly the settings the entry provides, and changes nothing else.
- `services` carries no `validation` block: every entry its type allows must work.
- Adding a workload service to `services` must plan only the creation of that workload service's resources, each configured exactly like its counterparts in the existing workload services apart from the workload service itself and the values its entry in `services` gives it (same settings, names and tags), and removing one only the destruction of that workload service's resources. Beyond that, the only change either may plan is an in-place update of the settings that collect something from every workload service today (wherever a setting holds a part of every workload service: their names, IDs, ARNs, subnets or CIDRs, say, in a list, a policy document or an environment value): each of them must take in, or drop, exactly that workload service's part where it belongs, in the same form as today (today's parts keep their order, except inside an IAM policy document, where the order of statements, actions and resources means nothing to AWS; where a new part goes is up to you), and change nothing else. No other resource may be created, updated, replaced or destroyed.

**Root variables.** Declare these in the root module, each defaulting to today's value:
- `project` (`string`, `"ecspresso"`): every whole-word occurrence of `ecspresso` in a resource name, identifier or tag value today comes from it (whole word: not part of a longer run of letters and digits, so `ecspresso-api`, `ecspresso_key` and `/ecspresso/` count, while a longer word that merely contains `ecspresso` stays as it is), and so does every mention of those names elsewhere in the configuration (for example a resource name inside a policy); inside documents such as policies, container definitions and environment values, every whole-word occurrence of `ecspresso` that stands for it comes from it too.
- `environment` (`string`, `"prod"`): every whole-word occurrence of `prod` in a resource name, identifier or tag value today comes from it (whole word: not part of a longer run of letters and digits, so `prod-api`, `prod_key` and `/prod/` count, while a longer word that merely contains `prod` stays as it is), and so does every mention of those names elsewhere in the configuration (for example a resource name inside a policy); inside documents such as policies, container definitions and environment values, every whole-word occurrence of `prod` that stands for it comes from it too.
- `vpc_cidr` (`string`, `"10.72.0.0/16"`): the VPC's CIDR block.
- `availability_zones`: `map(object({ public_cidr = string, private_cidr = string }))`, keyed by AZ name, defaulting to today's three AZs and their public and private subnet CIDRs. It is the only source of AZ names and subnet CIDRs.
- `services`: `map(object({ workload_priority = number }))`, keyed by service name, defaulting to today's worker, web and scheduler services and their workload priorities. It is the only source of service names and workload priorities.
- `tags` (`map(string)`, `{ Owner = "platform-team", CostCenter = "cc-2841", ManagedBy = "terraform" }`): the shared tags (`Owner`, `CostCenter` and `ManagedBy`) that tagged resources carry today. Wherever the configuration writes them out today, in any form, they come from this variable, so that a different map (other keys, other values) reaches every one of those places; a resource's other tags stay as they are, and resources that are untagged today stay untagged.
- `container_port` (`number`, `3000`): the port of every target group and both the container and host port in every task definition.
- `task_cpu` (`number`, `512`): the task-level and container-level CPU units in every task definition.
- `task_memory` (`number`, `1024`): the task-level and container-level memory in every task definition.
- `log_retention_days` (`number`, `30`): the retention of every CloudWatch log group.
- `alarm_period_seconds` (`number`, `300`): the metric period of every CloudWatch alarm.
- `alarm_evaluation_periods` (`number`, `2`): the evaluation periods of every CloudWatch alarm.
- `queue_retention_seconds` (`number`, `345600`): the message retention of every main workload queue; dead-letter queue retention keeps today's value.
- `access_log_expiration_days` (`number`, `90`): the current-version expiration in the access-log bucket's lifecycle rule; noncurrent-version expiration keeps today's value.
- Changing `vpc_cidr`, `container_port`, `task_cpu`, `task_memory`, `log_retention_days`, `alarm_period_seconds`, `alarm_evaluation_periods`, `queue_retention_seconds` and `access_log_expiration_days` changes only what each one's line above says it controls: every other setting keeps today's value, including a setting that merely has the same value today.

**Root outputs.** Keep `vpc_id`, `alb_dns_name`, `cluster_name`, `artifacts_bucket_name` and `deployments_table_name` with their current values. Add `primary_service`: the `value` of `aws_ssm_parameter.primary_service`. `public_subnet_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_subnet.public`. `private_subnet_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_subnet.private`. `nat_public_ips` becomes a map from the AZ name to the `public_ip` of that availability zone's `aws_eip.private`. `service_repository_urls` becomes a map from the service name to the `repository_url` of that workload service's `aws_ecr_repository.service`. `service_queue_urls` becomes a map from the service name to the `url` of that workload service's `aws_sqs_queue.service`. `service_task_definition_arns` is a new output: a map from the service name to the `arn` of that workload service's `aws_ecs_task_definition.service`. Each output passes through outputs of the module that owns the resource (network for `vpc_id`, `public_subnet_ids`, `private_subnet_ids` and `nat_public_ips`; platform for `alb_dns_name`, `cluster_name`, `artifacts_bucket_name`, `deployments_table_name` and `primary_service`; workloads for `service_repository_urls`, `service_queue_urls` and `service_task_definition_arns`): the root output is a plain reference to an output of that module, and that module output is a plain reference to the resource. A plain reference is a reference such as `module.network.<output>` or `<resource type>.<name>.<attribute>`, a local that holds one, or a `for` expression that only re-keys one (`{ for k, v in <reference> : k => v.id }`) or iterates a plain reference and looks each key up in one (`{ for k, v in var.<map> : k => <reference>[k].id }`); no literals, function calls, conditionals or string templates anywhere along the way, except inside the key that picks one instance of a resource (`<reference>[sort(keys(var.<map>))[0]].id` is a plain reference).

**Not allowed anywhere in the configuration:** `ignore_changes`, `prevent_destroy` and `replace_triggered_by`, `removed` and `import` blocks, provisioners, `external` data sources, backend or cloud blocks, provider blocks other than the one in `providers.tf`, override files and `.tf.json` files.
