The Terraform for our DevOps Mono production delivery stack in `/workspace/infra` has grown into one flat root module: everything is declared at the top level, the per-AZ resources are `count`-indexed by list position, and names, settings and tags are hard-coded all over the files. Split it into four local modules (network, data, identity and delivery) without touching the running infrastructure: against the current state, the plan has to come out as nothing but moves.

There is no AWS access from this machine. `terraform init` works offline from the local provider mirror, `terraform.tfstate` is a copy of the production state, and `scripts/ci-plan.sh` runs what CI runs: a `terraform plan -refresh=false` against the state followed by the guardrail policies in `policies/`.

## Detailed Constraints

**How CI judges the change.** CI takes the repository alone and plans it with `terraform plan -refresh=false` against its own copy of the production state. Local `terraform state` commands and edits to `terraform.tfstate` never reach it, so the whole migration has to be expressed in the configuration. That plan must:
- still manage every resource that is in the state today, and
- contain no create, update, replace, destroy or forget: only resources moving to new addresses.

The guardrail policies in `policies/` must pass on that plan, and `providers.tf` and everything in `policies/` stay exactly as they are, byte for byte.

**Layout.**
- The root module calls `module "network"`, `module "data"`, `module "identity"` and `module "delivery"`, with sources `./modules/network`, `./modules/data`, `./modules/identity` and `./modules/delivery` and one instance each, calls no other module and declares no resources of its own.
- Which module owns what (every instance of the resources described, wherever they are declared today):
  - network: the VPC, internet gateway, public, private and database subnets, NAT gateways and their Elastic IPs, public, private and database route tables, routes and route table associations, the S3 gateway endpoint and all of its route table associations, the VPC flow log with its CloudWatch log group, IAM role and inline policy, and the per-AZ subnet-config and network-inventory SSM parameters;
  - data: the KMS key and alias, release and trail buckets with all of their versioning, encryption and public-access settings, every deployment track's CloudWatch log group, SQS queue, SNS topic, DynamoDB release-lock table and track-config SSM parameter, the MySQL instance with its subnet group and parameter group, the database security group and ingress rule, and the deployment-manifest and track-inventory SSM parameters;
  - identity: the Jenkins and application IAM roles and instance profiles, the CodeCommit access policy and both of its role attachments, and the application's inline deployment-access policy;
  - delivery: the application load balancer, every deployment track's target group, launch template, auto scaling group and CPU alarm, the HTTP listener, and the load balancer, application and Jenkins security groups with all of their rules.
- Each of these modules declares the resources it owns itself and calls no other module.
- Modules get each other's IDs and ARNs through module outputs and variables. Never paste an ID, ARN, IP address or DNS name of an existing resource, or any part of one (such as an ARN suffix), into the `.tf` files or templates. A name the configuration itself chooses (a bucket, role or parameter name, and an ARN built from that name alone, such as `arn:aws:s3:::<bucket>`) may also be derived from the same root inputs in the module that needs it, as long as no module spells today's value. The configuration reads files only through literal paths inside its own module (such as `"${path.module}/templates/..."`; in a child module a path starts with `${path.module}/`, because Terraform resolves any other relative path from the root directory, not from the module): no computed paths, no `terraform_remote_state` data sources, and never the state or a plan file.

**Keys.**
- Everything that exists once per availability zone today is a `for_each` resource keyed by the AZ name (for example `["us-east-1a"]`), including each instance of a list that also holds things that belong to no single availability zone (the S3 gateway endpoint's associations with the private route tables are per AZ; the endpoint's single association with the public route table is not per AZ).
- Each AZ's subnet-config parameter records its AZ and all three CIDRs, and the network-inventory parameter collects those records for every AZ in today's AZ order.
- Everything that exists once per deployment track today is a `for_each` resource keyed by the track name (for example `["blue"]`), including each instance of a list that also holds things that belong to no single deployment track.
- The HTTP listener forwards to the remaining track with the lowest routing priority, breaking ties by track name. Each track-config parameter records every setting from that track's entry, and the track-inventory parameter collects the same records for every track in routing-priority order, also breaking ties by track name.
- Don't use `count` anywhere. Other repeated resources use `for_each` with string keys that are not numbers (a name such as `["assets"]`, never `["0"]`).
- Each existing availability zone's entry in `availability_zones` is the only source of its values: changing an entry changes, for that availability zone alone, exactly the settings the entry provides, and changes nothing else.
- `availability_zones` carries no `validation` block: every entry its type allows must work.
- Adding an availability zone to `availability_zones` must plan only the creation of that availability zone's resources, each configured exactly like its counterparts in the existing availability zones apart from the availability zone itself and the values its entry in `availability_zones` gives it (same settings, names and tags), and removing one only the destruction of that availability zone's resources. Beyond that, the only change either may plan is an in-place update of the settings that collect something from every availability zone today (wherever a setting holds a part of every availability zone: their names, IDs, ARNs, subnets or CIDRs, say, in a list, a policy document or an environment value): each of them must take in, or drop, exactly that availability zone's part where it belongs, in the same form as today (today's parts keep their order, except inside an IAM policy document, where the order of statements, actions and resources means nothing to AWS; where a new part goes is up to you), and change nothing else. No other resource may be created, updated, replaced or destroyed.
- Each existing deployment track's entry in `deployment_tracks` is the only source of its values: changing an entry changes, for that deployment track alone, exactly the settings the entry provides, and changes nothing else.
- `deployment_tracks` carries no `validation` block: every entry its type allows must work.
- Adding a deployment track to `deployment_tracks` must plan only the creation of that deployment track's resources, each configured exactly like its counterparts in the existing deployment tracks apart from the deployment track itself and the values its entry in `deployment_tracks` gives it (same settings, names and tags), and removing one only the destruction of that deployment track's resources. Beyond that, the only change either may plan is an in-place update of the settings that collect something from every deployment track today (wherever a setting holds a part of every deployment track: their names, IDs, ARNs, subnets or CIDRs, say, in a list, a policy document or an environment value): each of them must take in, or drop, exactly that deployment track's part where it belongs, in the same form as today (today's parts keep their order, except inside an IAM policy document, where the order of statements, actions and resources means nothing to AWS; where a new part goes is up to you), and change nothing else. No other resource may be created, updated, replaced or destroyed.

**Root variables.** Declare these in the root module, each defaulting to today's value:
- `project` (`string`, `"devopsmono"`): every whole-word occurrence of `devopsmono` in a resource name, identifier or tag value today, and the `PROJECT` value written by every deployment track's launch-template user data, comes from it (whole word: not part of a longer run of letters and digits, so `devopsmono-api`, `devopsmono_key` and `/devopsmono/` count, while a longer word that merely contains `devopsmono` stays as it is), and so does every mention of those names elsewhere in the configuration (for example a resource name inside a policy); inside documents such as policies, container definitions and environment values, every whole-word occurrence of `devopsmono` that stands for it comes from it too; more generally, every whole-word occurrence of `devopsmono` in any string the configuration writes comes from it, including free-text descriptions (security-group and security-group-rule descriptions, the KMS key description and alarm descriptions) and identifiers such as a CloudWatch alarm namespace; the MySQL database name's project prefix comes from it even though that prefix is joined directly to the environment token without a separator.
- `environment` (`string`, `"prod"`): every whole-word occurrence of `prod` in a resource name, identifier or tag value today, and the `APP_ENV` value written by every deployment track's launch-template user data, comes from it (whole word: not part of a longer run of letters and digits, so `prod-api`, `prod_key` and `/prod/` count, while a longer word that merely contains `prod` stays as it is), and so does every mention of those names elsewhere in the configuration (for example a resource name inside a policy); inside documents such as policies, container definitions and environment values, every whole-word occurrence of `prod` that stands for it comes from it too; more generally, every whole-word occurrence of `prod` in any string the configuration writes comes from it, including free-text descriptions (security-group and security-group-rule descriptions, the KMS key description and alarm descriptions) and identifiers such as a CloudWatch alarm namespace; the MySQL database name's environment suffix comes from it even though that suffix is joined directly to the project token without a separator.
- `vpc_cidr` (`string`, `"10.27.0.0/16"`): the VPC's CIDR block and the database ingress rule's source range; subnet CIDRs remain controlled only by the availability-zone map.
- `availability_zones`: `map(object({ public_cidr = string, private_cidr = string, database_cidr = string }))`, keyed by AZ name, defaulting to today's three AZs and their public, private and database subnet CIDRs. It is the only source of AZ names and subnet CIDRs.
- `deployment_tracks`: `map(object({ queue_visibility = number, queue_retention = number, log_retention = number, desired_capacity = number, maximum_capacity = number, service_port = number, health_path = string, cpu_threshold = number, routing_priority = number }))`, keyed by deployment track name, defaulting to today's green, canary and blue tracks and each track's queue visibility timeout, queue retention, log retention, desired capacity, maximum capacity, service port, health-check path, CPU alarm threshold and routing priority. It is the only source of track names and those settings.
- `tags` (`map(string)`, `{ Owner = "platform-team", CostCenter = "cc-2793", ManagedBy = "terraform" }`): the shared tags (`Owner`, `CostCenter` and `ManagedBy`) that tagged resources carry today. Wherever the configuration writes them out today, in any form, they come from this variable, so that a different map (other keys, other values) reaches every one of those places; a resource's other tags stay as they are, and resources that are untagged today stay untagged.
- `flow_log_retention_days` (`number`, `30`): the VPC flow-log group's retention in days.
- `app_ami_id` (`string`, `"ami-0b69ea66ff7391e80"`): the AMI used by every deployment track's launch template.
- `app_instance_type` (`string`, `"t3.small"`): the instance type used by every deployment track's launch template.
- `app_min_size` (`number`, `1`): the minimum size of every deployment track's auto scaling group.
- `db_instance_class` (`string`, `"db.t3.medium"`): the MySQL instance class.
- `db_allocated_storage` (`number`, `40`): the MySQL instance's allocated storage in GiB.
- `db_backup_retention` (`number`, `7`): the MySQL instance's backup retention in days.
- Changing `vpc_cidr`, `flow_log_retention_days`, `app_ami_id`, `app_instance_type`, `app_min_size`, `db_instance_class`, `db_allocated_storage` and `db_backup_retention` changes only what each one's line above says it controls: every other setting keeps today's value, including a setting that merely has the same value today.

**Root outputs.** Keep `vpc_id`, `load_balancer_dns`, `releases_bucket_name` and `database_endpoint` with their current values. `public_subnet_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_subnet.public`. `private_subnet_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_subnet.private`. `database_subnet_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_subnet.database`. `nat_public_ips` becomes a map from the AZ name to the `public_ip` of that availability zone's `aws_eip.nat_eip`. `track_queue_urls` becomes a map from the track name to the `url` of that deployment track's `aws_sqs_queue.deploy_events`. `track_topic_arns` becomes a map from the track name to the `arn` of that deployment track's `aws_sns_topic.deploy_alerts`. `track_log_groups` becomes a map from the track name to the `name` of that deployment track's `aws_cloudwatch_log_group.track`. `subnet_config_names` is a new output: a map from the AZ name to the `name` of that availability zone's `aws_ssm_parameter.subnet_config`. `track_config_names` is a new output: a map from the track name to the `name` of that deployment track's `aws_ssm_parameter.track_config`. `track_target_group_arns` is a new output: a map from the track name to the `arn` of that deployment track's `aws_lb_target_group.track`. `track_autoscaling_group_names` is a new output: a map from the track name to the `name` of that deployment track's `aws_autoscaling_group.track`. Each output passes through outputs of the module that owns the resource (network for `vpc_id`, `public_subnet_ids`, `private_subnet_ids`, `database_subnet_ids`, `nat_public_ips` and `subnet_config_names`; data for `track_queue_urls`, `track_topic_arns`, `track_log_groups`, `releases_bucket_name`, `database_endpoint` and `track_config_names`; delivery for `load_balancer_dns`, `track_target_group_arns` and `track_autoscaling_group_names`): the root output is a plain reference to an output of that module, and that module output is a plain reference to the resource. A plain reference is a reference such as `module.network.<output>` or `<resource type>.<name>.<attribute>`, a local that holds one, or a `for` expression that only re-keys one (`{ for k, v in <reference> : k => v.id }`) or iterates a plain reference and looks each key up in one (`{ for k, v in var.<map> : k => <reference>[k].id }`); no literals, function calls, conditionals or string templates anywhere along the way, except inside the key that picks one instance of a resource (`<reference>[sort(keys(var.<map>))[0]].id` is a plain reference).

**Not allowed anywhere in the configuration:** `ignore_changes`, `prevent_destroy` and `replace_triggered_by`, `removed` and `import` blocks, provisioners, `external` data sources, backend or cloud blocks, provider blocks other than the one in `providers.tf`, override files and `.tf.json` files.
