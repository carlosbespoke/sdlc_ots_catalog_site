# jjui-regen

Working with a recent build of this keyboard-driven terminal front end for a version control system, I hit a scatter of misbehaviour that does not seem to share one cause. The repository has received 30 separate undocumented edits. Below is everything I could reproduce, written as what I did and what came back.

Moving a highlight around and acting on whatever it sits on. In the panel that keeps previously issued instructions beside their output, with six entries recorded, the highlight starts on the newest but each press in either direction lands somewhere other than the neighbouring entry; and an entry whose output spans several lines, while it is the highlighted one, is missing from what gets drawn, neither its heading line nor any of its body appearing. Asking to remove the highlighted entry there does nothing at all: it stays in the visible list, it stays in the record behind the list, and the tally of live messages does not drop. Recall in the little field at the bottom is dead as well: with the as-you-type completion hint switched off, the key that opens the prompt for running an external instruction does focus the field, but pressing up leaves it empty instead of bringing back something I ran earlier, and pressing down afterwards yields the same text again rather than a neighbouring entry. And in the list of labels that can be moved onto the current change, pressing the filter key twice highlights the nearby candidate on the first press as it always did, while the second press, which should jump to the well-known default label and carry out the move onto it, issues no move at all.

Being asked a question and expecting it to go away. Rolling back the most recent change still raises its confirmation question, but pressing n there leaves the question on screen instead of closing it, and the question offered for reapplying a change that was just rolled back behaves the same way. A different prompt, the one that lists a handful of alternatives and asks me to pick one, draws almost nothing: given eighty columns and twenty rows of space, its heading and the entries of its list never reach the screen, in its plain form and in its numbered form alike.

Getting things into the space available on screen. With the side pane shown on the right at half width, the two keys that widen and narrow it no longer move the divider at all; the pane keeps exactly its size whichever one I press. When the terminal announces its background colour, the first announcement should record that colour and rebuild the theme around it, a repeat of the same colour should do nothing, and a later different colour should rebuild again and re-query the palette; that ordering breaks from the very first announcement. With a two-key combination in my bindings, pressing its first key used to grow the strip at the bottom and list the key that completes it; now the strip does not grow and no continuation is offered, so nothing on screen says a combination is pending. Opening a revision in the log to see its changed files is wrong in three ways at once: the expanded block refuses to sit below the row it belongs to, the height it reports for that placement coming back as nothing; with a filter typed in that matches no file, neither the filter line nor the notice that nothing matched fits into the two lines set aside for them; and what does get drawn sits one line lower than it should, so in a log where a row is followed by a marker for elided revisions the file entries now come after that marker instead of between the row and it.

Picking a file to work on. Handing over a set of file names to be offered for a pick filters them backwards: given three entries of which one is blank, the blank one is kept and the two real names are thrown away. That shows the moment I open the overlay that offers files on top of a displayed diff — the overlay is created, but the one file it should list never appears in the drawing, and its contents are stacked at the wrong depth relative to the frame around them, so they would be covered even if the names had survived. Narrowing the log by file path fails twice more: the list of paths worked out from the raw listing comes back empty, with neither the directory prefixes nor the file names in it, and applying the narrowing while nothing is highlighted rewrites the query instead of leaving it be, wrapping it around an empty path.

Asking it to do something to the repository, by key or by script. The invocation assembled to stop tracking a named label on a remote drops the remote entirely, while the ones for moving, deleting, forgetting and starting to track the same label all still carry their exactly quoted arguments, remote included. Running an action with a true-or-false option supplied in its argument map ignores the option: asking for the forcing variant of the apply step, in either of the two flows that accept it, produces a request with the flag unset, exactly as though nothing had been passed. A script asking for the id of the currently highlighted change gets nothing back when what is picked is a file inside a change, though when a whole change is picked the same question still answers with its id. Loading a user's startup script has regressed in two shapes: declaring an action and then binding a key to it in a second step still works, but declaring an action with its key and the place it applies given inline in the same call no longer succeeds, and a script that pulls in a helper file sitting beside it in the settings folder no longer loads. The helper that answers password prompts on behalf of child processes is wrong at two points too: merely starting it, enrolling a child and then cancelling leaves its tally of live children wrong, and a real ssh login driven through it — refusing the first prompt, answering the second with a wrong password and the third with the right one — never reaches the successful authentication, because what I type does not get back to the process that asked.

Asking what it can do, and keeping the checked-in descriptions of that in step. The one-line calling form shown for the built-in query helpers is mangled wherever a parameter may be given by name: the bracketed name and the equals sign that should precede the placeholder are gone, and the two run together as one word, while forms for plain required parameters and for simple optional ones read fine. Listing my own shorthand queries is wrong for every one whose definition ends in a parameter list — the name comes back with its parentheses still attached instead of stripped, and whether it takes parameters is answered no in all cases, including one declared with two parameters — though a shorthand written without parentheses is reported properly. The checked-in files that describe every available action are no longer reproduced, and in one respect it does not even get that far: checking now rejects a rule that assigns a plain true or false to a flag, treating it as unacceptable, so nothing is written. Past that, what is produced differs from what is committed in several ways: the fixed sets of allowed values that the rules actually use are left out while sets no rule mentions are listed, the constants naming where each rule applies are taken one position off in the list they come from, and the argument references written into the rules resolve to the wrong thing. That last problem shows in the produced type declarations for the embedded language too, which additionally treat actions carrying the closing token inversely, so those declarations cover the wrong set of entries.

It worked before a set of undocumented edits to the source of jjui. The repository has
no test suite to run: finding out what is wrong, and convincing yourself you have fixed
it, is part of the task.

Restore the behavior described above.

Record the functions that contain those edits in `/app/rca.json`, one entry each:

```json
{
  "causes": [
    {
      "file": "internal/askpass/ppid_darwin.go",
      "function": "enclosing_function_name"
    },
    {
      "file": "internal/askpass/ppid_darwin.go",
      "function": "Type.method_name"
    }
  ]
}
```

`file` is the path of the file relative to the repository root, written exactly as it
appears in the tree. A file inside a directory keeps its directory prefix: the example
above is `internal/askpass/ppid_darwin.go`, not `ppid_darwin.go`.

`function` is the function name. A class or receiver prefix, written `Type.name`, is
accepted anywhere and is required when two functions in the same file share a name: the
bare name cannot tell them apart. When an edit sits inside a function nested in another
function, either name is accepted. Name every function one of the undocumented edits is
in, and only those. Where you wrote the fix does not matter: if you restored the behavior
from a caller or from a helper of your own, name the function the edit is in rather than
the one you wrote. If you suspect a function but found no edit in it, leave it out.


Before you edit any code, write your research and your plan to /app/RESEARCH_AND_PLANNING.md. Cover what you learned about the existing code and the constraints that shape the change, then how you intend to carry it out and why, including how you will know it works. Be concrete - the files, names and decisions specific to this codebase, not generalities. Complete the document before you touch any code: it is the record of your up-front investigation and decisions, and it should not be rewritten to match whatever the implementation turns into afterwards. Once it is done, implement the plan.
