# typeagent-py: diagnosing 30 injected faults without a test suite

A round of maintenance left this project misbehaving in many unrelated places at once. The repository has received 30 separate undocumented edits, and what follows is everything users have reported from the outside, described only as what they did and what came back.

Asking a question of a saved conversation is the worst hit. When a batch of prepared search words is broadened before the question runs, a word that arrived with no alternatives attached keeps none, so an alias registered for it never reaches the question, while the words that already carried alternatives are the ones being reworked. Asking the similarity store kept inside a database file for the near matches of several strings at once now fails outright instead of handing back one result list per string, though its size bookkeeping after an empty batch is fine. Asking the shared helper for the numeric vector of a plain string fails as well, rather than returning a unit-length vector of the model's width, and searching messages by their text in the setup that keeps everything inside the running process raises instead of coming back with an empty result list when nothing matches.

Looking things up by what was said about them is wrong in several independent ways. After processing a conversation whose facts hold an entity with a name and a colour trait and an action with a verb phrase and a tag, asking for a property by its name together with its value finds nothing at all: the two appear to have gone in the other way round. The same question against a database file misses too — a property put there a moment earlier under a name and a value reports no hits when asked for by that name and value, and checks after removal look no different from never having kept it. Narrowing such a question to a span of the conversation is ignored as well: a value whose only occurrence lies outside the requested span still reports a hit rather than being filtered away. Feeding one extracted knowledge result — a single entity, a single action and a single topic — into the searchable term table still records three references, but the topic text afterwards resolves to nothing, while the entity name and the joined verb phrase each still resolve to one hit as before. And while matches pile up, anything that is not an exact hit is counted twice: one exact and one near hit on the same value report the near count as two instead of one, and two near hits on the same value report four, though the exact count and both score totals stay right.

Keeping work between sessions has its own trouble. Messages written into a database file and reopened in a fresh session come back in full, but the searchable text entries that should accompany them, one per chunk, are all gone: the count reads zero where three were expected. Loading a previously saved payload of text locations together with their vectors back into the database-backed text search store likewise leaves it empty — a size check straight afterwards still reads zero, and the underlying rows are absent. Fetching several kept items at once by their positions now refuses position zero: a request for items two and zero reports an out-of-range error, as does any batch containing the first item, even though fetching that first item on its own works and genuinely out-of-range or negative positions still report the error. Reading a kept numeric vector back by its position does not reproduce what was put there either: the number held is right, but the vector reported for a position is not the one recorded at it. Asking what was recorded at given instants confuses its two call shapes, so asking for entries at one instant does not come back with just the single entry recorded there, and asking for everything between two instants does not come back with the two entries lying in that window.

Getting material into the system in the first place suffers too. Turning a caption time marker into seconds is off whenever an hour field is present, coming out one second too long for each hour, while minute-and-second marks, bare fractional seconds and minutes-only marks all convert exactly. Pulling the name of whoever is talking off the front of a line of dialogue has stopped recognizing some of the shapes it used to: lines that give the name before a colon come back with nobody identified and the label still sitting in the text. Splitting a three-part person name whose middle word is a lower-case particle puts the pieces in the wrong slots, with the particle not carried onto the surname. Reading in a plain file of twenty-five speaker-labelled lines no longer settles cleanly: an extra round of work is attempted at the point where the kept message count has not advanced past where the previous round stopped, so the run does not finish with twenty-five messages held and one knowledge extraction started per message at the requested concurrency.

Assembling text has three problems of its own. Two short pieces whose joined length, separator included, exactly fills the permitted chunk length are no longer combined and come back as two chunks. Splitting a block of text into paragraphs when it begins and ends with blank lines leaves empty strings among the paragraphs instead of dropping them. Appending text to a message that already holds one chunk fails with an out-of-range error rather than extending that chunk in place.

Opening saved work misbehaves in two ways. Loading previously written-out conversation data into an object that already holds a message silently proceeds instead of refusing with a runtime error. Asking the service entry point to open a saved conversation while giving it neither of the two names it can be opened by no longer raises the argument error that names those two choices; it fails some other way first.

Preparing a reply for a person is affected at the end. Rolling a set of named traits up into grouped ones no longer folds the names to lower case, so a trait named with a capital letter is grouped under its original spelling and cannot be found by its lower-case name, while the values themselves are still lowered. Asking for the span that encloses a set of message positions gives the wrong end: a single position comes back with an end boundary attached where none should be, and a set of several positions no longer reports the highest of them as its end, though the lowest is still the start. Requesting the preamble that tells a model how far a conversation reaches in time returns nothing for a conversation whose messages carry times, and for a conversation with no times at all it no longer quietly returns nothing.

Reaching the model service is broken in four places. Wrapping a chat model for completion breaks when no retry policy is handed in at construction time: completing either a bare prompt string or a list of role-and-content sections raises instead of returning the model's text. Handing a literal API key to the key resolver no longer returns that key untouched — a plain key string is routed down the cloud-identity path instead. Fetching a credential while the cached one is still fresh does not return the cached one, and when a renewal does occur the credential is requested for the cloud management plane rather than for the AI service endpoint.

It worked before a set of undocumented edits to the source of typeagent-py. The repository has
no test suite to run: finding out what is wrong, and convincing yourself you have fixed
it, is part of the task.

Restore the behavior described above.

Record the functions that contain those edits in `/app/rca.json`, one entry each:

```json
{
  "causes": [
    {
      "file": "src/typeagent/aitools/embeddings.py",
      "function": "enclosing_function_name"
    }
  ]
}
```

`function` is the function name. A class prefix is ignored if you include one. When an
edit sits inside a function nested in another function, either name is accepted. Name
every function one of the undocumented edits is in, and only those. Where you wrote the
fix does not matter: if you restored the behavior from a caller or from a helper of your
own, name the function the edit is in rather than the one you wrote. If you suspect a
function but found no edit in it, leave it out.


Before you edit any code, write your research and your plan to /app/RESEARCH_AND_PLANNING.md. Cover what you learned about the existing code and the constraints that shape the change, then how you intend to carry it out and why, including how you will know it works. Be concrete - the files, names and decisions specific to this codebase, not generalities. Complete the document before you touch any code: it is the record of your up-front investigation and decisions, and it should not be rewritten to match whatever the implementation turns into afterwards. Once it is done, implement the plan.
