# Pendulum: repairing a date/time library without a test suite

I have been leaning on this library all over an application, and after picking up a recent checkout a great deal of everyday behaviour has gone wrong. The repository has received 20 separate undocumented edits. Nothing about the calendar changed and nothing in my own code changed: the same calls that used to give right answers now give wrong ones, and in several places a call that used to hand back a value now raises instead. Everything below is what I could pin down from the outside, set out by what I was doing when it went wrong.

Getting hold of a value from something outside my own program is the first thing that breaks. Anchoring a moment to a bare numeric offset rather than a named region — 6, 0, 5, -5, 9.5 — fails outright with a lookup error, and so does anything that needs one indirectly: reading text carrying an explicit offset, adapting an offset-bearing value handed over by another library, restoring a pickled value built that way, and comparing two such offsets for equality. Named regions such as `America/Toronto` or `Europe/Paris` are unaffected. Where one can be built at all, a negative offset reports a malformed name, minus five or minus five and a half no longer coming out in the `-05:30` / `-05:00` style, while positive offsets still look right. Anything that needs the host's own settings is broken as well: asking for the current moment, jumping to a given moment, shifting by a relative amount and pinning the clock in place all fail rather than returning a value on this box, which is not Windows. And when the host's region has to be discovered from the usual layouts — a symbolic link whose target path spells the region out, and a directory sitting where the plain text file usually is — the region that comes back is mangled rather than `Europe/Paris`.

Reading values out of text is the worst-hit thing I do. Almost every full date-and-clock string comes back damaged: the standard machine-readable spellings with or without separators, the offset-carrying variants, the extended fractional-second and nanosecond ones, and plain `YYYY-MM-DD HH:MM:SS` all give back something that has dropped the clock reading and the offset. Elapsed-span strings (`P2Y3M4DT5H6M7S`, `P2W`, the fractional and comma variants) likewise come back in a shape that does not expose the fields I expect, and text pairing a moment with a span is broken along with them; a plain date on its own still reads correctly. Camera-style text with colons in the date part (`2016:12:26 15:45:28`) is now rejected outright instead of yielding 26 December 2016 at 15:45:28. A year plus a day-of-year number resolves to a calendar date well off the right one, both in the `2017-079` spelling and when a day-of-year token appears in a pattern I supply. Week-numbered dates naming week 53 are refused even for years that genuinely have a 53rd week (`2009-W53-7`, `2015W53`), while week 53 of a year with no such week (`2017W53`) is accepted instead of being turned away as invalid. When I supply the pattern myself, any pattern holding a written-out month or weekday no longer matches at all — full and abbreviated month names, full, abbreviated and minimal weekday names, in English and in other languages — so the read errors out; a pattern built from a year and a quarter number leaves the quarter unhonoured; and a numeric weekday token lands on the wrong date.

Handing a value back out as text is wrong in as many ways. For a moment in a region behind UTC the offset written out has its minutes mangled, and that corrupted tail shows up in every canned string produced — the feed, mail-header and web-standard styles alike, and the language-aware rendering too — for somewhere like `America/Guayaquil` or a machine five hours behind UTC, while regions ahead of UTC (`+02:00`, `+01:00`) still come out right. Interpolating a date, a clock reading or a full date-and-clock value into a string with no specification gives the text it always gave, but supplying one is broken both ways round: this library's own token spelling comes back as the tokens themselves rather than the rendered value, and the percent-sign placeholder style no longer produces its result either, the two looking to have swapped places. Asking for a gap of about a year in words no longer mentions years, the phrasing picking a different unit and a different number. Setting the active language to an identifier that carries a region — written with a dash or an underscore, in any mixture of upper and lower case — now fails rather than being quietly accepted, and rendering a token while asking for a region-qualified variant such as British English yields another variant's values, the language-specific day-of-week number and its ordinal spelling coming out in the plain-English form.

Working a second value out of one I already hold goes wrong across the calendar. Stepping back to the nearest earlier occurrence of a weekday returns the wrong date — with a weekday named, with none named (the plain "a week earlier" behaviour), and in the variant meant to keep the clock reading — so the start of the week worked out from a mid-week date is wrong in consequence, including across a year boundary. Anything anchored at the beginning of a year is off too: the first day of a year, the first Wednesday or Friday of one, and the nth given weekday of one (2nd Monday, 3rd Wednesday, 7th Thursday, 1st Monday) all land somewhere they should not, as though the search began at the wrong point in the year. Asking a clock reading for a copy carrying a new hour, minute, second and microsecond hands back one whose minute, second and microsecond are updated as asked but whose hour is left untouched. Moving a moment's wall-clock reading to an instant that falls inside a spring-forward gap (2:30 on the transition morning in `Europe/Paris`) lands on the wrong hour, where it should come out at 3:30 with the minutes and seconds kept.

Bad input I expect to be refused now slips through in two places. Asking for an earlier occurrence of a weekday number outside the valid range no longer raises at all, and configuring which weekday the week finishes on swallows obviously invalid weekday numbers such as -1 and 11 without complaint. Both used to turn them down.

It worked before a set of undocumented edits to the source of pendulum. The repository has
no test suite to run: finding out what is wrong, and convincing yourself you have fixed
it, is part of the task.

Restore the behavior described above.

Record the functions that contain those edits in `/app/rca.json`, one entry each:

```json
{
  "causes": [
    {
      "file": "src/pendulum/date.py",
      "function": "enclosing_function_name"
    }
  ]
}
```

`function` is the function name. A class prefix is ignored if you include one. When an
edit sits inside a function nested in another function, either name is accepted. Name
every function one of the undocumented edits is in, and only those. Where you wrote the
fix does not matter: if you restored the behavior from a caller or from a helper of your
own, name the function the edit is in rather than the one you wrote. If you suspect a
function but found no edit in it, leave it out.


Before you edit any code, write your research and your plan to /app/RESEARCH_AND_PLANNING.md. Cover what you learned about the existing code and the constraints that shape the change, then how you intend to carry it out and why, including how you will know it works. Be concrete - the files, names and decisions specific to this codebase, not generalities. Complete the document before you touch any code: it is the record of your up-front investigation and decisions, and it should not be rewritten to match whatever the implementation turns into afterwards. Once it is done, implement the plan.
