The Terraform for our Pressline multi-site WordPress production stack in `/workspace/infra` has grown into one flat root module: everything is declared at the top level, the per-AZ resources are `count`-indexed by list position, and names, settings and tags are hard-coded all over the files. Split it into five local modules (network, security, data, compute and operations) without touching the running infrastructure: against the current state, the plan has to come out as nothing but moves.

There is no AWS access from this machine. `terraform init` works offline from the local provider mirror, `terraform.tfstate` is a copy of the production state, and `scripts/ci-plan.sh` runs what CI runs: a `terraform plan -refresh=false` against the state followed by the guardrail policies in `policies/`.

## Detailed Constraints

**How CI judges the change.** CI takes the repository alone and plans it with `terraform plan -refresh=false` against its own copy of the production state. Local `terraform state` commands and edits to `terraform.tfstate` never reach it, so the whole migration has to be expressed in the configuration. That plan must:
- still manage every resource that is in the state today, and
- contain no create, update, replace, destroy or forget: only resources moving to new addresses.

The guardrail policies in `policies/` must pass on that plan, and `providers.tf` and everything in `policies/` stay exactly as they are, byte for byte.

**Layout.**
- The root module calls `module "network"`, `module "security"`, `module "data"`, `module "compute"` and `module "operations"`, with sources `./modules/network`, `./modules/security`, `./modules/data`, `./modules/compute` and `./modules/operations` and one instance each, calls no other module and declares no resources of its own.
- Which module owns what (every instance of the resources described, wherever they are declared today):
  - network: the VPC and internet gateway; all public, private and database subnets; the NAT gateways and Elastic IPs; every route table, route and route table association; the S3 gateway endpoint and its route table associations; the three Systems Manager interface endpoints; and the endpoint security group;
  - security: the load balancer, WordPress server and database security groups, together with every ingress and egress rule attached to those groups or the endpoint security group;
  - data: the KMS key and alias; every site's media bucket and all bucket settings, jobs queue, lock table and configuration parameter; both database secrets and their versions; and the MySQL instance, subnet group and parameter group;
  - compute: the application load balancer, every site target group and listener rule, the listener, launch template and auto scaling group, plus the WordPress instance role, instance profile, customer policy and both policy attachments;
  - operations: the VPC flow log with its log group, role and inline policy; the shared WordPress and per-site log groups; every site's alert topic and healthy-host alarm; and the fleet and database alarms.
- Each of these modules declares the resources it owns itself and calls no other module.
- Modules get each other's IDs and ARNs through module outputs and variables. Never paste an ID, ARN, IP address or DNS name of an existing resource, or any part of one (such as an ARN suffix), into the `.tf` files or templates. The configuration reads files only through literal paths inside its own module (such as `"${path.module}/templates/..."`; in a child module a path starts with `${path.module}/`, because Terraform resolves any other relative path from the root directory, not from the module): no computed paths, no `terraform_remote_state` data sources, and never the state or a plan file.

**Keys.**
- Everything that exists once per availability zone today is a `for_each` resource keyed by the AZ name (for example `["us-east-1a"]`), including each instance of a list that also holds things that belong to no single availability zone (the S3 endpoint's associations with the private route tables are per AZ; its association with the public route table is not).
- Everything that exists once per WordPress site today is a `for_each` resource keyed by the site key (for example `["journal"]`), including each instance of a list that also holds things that belong to no single WordPress site.
- The listener's default action forwards to the site with the lowest `routing_priority`; ties are broken by the lexicographically smallest site key.
- Don't use `count` anywhere. Other repeated resources use `for_each` with string keys that are not numbers (a name such as `["assets"]`, never `["0"]`).
- Each existing availability zone's entry in `availability_zones` is the only source of its values: changing an entry changes, for that availability zone alone, exactly the settings the entry provides, and changes nothing else.
- Adding an availability zone to `availability_zones` must plan only the creation of that availability zone's resources, each configured exactly like its counterparts in the existing availability zones apart from the availability zone itself and the values its entry in `availability_zones` gives it (same settings, names and tags), and removing one only the destruction of that availability zone's resources. Beyond that, the only change either may plan is an in-place update of the settings that collect something from every availability zone today (wherever a setting holds a part of every availability zone: their names, IDs, ARNs, subnets or CIDRs, say, in a list, a policy document or an environment value): each of them must take in, or drop, exactly that availability zone's part where it belongs, in the same form as today (today's parts keep their order; where a new part goes is up to you), and change nothing else. No other resource may be created, updated, replaced or destroyed.
- Each existing WordPress site's entry in `sites` is the only source of its values: changing an entry changes, for that WordPress site alone, exactly the settings the entry provides, and changes nothing else.
- Adding a WordPress site to `sites` must plan only the creation of that WordPress site's resources, each configured exactly like its counterparts in the existing WordPress sites apart from the WordPress site itself and the values its entry in `sites` gives it (same settings, names and tags), and removing one only the destruction of that WordPress site's resources. Beyond that, the only change either may plan is an in-place update of the settings that collect something from every WordPress site today (wherever a setting holds a part of every WordPress site: their names, IDs, ARNs, subnets or CIDRs, say, in a list, a policy document or an environment value): each of them must take in, or drop, exactly that WordPress site's part where it belongs, in the same form as today (today's parts keep their order; where a new part goes is up to you), and change nothing else. No other resource may be created, updated, replaced or destroyed.

**Root variables.** Declare these in the root module, each defaulting to today's value:
- `project` (`string`, `"pressline"`): every whole-word occurrence of `pressline` in a resource name, identifier or tag value today, and the `APP_PROJECT` value in the launch template's user data, comes from it (whole word: not part of a longer run of letters and digits, so `pressline-api`, `pressline_key` and `/pressline/` count, while a longer word that merely contains `pressline` stays as it is), and so does every mention of those names elsewhere in the configuration (for example a resource name inside a policy); inside documents such as policies, container definitions and environment values, every whole-word occurrence of `pressline` that stands for it comes from it too; the project word joined directly to the environment in the MySQL database name follows it too, as does the project word in every CloudWatch alarm description.
- `environment` (`string`, `"prod"`): every whole-word occurrence of `prod` in a resource name, identifier or tag value today, and the `APP_ENV` value in the launch template's user data, comes from it (whole word: not part of a longer run of letters and digits, so `prod-api`, `prod_key` and `/prod/` count, while a longer word that merely contains `prod` stays as it is), and so does every mention of those names elsewhere in the configuration (for example a resource name inside a policy); inside documents such as policies, container definitions and environment values, every whole-word occurrence of `prod` that stands for it comes from it too; the environment word joined directly to the project in the MySQL database name follows it too, as does the environment word in every CloudWatch alarm description.
- `vpc_cidr` (`string`, `"10.72.0.0/16"`): the VPC's CIDR block.
- `availability_zones`: `map(object({ public_cidr = string, private_cidr = string, database_cidr = string }))`, keyed by AZ name, defaulting to today's three AZs and their public, private and database subnet CIDRs. It is the only source of which AZs exist and of every subnet CIDR.
- `sites`: `map(object({ hostname = string, bucket_suffix = string, routing_priority = number, cache_ttl = number, media_expiration_days = number, alarm_threshold = number }))`, keyed by site key, defaulting to today's three sites and each site's hostname, bucket suffix, routing priority, cache TTL, media expiration, and healthy-host threshold. It is the only source of which sites exist and of those per-site values; the project and environment words embedded in a hostname still follow their corresponding root variables.
- `tags` (`map(string)`, `{ Owner = "web-platform", CostCenter = "cc-2718", ManagedBy = "terraform", Compliance = "internal" }`): the shared tags (`Owner`, `CostCenter`, `ManagedBy` and `Compliance`) that tagged resources carry today. Wherever the configuration writes them out today, in any form, they come from this variable, so that a different map (other keys, other values) reaches every one of those places; a resource's other tags stay as they are, and resources that are untagged today stay untagged.
- `app_ami_id` (`string`, `"ami-0b5eea76982371e91"`): the WordPress launch template's AMI.
- `app_instance_type` (`string`, `"t3.small"`): the WordPress launch template's instance type.
- `app_min_size` (`number`, `2`): the WordPress auto scaling group's minimum size.
- `app_max_size` (`number`, `6`): the WordPress auto scaling group's maximum size.
- `app_desired_capacity` (`number`, `3`): the WordPress auto scaling group's desired capacity.
- `db_instance_class` (`string`, `"db.t3.small"`): the MySQL instance class.
- `db_allocated_storage` (`number`, `40`): the MySQL instance's allocated storage in GiB.
- `db_max_allocated_storage` (`number`, `200`): the MySQL instance's autoscaling storage ceiling in GiB.
- `db_backup_retention_days` (`number`, `14`): the MySQL instance's backup retention in days.
- `log_retention_days` (`number`, `30`): the retention in days of every CloudWatch log group.
- `queue_message_retention_seconds` (`number`, `345600`): the message retention in seconds of every site's jobs queue.
- `alarm_period_seconds` (`number`, `60`): the period in seconds of every CloudWatch metric alarm.
- Changing `vpc_cidr`, `app_ami_id`, `app_instance_type`, `app_min_size`, `app_max_size`, `app_desired_capacity`, `db_instance_class`, `db_allocated_storage`, `db_max_allocated_storage`, `db_backup_retention_days`, `log_retention_days`, `queue_message_retention_seconds` and `alarm_period_seconds` changes only what each one's line above says it controls: every other setting keeps today's value, including a setting that merely has the same value today.

**Root outputs.** Keep `vpc_id`, `load_balancer_dns_name`, `database_endpoint` and `wordpress_role_arn` with their current values. `public_subnet_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_subnet.public_wordpress`. `private_subnet_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_subnet.private_wordpress`. `database_subnet_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_subnet.database_wordpress`. `nat_public_ips` becomes a map from the AZ name to the `public_ip` of that availability zone's `aws_eip.nat`. `site_target_group_arns` becomes a map from the site key to the `arn` of that WordPress site's `aws_lb_target_group.wordpress_site`. `site_media_bucket_names` becomes a map from the site key to the `bucket` of that WordPress site's `aws_s3_bucket.media`. `site_queue_urls` becomes a map from the site key to the `url` of that WordPress site's `aws_sqs_queue.site_jobs`. `site_alert_topic_arns` becomes a map from the site key to the `arn` of that WordPress site's `aws_sns_topic.site_alerts`. Each output passes through outputs of the module that owns the resource (network for `vpc_id`, `public_subnet_ids`, `private_subnet_ids`, `database_subnet_ids` and `nat_public_ips`; data for `site_media_bucket_names`, `site_queue_urls` and `database_endpoint`; compute for `load_balancer_dns_name`, `site_target_group_arns` and `wordpress_role_arn`; operations for `site_alert_topic_arns`): the root output is a plain reference to an output of that module, and that module output is a plain reference to the resource. A plain reference is a reference such as `module.network.<output>` or `<resource type>.<name>.<attribute>`, a local that holds one, or a `for` expression that only re-keys one (`{ for k, v in <reference> : k => v.id }`) or iterates a plain reference and looks each key up in one (`{ for k, v in var.<map> : k => <reference>[k].id }`); no literals, function calls, conditionals or string templates anywhere along the way.

**Not allowed anywhere in the configuration:** `ignore_changes`, `prevent_destroy` and `replace_triggered_by`, `removed` and `import` blocks, provisioners, `external` data sources, backend or cloud blocks, provider blocks other than the one in `providers.tf`, override files and `.tf.json` files.
