The Terraform for our on-demand GitLab runner production stack in `/workspace/infra` has grown into one flat root module: everything is declared at the top level, the per-AZ resources are `count`-indexed by list position, and names, settings and tags are hard-coded all over the files. Split it into four local modules (network, runners, identity and control) without touching the running infrastructure: against the current state, the plan has to come out as nothing but moves.

There is no AWS access from this machine. `terraform init` works offline from the local provider mirror, `terraform.tfstate` is a copy of the production state, and `scripts/ci-plan.sh` runs what CI runs: a `terraform plan -refresh=false` against the state followed by the guardrail policies in `policies/`.

## Detailed Constraints

**How CI judges the change.** CI takes the repository alone and plans it with `terraform plan -refresh=false` against its own copy of the production state. Local `terraform state` commands and edits to `terraform.tfstate` never reach it, so the whole migration has to be expressed in the configuration. That plan must:
- still manage every resource that is in the state today, and
- contain no create, update, replace, destroy or forget: only resources moving to new addresses.

The guardrail policies in `policies/` must pass on that plan, and `providers.tf` and everything in `policies/` stay exactly as they are, byte for byte.

**Layout.**
- The root module calls `module "network"`, `module "runners"`, `module "identity"` and `module "control"`, with sources `./modules/network`, `./modules/runners`, `./modules/identity` and `./modules/control` and one instance each, calls no other module and declares no resources of its own.
- Which module owns what (every instance of the resources described, wherever they are declared today):
  - network: the VPC and internet gateway, public and private subnets, Elastic IPs and NAT gateways, route tables, routes and route table associations, the Lambda control-plane security group and its egress, the per-zone, zone-catalog, private-subnet-catalog and selected control-subnet parameters, and the S3 gateway endpoint with all of its route table associations;
  - runners: the runner-data KMS key and alias, the artifacts bucket and all of its settings resources, the runner security group and its rules, the shared bootstrap launch template, and each pool's job and dead-letter queues, queue policy, alert topic and subscription, image repository, pool parameter, runner log group, runner launch template and backlog alarm;
  - identity: the runner and Lambda IAM roles and policies, both policy attachments, and the runner instance profile;
  - control: the per-pool up and down Lambda functions and log groups, EventBridge rules, targets and Lambda permissions, the REST API with its resources, methods, integrations, deployment and Lambda permissions, the pool-catalog and primary-pool parameters, and the Lambda error alarms.
- Each of these modules declares the resources it owns itself and calls no other module.
- Modules get each other's IDs and ARNs through module outputs and variables. Never paste an ID, ARN, IP address or DNS name of an existing resource, or any part of one (such as an ARN suffix), into the `.tf` files or templates. The configuration reads files only through literal paths inside its own module (such as `"${path.module}/templates/..."`; in a child module a path starts with `${path.module}/`, because Terraform resolves any other relative path from the root directory, not from the module): no computed paths, no `terraform_remote_state` data sources, and never the state or a plan file.

**Keys.**
- Everything that exists once per availability zone today is a `for_each` resource keyed by the AZ name (for example `["us-east-1a"]`), including each instance of a list that also holds things that belong to no single availability zone (its associations with the private route tables; its association with the public route table is not per AZ).
- The control-subnet parameter always contains the private-subnet ID for the entry with the lowest `control_priority`; ties choose the lexicographically first AZ name, so removing or reprioritizing the current choice selects the next eligible entry.
- Everything that exists once per runner pool today is a `for_each` resource keyed by the pool name (for example `["build"]`), including each instance of a list that also holds things that belong to no single runner pool.
- Preserve the existing relative order wherever a setting collects all pools, while accepting any new pool name. The primary-pool parameter always contains the name of the selected pool's pool parameter, choosing the lowest `priority` and breaking ties by the lexicographically first pool name; removing or reprioritizing the current choice selects the next eligible pool.
- Don't use `count` anywhere. Other repeated resources use `for_each` with string keys that are not numbers (a name such as `["assets"]`, never `["0"]`).
- Each existing availability zone's entry in `availability_zones` is the only source of its values: changing an entry changes, for that availability zone alone, exactly the settings the entry provides, and changes nothing else.
- Adding an availability zone to `availability_zones` must plan only the creation of that availability zone's resources, each configured exactly like its counterparts in the existing availability zones apart from the availability zone itself and the values its entry in `availability_zones` gives it (same settings, names and tags), and removing one only the destruction of that availability zone's resources. Beyond that, the only change either may plan is an in-place update of the settings that collect something from every availability zone today (wherever a setting holds a part of every availability zone: their names, IDs, ARNs, subnets or CIDRs, say, in a list, a policy document or an environment value): each of them must take in, or drop, exactly that availability zone's part where it belongs, in the same form as today (today's parts keep their order, except inside an IAM policy document, where the order of statements, actions and resources means nothing to AWS; where a new part goes is up to you), and change nothing else. No other resource may be created, updated, replaced or destroyed.
- Each existing runner pool's entry in `runner_pools` is the only source of its values: changing an entry changes, for that runner pool alone, exactly the settings the entry provides, and changes nothing else.
- Adding a runner pool to `runner_pools` must plan only the creation of that runner pool's resources, each configured exactly like its counterparts in the existing runner pools apart from the runner pool itself and the values its entry in `runner_pools` gives it (same settings, names and tags), and removing one only the destruction of that runner pool's resources. Beyond that, the only change either may plan is an in-place update of the settings that collect something from every runner pool today (wherever a setting holds a part of every runner pool: their names, IDs, ARNs, subnets or CIDRs, say, in a list, a policy document or an environment value): each of them must take in, or drop, exactly that runner pool's part where it belongs, in the same form as today (today's parts keep their order, except inside an IAM policy document, where the order of statements, actions and resources means nothing to AWS; where a new part goes is up to you), and change nothing else. No other resource may be created, updated, replaced or destroyed.

**Root variables.** Declare these in the root module, each defaulting to today's value:
- `project` (`string`, `"gitlabrunner"`): every whole-word occurrence of `gitlabrunner` in a resource name, identifier or tag value today, and the shared bootstrap launch template's user data writes `PROJECT=<project>`, comes from it (whole word: not part of a longer run of letters and digits, so `gitlabrunner-api`, `gitlabrunner_key` and `/gitlabrunner/` count, while a longer word that merely contains `gitlabrunner` stays as it is), and so does every mention of those names elsewhere in the configuration (for example a resource name inside a policy); inside documents such as policies, container definitions and environment values, every whole-word occurrence of `gitlabrunner` that stands for it comes from it too.
- `environment` (`string`, `"prod"`): every whole-word occurrence of `prod` in a resource name, identifier or tag value today, and the shared bootstrap launch template's user data writes `APP_ENV=<environment>`, comes from it (whole word: not part of a longer run of letters and digits, so `prod-api`, `prod_key` and `/prod/` count, while a longer word that merely contains `prod` stays as it is), and so does every mention of those names elsewhere in the configuration (for example a resource name inside a policy); inside documents such as policies, container definitions and environment values, every whole-word occurrence of `prod` that stands for it comes from it too.
- `vpc_cidr` (`string`, `"10.72.0.0/16"`): the VPC CIDR block and the VPC-range entry in the runner SSH rule.
- `availability_zones`: `map(object({ public_cidr = string, private_cidr = string, control_priority = number }))`, keyed by AZ name, defaulting to today's three AZs and their public and private subnet CIDRs and control priority. It is the only source of AZ names and those per-AZ settings.
- `runner_pools`: `map(object({ visibility_timeout = number, memory_size = number, schedule = string, instance_type = string, lambda_timeout = number, backlog_threshold = number, alarm_period = number, priority = number }))`, keyed by pool name, defaulting to today's three pools and each pool's job-queue visibility timeout, Lambda memory size, reconciliation schedule, runner instance type, Lambda timeout, alarm threshold, alarm period and selection priority. It is the only source of pool names and those per-pool settings.
- `tags` (`map(string)`, `{ Owner = "developer-platform", CostCenter = "cc-7310", ManagedBy = "terraform" }`): the shared tags (`Owner`, `CostCenter` and `ManagedBy`) that tagged resources carry today. Wherever the configuration writes them out today, in any form, they come from this variable, so that a different map (other keys, other values) reaches every one of those places; a resource's other tags stay as they are, and resources that are untagged today stay untagged.
- `trusted_cidr_blocks` (`list(string)`, `["203.0.113.0/24"]`): the non-VPC trusted networks in the runner SSH rule.
- `log_retention_days` (`number`, `30`): the retention of every CloudWatch log group.
- `kms_deletion_window_days` (`number`, `30`): the deletion window of the runner-data KMS key.
- `job_queue_retention_seconds` (`number`, `345600`): the message retention of every runner-pool job queue.
- `dead_letter_retention_seconds` (`number`, `1209600`): the message retention of every runner-pool dead-letter queue.
- `runner_ami_id` (`string`, `"ami-0c02fb55956c7d316"`): the machine image of every runner launch template, including the shared bootstrap template.
- Changing `vpc_cidr`, `trusted_cidr_blocks`, `log_retention_days`, `kms_deletion_window_days`, `job_queue_retention_seconds`, `dead_letter_retention_seconds` and `runner_ami_id` changes only what each one's line above says it controls: every other setting keeps today's value, including a setting that merely has the same value today.

**Root outputs.** Keep `vpc_id`, `api_execution_arn`, `artifact_bucket_name`, `runner_instance_profile_name`, `control_subnet_parameter_name` and `primary_pool_parameter_name` with their current values. `private_subnet_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_subnet.private`. `public_subnet_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_subnet.public`. `job_queue_urls` becomes a map from the pool name to the `url` of that runner pool's `aws_sqs_queue.jobs`. `runner_repository_urls` becomes a map from the pool name to the `repository_url` of that runner pool's `aws_ecr_repository.runner`. `up_function_arns` becomes a map from the pool name to the `arn` of that runner pool's `aws_lambda_function.up`. `private_route_table_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_route_table.private`. `nat_gateway_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_nat_gateway.main`. `zone_parameter_names` becomes a map from the AZ name to the `name` of that availability zone's `aws_ssm_parameter.zone`. `job_queue_arns` becomes a map from the pool name to the `arn` of that runner pool's `aws_sqs_queue.jobs`. `dead_letter_queue_arns` becomes a map from the pool name to the `arn` of that runner pool's `aws_sqs_queue.dead_letter`. `pool_parameter_names` becomes a map from the pool name to the `name` of that runner pool's `aws_ssm_parameter.pool`. `runner_launch_template_ids` becomes a map from the pool name to the `id` of that runner pool's `aws_launch_template.runner`. `backlog_alarm_names` becomes a map from the pool name to the `alarm_name` of that runner pool's `aws_cloudwatch_metric_alarm.backlog`. `down_function_arns` becomes a map from the pool name to the `arn` of that runner pool's `aws_lambda_function.down`. `lambda_error_alarm_names` becomes a map from the pool name to the `alarm_name` of that runner pool's `aws_cloudwatch_metric_alarm.lambda_errors`. Each output passes through outputs of the module that owns the resource (network for `vpc_id`, `private_subnet_ids`, `public_subnet_ids`, `private_route_table_ids`, `nat_gateway_ids`, `zone_parameter_names` and `control_subnet_parameter_name`; runners for `job_queue_urls`, `runner_repository_urls`, `artifact_bucket_name`, `job_queue_arns`, `dead_letter_queue_arns`, `pool_parameter_names`, `runner_launch_template_ids` and `backlog_alarm_names`; identity for `runner_instance_profile_name`; control for `up_function_arns`, `api_execution_arn`, `down_function_arns`, `lambda_error_alarm_names` and `primary_pool_parameter_name`): the root output is a plain reference to an output of that module, and that module output is a plain reference to the resource. A plain reference is a reference such as `module.network.<output>` or `<resource type>.<name>.<attribute>`, a local that holds one, or a `for` expression that only re-keys one (`{ for k, v in <reference> : k => v.id }`) or iterates a plain reference and looks each key up in one (`{ for k, v in var.<map> : k => <reference>[k].id }`); no literals, function calls, conditionals or string templates anywhere along the way.

**Not allowed anywhere in the configuration:** `ignore_changes`, `prevent_destroy` and `replace_triggered_by`, `removed` and `import` blocks, provisioners, `external` data sources, backend or cloud blocks, provider blocks other than the one in `providers.tf`, override files and `.tf.json` files.
