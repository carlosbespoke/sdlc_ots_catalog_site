The Terraform for our Matinale Tech ECS blue/green production stack in `/workspace/infra` has grown into one flat root module: everything is declared at the top level, the per-network-cell resources are `count`-indexed by list position, and names, settings and tags are hard-coded all over the files. Split it into four local modules (network, identity, application and operations) without touching the running infrastructure: against the current state, the plan has to come out as nothing but moves.

There is no AWS access from this machine. `terraform init` works offline from the local provider mirror, `terraform.tfstate` is a copy of the production state, and `scripts/ci-plan.sh` runs what CI runs: a `terraform plan -refresh=false` against the state followed by the guardrail policies in `policies/`.

## Detailed Constraints

**How CI judges the change.** CI takes the repository alone and plans it with `terraform plan -refresh=false` against its own copy of the production state. Local `terraform state` commands and edits to `terraform.tfstate` never reach it, so the whole migration has to be expressed in the configuration. That plan must:
- still manage every resource that is in the state today, and
- contain no create, update, replace, destroy or forget: only resources moving to new addresses.

The guardrail policies in `policies/` must pass on that plan, and `providers.tf` and everything in `policies/` stay exactly as they are, byte for byte.

**Layout.**
- The root module calls `module "network"`, `module "identity"`, `module "application"` and `module "operations"`, with sources `./modules/network`, `./modules/identity`, `./modules/application` and `./modules/operations` and one instance each, calls no other module and declares no resources of its own.
- Which module owns what (every instance of the resources described, wherever they are declared today):
  - network: the VPC, internet gateway, public and private subnets, Elastic IPs and NAT gateways, route tables, routes and route table associations, and the S3 gateway endpoint with all of its route table associations;
  - identity: the load-balancer and ECS security groups with all of their rules, and the legacy ECS instance and service IAM roles, instance profile and managed-policy attachments;
  - application: the ECS cluster, ECR repository, workload task definitions and log groups, the task-execution IAM role and inline policy, and the application load balancer, listener and workload target groups;
  - operations: the alerts topic, workload and NAT metric alarms, deployment queues and their policies, deployment and network SSM parameters, and the VPC flow log with its log group, IAM role and inline policy.
- Each of these modules declares the resources it owns itself and calls no other module.
- Modules get each other's IDs and ARNs through module outputs and variables. Never paste an ID, ARN, IP address or DNS name of an existing resource, or any part of one (such as an ARN suffix), into the `.tf` files or templates. The configuration reads files only through literal paths inside its own module (such as `"${path.module}/templates/..."`; in a child module a path starts with `${path.module}/`, because Terraform resolves any other relative path from the root directory, not from the module): no computed paths, no `terraform_remote_state` data sources, and never the state or a plan file.

**Keys.**
- Everything that exists once per network cell today is a `for_each` resource keyed by the stable cell name (for example `["alpha"]`), including each instance of a list that also holds things that belong to no single network cell (the S3 endpoint's associations with the private route tables are per network cell; its association with the public route table belongs to no single cell).
- Keep the existing cells in their commissioned order wherever a setting collects them; a new cell follows those existing entries.
- Everything that exists once per deployment slot today is a `for_each` resource keyed by the slot name (for example `["production"]`), including each instance of a list that also holds things that belong to no single deployment slot.
- Keep the existing slots in their historical order wherever a setting collects them; a new slot follows those existing entries.
- Don't use `count` anywhere. Other repeated resources use `for_each` with string keys that are not numbers (a name such as `["assets"]`, never `["0"]`).
- Each existing network cell's entry in `network_cells` is the only source of its values: changing an entry changes, for that network cell alone, exactly the settings the entry provides, and changes nothing else.
- Adding a network cell to `network_cells` must plan only the creation of that network cell's resources, each configured exactly like its counterparts in the existing network cells apart from the network cell itself and the values its entry in `network_cells` gives it (same settings, names and tags), and removing one only the destruction of that network cell's resources. Beyond that, the only change either may plan is an in-place update of the settings that collect something from every network cell today (wherever a setting holds a part of every network cell: their names, IDs, ARNs, subnets or CIDRs, say, in a list, a policy document or an environment value): each of them must take in, or drop, exactly that network cell's part where it belongs, in the same form as today (today's parts keep their order, except inside an IAM policy document, where the order of statements, actions and resources means nothing to AWS; where a new part goes is up to you), and change nothing else. No other resource may be created, updated, replaced or destroyed.
- Each existing deployment slot's entry in `workloads` is the only source of its values: changing an entry changes, for that deployment slot alone, exactly the settings the entry provides, and changes nothing else.
- Adding a deployment slot to `workloads` must plan only the creation of that deployment slot's resources, each configured exactly like its counterparts in the existing deployment slots apart from the deployment slot itself and the values its entry in `workloads` gives it (same settings, names and tags), and removing one only the destruction of that deployment slot's resources. Beyond that, the only change either may plan is an in-place update of the settings that collect something from every deployment slot today (wherever a setting holds a part of every deployment slot: their names, IDs, ARNs, subnets or CIDRs, say, in a list, a policy document or an environment value): each of them must take in, or drop, exactly that deployment slot's part where it belongs, in the same form as today (today's parts keep their order, except inside an IAM policy document, where the order of statements, actions and resources means nothing to AWS; where a new part goes is up to you), and change nothing else. No other resource may be created, updated, replaced or destroyed.

**Root variables.** Declare these in the root module, each defaulting to today's value:
- `project` (`string`, `"matinale"`): every whole-word occurrence of `matinale` in a resource name, identifier or tag value today comes from it (whole word: not part of a longer run of letters and digits, so `matinale-api`, `matinale_key` and `/matinale/` count, while a longer word that merely contains `matinale` stays as it is), and so does every mention of those names elsewhere in the configuration (for example a resource name inside a policy); inside documents such as policies, container definitions and environment values, every whole-word occurrence of `matinale` that stands for it comes from it too; the lower-case project token used by every resource name and identifier, every tag value that contains it, and every lower-case whole-word mention of those names in configured documents. The existing title-cased IAM policy Sid labels remain fixed audit identifiers.
- `environment` (`string`, `"prod"`): every whole-word occurrence of `prod` in a resource name, identifier or tag value today comes from it (whole word: not part of a longer run of letters and digits, so `prod-api`, `prod_key` and `/prod/` count, while a longer word that merely contains `prod` stays as it is), and so does every mention of those names elsewhere in the configuration (for example a resource name inside a policy); inside documents such as policies, container definitions and environment values, every whole-word occurrence of `prod` that stands for it comes from it too; the lower-case environment token used by every resource name and identifier, every tag value that contains it, and every lower-case whole-word mention of those names in configured documents. The existing title-cased IAM policy Sid labels remain fixed audit identifiers.
- `vpc_cidr` (`string`, `"10.24.0.0/16"`): the VPC address range and the load balancer security-group egress rule's destination range; subnet CIDRs remain controlled only by the network-cell map.
- `network_cells`: `map(object({ availability_zone = string, public_cidr = string, private_cidr = string }))`, keyed by stable cell name, defaulting to today's three cells and each cell's availability zone, public subnet CIDR and private subnet CIDR. It is the only source of cell names, availability zones and subnet CIDRs.
- `workloads`: `map(object({ latency_threshold = number, unhealthy_host_limit = number, queue_visibility_timeout_seconds = number }))`, keyed by deployment slot name, defaulting to today's test, production and canary slots and their latency threshold, unhealthy-host limit and queue visibility timeout. It is the only source of slot names and those per-slot values.
- `tags` (`map(string)`, `{ Owner = "platform-team", CostCenter = "mt-2017", ManagedBy = "terraform", Source = "sogilis-matinale-tech" }`): the shared tags (`Owner`, `CostCenter`, `ManagedBy` and `Source`) that tagged resources carry today. Wherever the configuration writes them out today, in any form, they come from this variable, so that a different map (other keys, other values) reaches every one of those places; a resource's other tags stay as they are, and resources that are untagged today stay untagged.
- `image_version` (`string`, `"1"`): the container image version in every workload task definition.
- `task_cpu` (`number`, `256`): the CPU configured both on every ECS task definition and in every task's container definition.
- `task_memory` (`number`, `512`): the memory configured both on every ECS task definition and in every task's container definition.
- `log_retention_days` (`number`, `30`): the retention period of every CloudWatch log group.
- `workload_alarm_period` (`number`, `60`): the metric period of every per-workload load-balancer alarm.
- `queue_retention_seconds` (`number`, `345600`): the message retention period of every deployment queue.
- `target_deregistration_delay` (`number`, `30`): the deregistration delay of every workload target group.
- Changing `vpc_cidr`, `image_version`, `task_cpu`, `task_memory`, `log_retention_days`, `workload_alarm_period`, `queue_retention_seconds` and `target_deregistration_delay` changes only what each one's line above says it controls: every other setting keeps today's value, including a setting that merely has the same value today.

**Root outputs.** Keep `vpc_id`, `alb_dns_name`, `cluster_name`, `repository_name` and `deployment_manifest_name` with their current values. `public_subnet_ids` becomes a map from the stable cell name to the `id` of that network cell's `aws_subnet.public`. `private_subnet_ids` becomes a map from the stable cell name to the `id` of that network cell's `aws_subnet.private`. `nat_public_ips` becomes a map from the stable cell name to the `public_ip` of that network cell's `aws_eip.nat`. `workload_target_group_names` becomes a map from the slot name to the `name` of that deployment slot's `aws_lb_target_group.slot`. `workload_log_group_names` becomes a map from the slot name to the `name` of that deployment slot's `aws_cloudwatch_log_group.workload`. `workload_queue_names` becomes a map from the slot name to the `name` of that deployment slot's `aws_sqs_queue.deployment`. Each output passes through outputs of the module that owns the resource (network for `vpc_id`, `public_subnet_ids`, `private_subnet_ids` and `nat_public_ips`; application for `alb_dns_name`, `cluster_name`, `repository_name`, `workload_target_group_names` and `workload_log_group_names`; operations for `workload_queue_names` and `deployment_manifest_name`): the root output is a plain reference to an output of that module, and that module output is a plain reference to the resource. A plain reference is a reference such as `module.network.<output>` or `<resource type>.<name>.<attribute>`, a local that holds one, or a `for` expression that only re-keys one (`{ for k, v in <reference> : k => v.id }`) or iterates a plain reference and looks each key up in one (`{ for k, v in var.<map> : k => <reference>[k].id }`); no literals, function calls, conditionals or string templates anywhere along the way.

**Not allowed anywhere in the configuration:** `ignore_changes`, `prevent_destroy` and `replace_triggered_by`, `removed` and `import` blocks, provisioners, `external` data sources, backend or cloud blocks, provider blocks other than the one in `providers.tf`, override files and `.tf.json` files.
