# S3 annotation projection

## Goal
Our ML pipeline needs S3 target storage to represent the project's current annotations, rather than a mixture of versions from concurrent web and worker activity. Extend the existing annotation export path so every connected S3 target storage eventually converges to one object per existing annotation, containing its latest saved content and a monotonic annotation version in the `annotation-version` S3 object metadata field.

## Requirements
1. Every committed annotation creation, edit and deletion reaches the exports, even when the RQ job or worker handling it is lost (see 3). Each successive saved annotation version has a strictly greater numeric `annotation-version` value than the preceding one. The existing RQ export worker must export creates and edits without requiring a manual sync. After activity settles, deletable storages have no objects for deleted annotations; a delayed export must not resurrect one.
2. Concurrent saves handled by separate workers, including an older PUT held until after a newer save, converge to the latest committed content. Annotation saves and deletions through the HTTP API still respond promptly while an export PUT of the same annotation is stalled at S3 (for over 30 seconds). A full storage sync concurrent with edits to 20 annotations also converges to their latest content and versions.
3. When an RQ job is lost or its worker dies after the database commit, a subsequent sync repairs missing or stale exports before reporting completion. Repeated syncs do not PUT unchanged objects. Newer annotations are exported to every connected storage.
4. For S3 target storages with `can_delete_objects` disabled, deleting an annotation leaves its existing exported object in place.

## Keep compatible
The existing annotation create, PATCH and DELETE HTTP flows, S3 target-storage creation and sync endpoints, and S3 export object JSON (including `id` and `lead_time`) continue working. The S3 target-storage endpoints are `/api/storages/export/s3` and `/api/storages/export/s3/{id}/sync`.

## Environment
Work in `/app` on the pinned Label Studio source. PostgreSQL and Redis are installed locally; start them with `sudo service postgresql start` and `sudo service redis-server start`. The local S3 emulator can be launched with `/app/.venv/bin/moto_server -H 127.0.0.1 -p 5000`; `S3_ENDPOINT=http://127.0.0.1:5000`, `AWS_ACCESS_KEY_ID=testing`, `AWS_SECRET_ACCESS_KEY=testing`, and `DJANGO_SETTINGS_MODULE=sd_settings` (with `PYTHONPATH=/opt/sd-settings:/app/label_studio`) select the bundled offline setup. Run migrations from `/app/label_studio` with `/app/.venv/bin/python manage.py migrate --noinput`.
