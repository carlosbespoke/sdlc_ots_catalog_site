We have three FlaskBB schema releases queued (4.0, 4.1 and 4.2), and none of their migrations exist yet. Ops needs to be able to pull any one of them after it has started taking writes: downgrade, put the previous app back, let it keep writing, then ship the same release again later. Rollback safety is the blocker: a pull must never lose or reinterpret anything either app version wrote.

Please add the Alembic revisions `fb400_profiles_moderation`, `fb410_topics_posts` and `fb420_storage_permissions` following `MIGRATION_SPEC.md`, the approved plan that fixes the target schema, the names and how every value maps in both directions. They must chain from the deployed `1789335000` in that order, with `fb420_storage_permissions` as the only head; extra revisions in between are fine. Downgrading a release to the previous release's revision (`1789335000` for 4.0) must restore exactly the earlier schema, with the same names, and keep every row (the newer app's writes too) mapped back as the spec says. Upgrading again must give the same schema as the first time and convert everything the old app wrote in the meantime. Whichever app version is live must run its SQL from `app_queries/r0` through `r3` unchanged, with any valid values, and read correctly mapped data. Nothing outside the spec may change: no lost or altered rows, no helper objects left behind. All of this has to hold for any data of the same shape, with the same kinds of legacy values in other rows and proportions, not just your copy. No migration may write to `alembic_version`, and the existing revisions, the four query files, `MIGRATION_SPEC.md`, `LICENSE` and `NOTICE` stay as they are.

The repo is at `/workspace/flaskbb`. Production is PostgreSQL 16.15 with database `flaskbb_prod`, and we use Alembic 1.20.0. The pipeline runs `alembic upgrade <revision>` and `alembic downgrade <revision>` from the repo root as the `flaskbb` role, which is not a superuser; each command has 30 minutes and must not leave anything running. A private copy of production runs in this container: `dbm status`, `dbm reset`, `dbm save NAME`, `dbm load NAME` and `dbm sql` manage it, and `DATABASE_URL` points at it as `flaskbb`.
