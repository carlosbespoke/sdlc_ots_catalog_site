We need public scheduling to stay responsive without repeatedly fetching an owner's CalDAV calendar, while keeping booking decisions exact. Extend the Python backend in `/app/backend` for CalDAV schedules; the public page is `POST /schedule/public/availability` with `{"url": "<public schedule link>"}`, and requests use `PUT /schedule/public/availability/request` with `{"url": "<link>", "s_a": {"slot": {"start": "<ISO datetime>", "duration": 30}, "attendee": {"email": "<email>", "name": "<name>", "timezone": "UTC"}}}`.

Availability across API instances and Celery workers must use shared per-calendar remote-calendar snapshots (without mixing calendars' busy events) no older than `AVAILABILITY_MAX_STALENESS_SECONDS` (3 seconds here); every successful page response carries a timezone-aware ISO timestamp (with a UTC offset) in `X-Availability-As-Of`. A new remote busy event must appear as a booked slot (its entry stays in `slots` with `booking_status` 3) within 8 seconds (and never from a snapshot older than the budget); read busy time from the remote calendar's events rather than free-busy queries, and note that the existing `CalDavConnector.list_events` keeps its results in Redis for up to `REDIS_EVENT_EXPIRE_SECONDS` (900 seconds), so snapshots need their own fresh fetch, and 20 concurrent reads across two instances of an expired snapshot cause at most one remote calendar fetch per calendar. A Celery worker must be able to refresh an active schedule's snapshot ahead of a page request, so a page request still sees that snapshot if CalDAV becomes unavailable immediately afterward. If the remote calendar is unavailable, return the last good snapshot only while it is within budget; after that, return HTTP 503 with the `AVAILABILITY_TEMPORARILY_UNAVAILABLE` error. If a refresh holder is killed or its remote fetch hangs (even while its process keeps running), another instance must take over and serve a fresh snapshot within 8 seconds; an older held response must not replace a newer snapshot even if its holder continues running.

For the same slot, exactly one of two simultaneous booking requests can succeed, even on separate API instances. A remote event created after the page view must make the booking return the existing `SLOT_ALREADY_TAKEN` error (HTTP 403), using a fresh remote interval check rather than a page snapshot. Preserve the existing page's `title`, `owner_name`, `slot_duration`, `booking_confirmation`, and `slots` fields (including each slot's `start` and `booking_status`); a successful request still creates an attendee-linked appointment, and a previously occupied slot still returns `SLOT_ALREADY_TAKEN`. Expose the worker refresh as the Celery task `appointment.tasks.availability.refresh_availability`; `celery call` with no arguments refreshes every active schedule's snapshot. Do not add custom PostgreSQL triggers on `slots`, `appointments`, or `attendees`, or rules on `slots`. PostgreSQL and Redis are available locally; start them with `sudo service postgresql start` and `sudo service redis-server start`. The backend and Celery are installed in `/app/.venv`; no external network or Docker daemon is available inside the container.
