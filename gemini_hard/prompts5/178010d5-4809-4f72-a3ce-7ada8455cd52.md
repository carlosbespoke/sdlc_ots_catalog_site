# OCI image tool: diagnosing widespread misbehaviour without a test suite

This is the command-line tool people use to build, read and write container images held as directory trees on disk, and it now misbehaves all over. The repository has received 28 separate undocumented edits. What follows is everything that has been observed from the outside, in the order the problems were run into.

Pointing the tool at an empty directory and asking it to work with the image store held there succeeds, when there is plainly no store there; and asking it to lay down a fresh store in a directory that already holds one also succeeds instead of refusing. Those are two independent slips, one on each side. Exporting SOURCE_DATE_EPOCH=1234567890 before a build no longer yields the instant that value denotes; the timestamp that comes back sits far away from it, although leaving the variable unset still yields no timestamp at all and a value that is not a number still reports a parse failure. Handing in an identity mapping written with three fields, such as 0:0:1 or 32:100:2421, is now rejected outright, while the two-field form such as 2:1 is still accepted and still fills in a size of one.

Sweeping an image directory for unreferenced content while supplying a callback that itself reports a failure comes back reporting success, swallowing the callback's complaint. Asking for the bytes of a descriptor that carries the canonical two-byte empty-JSON payload inline now fails, both when asking for the parsed object and when asking for a stream of the raw bytes; descriptors that embed ordinary text inline still hand it back, and ones whose recorded digest or length disagrees with the inline bytes are still refused for exactly those reasons. Wrapping a digest-checking stream inside a second one that demands the very same digest and the very same length no longer notices that the inner check already covers it, so the data is hashed a second time; wrappers demanding a different digest, or a different length, still do their own hashing as they always did.

Dumping a manifest in human-readable form loses everything from the point where the other manifest it is attached to would have been described onwards, so the annotations that come after it never appear at all; manifests with no such attachment print in full, down to the last annotation. Dumping an image's stored settings is worse when they carry a made-at timestamp: the text breaks off right where that timestamp belongs, while settings without one still print out completely. Putting a made-at timestamp into an image's settings and reading it straight back gives something other than the value just set. Serialising an image's settings into a file already prepared for writing reports a byte total that does not agree with the size the file actually ends up with.

Comparing a directory tree before and after a whole nested subtree has been removed, and then reducing the resulting set of differences to its minimal form, gives back a set no smaller than the one it was handed, still carrying one removal record for every single path that went away rather than a single record for the top of the vanished subtree. Two edits conspire here: one in the decision about which kind of difference deserves collapsing, and one in how a path is compared against the prefix it is being tested against. Producing an archive stream of changes from such a difference set when one of the changed files has since been removed from disk, or when a directory below the real root is handed in as the root, no longer surfaces the not-found failure at all — reading the stream simply runs to its end as if nothing were missing.

Putting a soft pointer to another path into an archive stream that is being built does not produce the entry it should: its type, the path it aims at, its ownership and its timestamps do not turn up on the other side. Packing a tree that follows the conventions of stacked mounts goes wrong in two further, unrelated ways. When a directory is marked opaque through the kind of extended attribute an ordinary user can set, the stream produced for it is wrong, both when the whole tree is packed and when an entry is inserted into a stream already under way. And in that insertion flow, both opaque markings and the extended attribute that stands for a deleted entry come out under names beginning with a slash instead of names relative to the root of the tree being packed. Separately, asking whether a given extended attribute is hidden on disk for such a tree answers yes for names carrying the doubled, escaped form of the reserved prefix, even though those are precisely the names that should surface and fold back down to a single prefix; names with one prefix, and names with none of it at all, still answer as they used to.

Expanding an archive stream that holds a plain file called foo and then an entry at foo/bar/baz fails, instead of turning that file into a directory so the deeper entry has somewhere to live. A stream holding an entry that asks to become a second name for a file already written fails outright, while the plain files and soft pointers in the same stream land without trouble. While a stream is being written out, a soft pointer aimed at a directory is reported as not aimed at one. Writing a complete image out into a bundle directory fails even when no request was made to begin partway down the stack of archives; and it fails for a second, independent reason as well, in the step that derives the container's own settings file from the image's stored settings — this one also spoils the case where the work is asked to begin at a chosen point and skip everything before it. Turning an archive entry's type byte into a file mode yields 1 for plain files, where soft pointers, directories, fifos, character devices and block devices are all still translated as before. Adding fresh content to an image records an uncompressed-size annotation that is one byte larger than the content actually handed over.

Finally, two things that used to work on paths buried under directories whose permission bits have all been cleared no longer do: setting a file's access and modification times there reports a failure rather than briefly making the way in, and listing what such a directory holds likewise fails rather than returning what is in it. And in the in-memory index from absolute paths to values, deleting an interior path that holds a value of its own while deeper paths beneath it still hold theirs leaves the structure inconsistent — nodes that have nothing left under them are still found by lookup, and the running tally of live items beneath the root no longer matches what is actually stored.

It worked before a set of undocumented edits to the source of umoci. The repository has
no test suite to run: finding out what is wrong, and convincing yourself you have fixed
it, is part of the task.

Restore the behavior described above.

Record the functions that contain those edits in `/app/rca.json`, one entry each:

```json
{
  "causes": [
    {
      "file": "cmd/umoci/config.go",
      "function": "enclosing_function_name"
    },
    {
      "file": "cmd/umoci/config.go",
      "function": "Type.method_name"
    }
  ]
}
```

`file` is the path of the file relative to the repository root, written exactly as it
appears in the tree. A file inside a directory keeps its directory prefix: the example
above is `cmd/umoci/config.go`, not `config.go`.

`function` is the function name. A class or receiver prefix, written `Type.name`, is
accepted anywhere and is required when two functions in the same file share a name: the
bare name cannot tell them apart. When an edit sits inside a function nested in another
function, either name is accepted. Name every function one of the undocumented edits is
in, and only those. Where you wrote the fix does not matter: if you restored the behavior
from a caller or from a helper of your own, name the function the edit is in rather than
the one you wrote. If you suspect a function but found no edit in it, leave it out.


Before you edit any code, write your research and your plan to /app/RESEARCH_AND_PLANNING.md. Cover what you learned about the existing code and the constraints that shape the change, then how you intend to carry it out and why, including how you will know it works. Be concrete - the files, names and decisions specific to this codebase, not generalities. Complete the document before you touch any code: it is the record of your up-front investigation and decisions, and it should not be rewritten to match whatever the implementation turns into afterwards. Once it is done, implement the plan.
