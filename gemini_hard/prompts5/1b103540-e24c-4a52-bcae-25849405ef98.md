# Versioned workflow waits

## Goal
Support versioned workflow waits so authors can publish revisions while contacts are still in flight. Each contact should receive one appropriate follow-up even when event delivery overlaps a timeout or a worker restart.

## Requirements
1. A `WAIT_FOR_EVENT` step selects the first matching event received after entering the wait or its timeout, never both. Its `config.eventName` identifies the matching event and `config.timeout` is in seconds. For a wait with separate outgoing branches, an unconditional transition is the event branch and a transition whose condition is `{"branch":"timeout"}` or `{"fallback":true}` is the timeout branch. Concurrent event deliveries, including five copies, produce one continuation; the event and timeout branches never both enqueue an email for one execution. With no event, the timeout branch completes. A `DELAY` resumes once, including duplicated jobs.
2. An execution reads an immutable published graph from start to finish. Publishing edits to steps and transitions makes the revised graph available to new executions; a `PATCH /workflows/:id` publishes the current graph even when it only updates workflow metadata such as `description`. Deleting a step from the live graph does not change an execution already waiting there. Store published graphs in `workflow_versions` (with `id` and `workflowId` columns), and pin each execution with `workflow_executions.versionId`. An old published version remains available while any execution uses it; once its executions finish, delete that version, leaving only the current version.
3. Resolution and continuation survive a killed worker: after restart a timeout winner finishes within 30 seconds with one email record, not zero or two. The same applies if the kill happens after the resolution commits but before the next step completes.

## Keep compatible
The existing `POST /events/track` accepts `name` and `contactId` and returns an event with `name`; `GET /workflows` returns a `data` array. Keep `POST /workflows`, `POST /workflows/:id/steps`, `POST /workflows/:id/transitions`, `POST /workflows/:id/executions`, `PATCH /workflows/:id`, and `DELETE /workflows/:id/steps/:stepId` usable with their existing request shapes.

## Environment
The repository is at `/app`. PostgreSQL and Redis are installed locally; start with `sudo service postgresql start` and `sudo service redis-server start`. The API and queue worker live in `apps/api`, with database schema and migrations in `packages/db/prisma`. Use `DATABASE_URL` and `DIRECT_DATABASE_URL` for PostgreSQL and `REDIS_URL` for Redis. Docker is not available inside this container. Build from `/app` using `node .yarn/releases/yarn-4.9.1.cjs turbo build --filter=api...`.
