# Namespace storage budgets for shared zot

Two zot instances sharing an S3 bucket and Redis can currently admit uploads without a byte budget. The existing `storage.maxRepos` limit is not a byte limit and cannot protect a namespace from filling storage.

## What we need

- Add `storage.namespaceQuotas`, a map of repository-name prefixes to byte limits; the longest matching prefix on a repository boundary wins. Add `storage.uploadHoldTTL` as a duration; a configured `15s` hold expires within 30 seconds after its last successful upload activity.
- Make `GET /v2/_zot/ext/quota/{ns}` return JSON integer fields `limitBytes`, `usedBytes`, `heldBytes` for a configured namespace on either instance. `usedBytes` counts each distinct digest once per namespace, even across repositories; `heldBytes` covers accepted partial upload bytes not yet committed. Both instances agree, including after simultaneous starts with pre-existing images uploaded while quotas were disabled.
- Enforce `usedBytes + heldBytes <= limitBytes` across instances. PATCH, final PUT (including bytes sent with PUT), monolithic POST with `digest`, cross-repository mount, and dedupe hydration on HEAD cannot bypass the limit. A quota refusal is HTTP 429 with an OCI `DENIED` error; it must not create a visible blob. A second upload of an already-accounted digest in the same namespace does not add usage.
- An abandoned upload or killed instance eventually frees its hold; an expired session cannot later consume capacity already claimed by another client. Cancelled uploads free their holds. Direct blob deletion, or removing a manifest and collecting blobs, returns capacity only once the namespace has no remaining repository reference to that digest. With GC enabled, capacity from a deleted manifest's orphaned blobs is reclaimed within 30 seconds.

## Keep working

Existing OCI blob upload initiation, PATCH, PUT, mount, HEAD, DELETE and manifest-delete/GC flows, including successful pushes without namespace quotas and `storage.maxRepos`, retain their existing responses.

## Setup

The repository is at `/app`. Redis is at `redis:6379`, MinIO at `minio:9000` (bucket creation is needed); S3 credentials are `zot` / `zotpassword`, region `us-east-1`. Two zot server processes can use separate HTTP ports with the same Redis cache/metaDB and MinIO bucket. Build offline with `CGO_ENABLED=0 go build -o /app/zot ./cmd/zot` from `/app`; the UI extension is not needed. Docker is unavailable inside the solver container.
