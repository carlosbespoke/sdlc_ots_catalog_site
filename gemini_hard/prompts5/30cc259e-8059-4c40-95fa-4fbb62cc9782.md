Our webhook receiver must not lose NetBox REST changes when Redis is unavailable, the receiver temporarily rejects requests, or a worker dies. Implement durable, ordered webhook deliveries for REST create, update and delete on `/api/dcim/sites/` and `/api/tenancy/tenants/` when an enabled EventRule targeting a Webhook matches. A committed write must record its deliveries atomically with the object change; an invalid item in a bulk create must reject the request (HTTP 400), leave no created object, and produce no deliveries. Redis downtime of 20 seconds must not cause writes to fail or lose events: deliver each within 45 seconds of recovery. API writes must still succeed while Redis is down, including any of NetBox's own Redis-backed caching on the request path.

A receiver returning 503 for 20 seconds must receive all changes within 45 seconds after recovery; make the first retry within 10 seconds and cap retry backoff at 30 seconds. If a worker is SIGKILLed during an in-flight HTTP request, a replacement worker must resume the delivery within 45 seconds. With two API processes and two workers, 20 concurrent changes to one object must arrive in per-(webhook, object) commit order: successful requests carry strictly increasing `X-NetBox-Sequence` values, starting at 1 for each (webhook, object) stream, and the final payload reflects the final stored object. Each attempt must use the same `X-NetBox-Delivery` identifier for that delivery; receivers should deduplicate by that identifier (an in-flight request can be repeated after a crash). Expose a read-only `/api/extras/webhook-deliveries/` GET list (paginated under `results`; POST returns 405) with delivery ID (`id`), status (`delivered` after success), actual HTTP attempt count (`attempts`, including failed attempts and at least 2 after a retry), and sequence (`sequence`). Preserve existing webhook templates, additional headers, event payload fields (`event`, `timestamp`, `model`/`object_type`, `data`, `snapshots`), conditions, `X-Hook-Signature`, and existing `/api/status/` worker reporting (`rq-workers-running` reflects running workers); nonmatching conditions send nothing. In particular, a custom body template such as `{"event":"{{ event }}","name":"{{ data.name }}"}` must render the created event and object name without added fields; a templated additional header such as `X-Object-Name: {{ data.name | header_safe }}` must render the name. Preserve the signature as the hex HMAC-SHA512 of the exact transmitted body using the webhook secret, including when using a custom template. A configured literal header such as `X-Example: present` must also reach the receiver.
