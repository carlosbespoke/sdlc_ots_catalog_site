# Rolling run-tag schema upgrade

We need to deploy MLflow tracking servers without pausing tracking when run-tag storage changes. Extend this checkout so current-release servers and upgraded servers can share a PostgreSQL tracking database during a rolling rollout. The schema change is a separate `run_tag_values` table keyed by `(run_uuid, key)`, with the tag value stored as text; existing `tags` remain readable and writable until old servers leave.

Requirements:
- `mlflow db expand-run-tags <database_uri>` adds the shadow storage without advancing the current release's Alembic revision. Both releases must continue serving reads and writes on the expanded database.
- Run tags (including 8,000-character values), metrics and runs written through either release remain visible through the other. Changing or deleting a tag while copying historical tags must not resurrect a stale value. Registry model versions and aliases remain visible through either release.
- `mlflow db backfill-run-tags <database_uri> --batch-size N` copies historical tags in bounded committed batches, keeps a durable checkpoint, and safely resumes after SIGKILL. Repeating the command must not duplicate data or lose updates from concurrent servers.
- A subsequent `mlflow db upgrade <database_uri>` may advance to the contract revision only after backfill completes; before that it exits with a non-zero status and leaves the revision unchanged. Contract fences current-release binaries but preserves the legacy `tags` table while this release still reads it. Once contracted, tags, metrics, runs and registry entries written throughout the rollout remain readable; a current-release binary must refuse that revision.
- The upgraded server accepts the original, expanded and contracted revisions but rejects other revisions clearly. It reports its supported revisions at `GET /schema-compatibility` as a JSON object with the keys `minimum`, `maximum`, `current` and `expanded`; retain the existing `GET /health` status 200 and `GET /version` text response.

Rollout identifiers: the original Alembic revision is `f4a9b2c7d1e6`, the expanded revision is `9c724ed7a611`, and the contract revision is `3c8e71a4b229`. Expansion must leave the database stamped at the original revision; after successful backfill, upgrade stamps the contract revision. Store durable backfill state in `run_tag_backfill`, including a row with `id = 1`, a boolean `complete` field indicating whether backfill has finished, and `cursor_run` and `cursor_key` fields recording the last committed tag position.

Work in `/app`. PostgreSQL is installed locally; start it with `sudo service postgresql start`. Database URLs use `postgresql+psycopg://...`; run the CLI from `/app` with `python -m mlflow db ...`. The existing MLflow HTTP routes and PostgreSQL backend URI remain the public interface.
