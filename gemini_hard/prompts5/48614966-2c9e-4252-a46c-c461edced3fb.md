# Shared analyzer quotas

## Goal

Add organization-level, quota-aware scheduling for external-service analyzers so analysts can share provider keys without exhausting them. The quota applies across Celery workers and organizations, with fair service for each organization.

## Requirements

1. Add `GET` and `PATCH /api/analyzer/<name>/quota` for an organization's analyzer configuration. An owner can set and read `quota_calls` (calls), `quota_window` (seconds), `quota_hold` (seconds), `quota_key` (optional shared-key string), and `quota_weight` (integer). Shared keys apply across organizations for the same analyzer; without one, budgets are organization-local.
2. Before an analyzer contacts its provider, admit it against a shared rolling-window budget across workers. With four calls per ten seconds, twelve concurrent analyses finish successfully, with no more than four provider requests in *any* ten-second interval. Work that cannot be admitted remains visible as `waiting_quota` in job/report status and resumes when capacity is available; it does not fail for quota exhaustion. Jobs in this workload finish within 100 seconds.
3. A worker killed while awaiting a provider response cannot strand its job: with a three-second hold, a replacement worker finishes that analysis within 35 seconds of the kill.
4. Organizations sharing a key with equal weights get a fair turn even with unequal backlogs: when one submits twenty analyses and another submits two against four calls per ten seconds, both smaller-organization jobs finish within 55 seconds, all twenty larger-organization jobs within 125 seconds, without violating the shared rolling limit.
5. An unexpected provider HTTP 429 pauses quota-backed execution for the configured `rate_limit_timeout` (or one quota window if unset). Waiting work resumes when the pause ends, without failed analyses. For a four-second window and no configured timeout, three analyses finish within 70 seconds after the provider becomes available again.

## Keep compatible

Unmetered `POST /api/analyze_observable` analyses still complete and call their configured provider once; `GET /api/jobs/<id>` continues to expose the resulting `reported_without_fails` job and analyzer reports.

## Environment

The IntelOwl source is in `/app`; work there. PostgreSQL and Redis are installed locally and can be started with `sudo service postgresql start` and `sudo service redis-server start`. Use database `sd` with `app:app` on localhost for local verification; the Celery broker is `redis://localhost:6379/1`. The services are started as separate Django API, two workers and beat processes. Run the application using its existing `manage.py` and Celery entry points from `/app`; Docker is unavailable inside the container.
