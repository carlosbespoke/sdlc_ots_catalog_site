# Content cache coherence for Pulp distributions

Support publication rollouts across mirrors without sacrificing response-cache performance: once a change to what a distribution's base path serves commits, no content instance should return an older cached answer.

Requirements:

- A completed distribution switch to another `pulp_file` publication changes previously cached manifest and artifact responses on the next GET, across content instances. A repeat GET of an unchanged response remains an `X-PULP-CACHE: HIT`.
- Publishing a new version of a repository-backed distribution, deleting its publication, deleting a distribution, renaming its base path, and reclaiming repository artifacts cannot leave a pre-change response cached. Deleted or renamed-away base paths answer HTTP 404 on both instances.
- An on-demand download begun before a distribution switch may finish afterward; subsequent GETs must use the new publication, not its late cache fill.
- During a publication's uncommitted finalization, reads may see the previous publication, but after the publish task finishes they must see the new publication.
- Serving a cached response must not depend on PostgreSQL beyond the existing per-request domain lookup: while the other tables are locked or slow, both content instances keep answering already-cached requests promptly with `X-PULP-CACHE: HIT`, and after a change they cache and serve the new answer the same way.
- Changes committed while Redis is unreachable remain visible when it recovers, including on content instances that served no requests during the outage, even if the worker exits immediately. Content continues to return correct database-backed responses without 5xx during the outage, and repeat reads become cache hits again after recovery. Recovery of both content instances must take at most 10 seconds after Redis returns, including after a 20-second outage.

Implement the change in `/app` (pulpcore at `3a8509e5d4684035974ddc4dac768903e70f7a4f`). Preserve the existing `pulp_file` repository, publication, distribution and content HTTP flows, including `PULP_MANIFEST`, artifact GET and `X-PULP-CACHE`. Other plugins' caches, API-side `SyncContentCache` and external CDNs are outside this change.

Work as `agent` in `/app`. PostgreSQL and Redis are installed locally; start them with `sudo service postgresql start` and `sudo service redis-server start`. The app uses `/etc/pulp/settings.py`, database `sd` on localhost with credentials `app:app`, and Redis at `localhost:6379`. A fresh image has only the PostgreSQL `postgres` role (password `postgres`): create role `app` with password `app` and `CREATEDB`, create database `sd` owned by `app`, enable PostgreSQL `hstore`, then run the Django migrations. Docker is unavailable inside the container. The canonical content command from `/app` is `pulpcore-content --bind 127.0.0.1:8081 --workers 1 --no-control-socket`.
