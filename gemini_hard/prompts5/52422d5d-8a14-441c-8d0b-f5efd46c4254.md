# quic-go-regen

An application built on this library dials a peer, brings a link up, moves data over it, gives up on a transfer partway, and winds itself down, and it now gets all of that wrong in ways that look unrelated to one another. Nothing about the protocol changed and nothing about the callers changed. The repository has received 30 separate undocumented edits.

Getting a link up at all is the first thing to go. Almost every fetch against a locally launched peer dies during setup with the identity credential refused: the throwaway credential minted on the fly for the loopback address no longer covers what the dialing side checks. The disposable signing authority such a credential chains up to is separately minted with a validity span beginning a year later than it used to, so links relying on that chain fail rather than completing. A peer that has to pick the hostname the dialer asked for out of the dialer's opening greeting takes the list of names from an offset before the position it computed rather than after it, so the greeting is misparsed and the link either never comes up or comes up under the wrong identity. A peer announcing exactly the largest permitted count of simultaneous two-way transfers is now turned away while its opening limits are being taken in, although one announcing one less is still accepted. Point a dialer at a peer that demands a cookie before it will serve, and let that cookie either expire before it comes back or arrive from an address other than the one it was issued to: the dialer should finish with a failure naming the refused cookie and gets nothing of the kind, while an opening message that cannot be decrypted at all, which should simply be discarded with neither a refusal nor a fresh challenge, now provokes the refusal. And a fabricated first-flight message spliced in by an attacker in the middle, built from a victim's link labels and a chosen set of protocol items, draws no reaction at all: one carrying an acknowledgement for a number never emitted should tear the link down with a protocol violation naming an acknowledgement for something unsent, an empty one should leave the link to time out, and neither outcome is produced any more, because the fabricated message is no longer assembled in a form the victim will process.

Keeping a link going once it is up has become unreliable too. Links that live long enough for their traffic secrets to rotate break, because the countdown that retires the superseded secrets is armed against the generation after the current one instead of the one before it. Long fetches over links that hand out a fresh credential for resuming later fail intermittently, that credential now being written into a buffer sized differently from before. And switching over to a freshly issued label for the link pre-charges the counter that measures activity under it with one instead of beginning at zero.

Once data is moving, the accounting is off in several unrelated ways. When the whole-link outgoing allowance is exactly used up, nothing announces that the writer is held up; the announcement appears only once the allowance has been passed, so a transfer that should declare itself stalled at the limit stays quiet. Re-announcing the same allowance the peer already granted is taken as a fresh raise rather than as a repetition. Clearing the whole-link outgoing accounting leaves one byte of room reported as usable where none should be. Growth of the inbound allowance no longer respects the callback that vets enlargements: with a callback that declines, it is enlarged anyway, and a dialer sees a larger offer it should never have been given. Asking for the next waiting protocol item when the room left is exactly the size of that item yields nothing instead of the item. Announcing the same data-carrying transfer twice as having something to write is no longer the no-op it was, and the transfer is drained twice in one round, so a single pass produces more items than there were distinct transfers. Outgoing buffers come out of their recycling store already one byte long instead of empty, so messages are built on top of a stray leading byte; one visible consequence is that the near-universal bundling of an acknowledgement together with data in the same message, in a ping-pong of one-byte replies, stops happening reliably. A fresh round-trip sample exactly equal to the smallest one yet seen is taken as an improvement, shifting when the writer leaves its opening ramp-up phase. Taking a message that genuinely went out back off the record of what has already gone out reports it as unknown, which tears the link down the moment an acknowledgement for it arrives, and a number deliberately left unused is filed against the number after the one actually left out.

Giving up partway and winding things down are visibly wrong. When the peer asks us to give up writing, the abort notice we emit claims one byte still has to be delivered reliably rather than none, which is observable both immediately and after that notice is acknowledged or lost. An inbound transfer that has already finished and been cleaned up is handed back again on the next lookup, as though it were still around, instead of being reported as gone. A link shut down on our side answers arriving messages on the wrong schedule: the farewell notice should go out for the 1st, 2nd, 4th, 8th and 16th message that arrives and for no others, and it now goes out for a shifted set, which also changes how many identical repeats an onlooker counts after a peer departs. A per-fetch byte channel is marked entirely finished as soon as either of its two directions ends, so consuming a body to its end declares the whole thing done although writing is still possible, and when the writing direction has already failed, finishing the consuming direction fails to declare it done at all; links are torn down or kept alive at the wrong moment, and idle ones do not go away when the serving side begins winding down. Winding that serving side down reports the wrong outcome and leaves outstanding work in the wrong condition: given a deadline shorter than an in-flight fetch it should come back with the deadline exceeded and should terminate that fetch around the deadline, and instead it takes the failure branch on a successful teardown.

Asking for a document and reading back what comes is wrong in two further ways. Taking in a reply whose status is plainly 200 now behaves as though those were non-final, interim fields, so the caller keeps waiting for another set that never arrives. And in the plain, minimal fetch format, a first line arrives with its trailing carriage return and newline still attached and is looked up verbatim, so a fetch for a registered location comes back with the wrong body.

Reading back the written account of a run afterwards misleads as well. The description of an outgoing compact-form message attaches acknowledgement details to messages that carry none and omits them from the ones that do. The two-ends description emitted when a link begins inverts the treatment of the local address: a link begun from an explicitly chosen local address is recorded under a wildcard address, and one begun without a local address is recorded with no address at all instead of the all-zeros address of the family the peer is on, although the peer's own address and the local port number are still reported as they should be. The diagnostic line about the loss-recovery countdown is emitted when debug output is switched off and when nothing at all is outstanding, rather than only when both hold. And the value 0x200 is now reported as belonging to the block of failure numbers that indicate an alert raised during secure setup, even though only 0x100 through 0x1ff do — values below 0x100 and above 0x200 are still reported as outside it.

It worked before a set of undocumented edits to the source of quic-go. The repository has
no test suite to run: finding out what is wrong, and convincing yourself you have fixed
it, is part of the task.

Restore the behavior described above.

Record the functions that contain those edits in `/app/rca.json`, one entry each:

```json
{
  "causes": [
    {
      "file": "example/client/main.go",
      "function": "enclosing_function_name"
    },
    {
      "file": "example/client/main.go",
      "function": "Type.method_name"
    }
  ]
}
```

`file` is the path of the file relative to the repository root, written exactly as it
appears in the tree. A file inside a directory keeps its directory prefix: the example
above is `example/client/main.go`, not `main.go`.

`function` is the function name. A class or receiver prefix, written `Type.name`, is
accepted anywhere and is required when two functions in the same file share a name: the
bare name cannot tell them apart. When an edit sits inside a function nested in another
function, name the innermost function that directly contains it; the enclosing function's
name is accepted too, except when another edited function in the file shares it, where only
the innermost name tells the two apart. Name every function one of the undocumented edits is
in, and only those. Where you wrote the fix does not matter: if you restored the behavior
from a caller or from a helper of your own, name the function the edit is in rather than
the one you wrote. If you suspect a function but found no edit in it, leave it out.


Before you edit any code, write your research and your plan to /app/RESEARCH_AND_PLANNING.md. Cover what you learned about the existing code and the constraints that shape the change, then how you intend to carry it out and why, including how you will know it works. Be concrete - the files, names and decisions specific to this codebase, not generalities. Complete the document before you touch any code: it is the record of your up-front investigation and decisions, and it should not be rewritten to match whatever the implementation turns into afterwards. Once it is done, implement the plan.
