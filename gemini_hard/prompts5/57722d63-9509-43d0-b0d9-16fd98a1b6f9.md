The dispatcher accepts a task assignment as delivered even when its gRPC stream send disappears. A heartbeating worker that never starts the task can hold it until its execution timeout, spending an application retry on work that never ran.

Implement confirmed delivery for ordinary, non-batch Go worker tasks across grpc-api instances, the task controller and the Go worker SDK:

- An ack-capable worker advertises acknowledgment support at registration with `runtime_info.extra` set to `assignment-ack-v1` and acknowledges each assignment on receipt, before running it and without waiting on its other acknowledgments, with a `STEP_EVENT_TYPE_ACKNOWLEDGED` step action event carrying its worker id and the task run's external id and retry count. Persist confirmation against the current task attempt and worker. Reject an acknowledgment that does not match a current assignment to that worker (a stale or foreign one) with an error status, without confirming anything. An older worker without acknowledgment support keeps receiving tasks, and its assignments are not reclaimed for lack of acknowledgment.
- Ten seconds after an unacknowledged assignment, release its worker slot and make the same attempt schedulable again, even if that worker continues to heartbeat or the original grpc-api process was killed. Reassignment creates a `REASSIGNED` task event, not a `TIMED_OUT` or `FAILED` event, and does not increase `retry_count`. If the grpc-api process holding an unacknowledged assignment is killed, a worker connected to another grpc-api instance finishes the task within 45 seconds; one or more silent workers alongside an available worker, even one with only a few slots, cannot strand a burst of 20 tasks beyond 30 seconds.
- Repeated delivery of the same task and retry count never executes the body twice. An acknowledged assignment remains with its worker for 60 seconds rather than being reclaimed.
- Keep the existing task-event API `rows` response, task cancellation API `ids` response, worker registration and heartbeat, and worker-slot accounting working.

The repository is at `/app`. PostgreSQL and RabbitMQ are available locally; start them with `sudo service postgresql start` and `sudo service rabbitmq-server start`. The engine must run with `SERVER_SECURITY_CHECK_ENABLED=false`. Docker is unavailable inside the solver container. Apply schema changes with a Goose migration.
