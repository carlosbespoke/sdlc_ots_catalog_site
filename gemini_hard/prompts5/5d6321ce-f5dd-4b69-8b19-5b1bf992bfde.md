# A multi-architecture emulation engine with silent behavioural regressions and without a test suite

The repository has received 18 separate undocumented edits.

A library that lets a program lay out a simulated address space, load machine code for any of several processor families into it and run that code now gets a long list of things wrong. Nothing about the machine code being fed in changed and nothing about the calling program changed. The same setups that used to be handled correctly now hand back wrong values, and in several places a run that used to finish stops outright.

Start with laying out the address space. A program that maps several regions and then starts a run crashes or gets nonsense back whichever family it picked, and a setup with more than a couple of regions fails before a single instruction completes. A region mapped readable, loaded from by the running code, ends the run with a protection fault instead of handing back the bytes stored there. A region fitted with read and write callbacks has every touch from the running code split into pieces smaller than the access that was made, so the callbacks are asked for sizes nobody requested and the value the running code receives is wrong. Loading a wide value out of the address space yields one whose upper half does not match what was put there.

Asking the engine to do something on the caller's behalf fails in its own ways. Registering a callback hands back a failure code about the registration instead of success, even though the callback does get installed. Asking the engine to save its state into the holder it provides reports that it ran out of resources rather than success. Raising, through the runtime control interface, how many instructions may be handled in one stretch and then starting a run aborts rather than honouring the request. Choosing a different variant of a processor family through that same interface and then starting a run faults immediately.

Watching a run from the outside is no better. A software interrupt raised by 32-bit code never reaches the callback registered for interrupts, and callbacks that had already been removed are consulted in its place. On the 64-bit desktop family, the callback registered for the instruction that asks the operating system for a service is not run when that instruction is reached, while callbacks registered for other instructions are consulted for it instead. When a run ends part way through, on a fault or at the address it was told to stop at, the address reported back names a different instruction than the one that was running.

Running code and reading the results back afterwards goes wrong in a scatter of ways. In 32-bit code of one family, an addition that also sets the condition flags, when it is watched through a callback registered to observe the two values it operates on, hands that callback the wrong first value, reporting a copy of the second operand in place of the first, and an instruction that writes the low byte of the status register leaves those bits as they were. On the 64-bit members of that same family, results of instructions that also change engine state are thrown away, so registers read after the run still hold their old values. Code for the desktop family that writes only the low sixteen bits of a register aborts the whole process rather than being emulated. Running several stretches of code one after another in the same engine lets values from earlier stretches leak into later arithmetic, so registers come back holding results that depend on what ran before. For another family, reading a register back through the interface returns the contents of its neighbour, so what was written before a run is not what comes out after it, and starting an engine for that family damages its own start-up bookkeeping before any instruction runs, so the first run ends in a crash or in values that make no sense.

It worked before a set of undocumented edits to the source of unicorn. This checkout has
no test suite.

Restore the behavior described above.

Record the functions that contain those edits in `/app/rca.json`, one entry each:

```json
{
  "causes": [
    {
      "file": "/workspace/repo/bindings/go/unicorn/hook.c",
      "function": "enclosing_function_name"
    },
    {
      "file": "/workspace/repo/bindings/go/unicorn/hook.c",
      "function": "Type.method_name"
    }
  ]
}
```

Each entry is an object with a `file` and a `function`; anything in `causes` that is not
an object counts as a wrong entry. `file` is the absolute path of the file, in the
repository checked out at `/workspace/repo`, written exactly as it appears in the tree.
A file inside a directory keeps its directories: the example above is
`/workspace/repo/bindings/go/unicorn/hook.c`, not `hook.c`. The same path relative to
the repository root, such as `bindings/go/unicorn/hook.c`, is accepted too. A path
outside `/workspace/repo`, or a path with a `..` segment, does not name a file in the
repository and counts as a wrong entry.

`function` is the function name. A class or receiver prefix, written `Type.name`, is
accepted anywhere and is required when two functions in the same file share a name, since
the bare name cannot tell them apart; a function with no class or receiver has no prefix to
add, and its bare name names it. When an edit sits inside a function nested in another
function, name the innermost function that directly contains it; the enclosing function's
name is accepted in its place, except when that function holds another edit too, where only
the innermost names tell them apart. Name every function one of the undocumented edits is
in, and only those, once each: an entry for an edit another entry already names, such as
the same function written twice, with and without its prefix, or by its enclosing function
beside its innermost one, counts as a wrong entry. Where you wrote the fix does not matter:
if you restored the behavior from a caller or from a helper of your own, name the function
the edit is in rather than the one you wrote. If you suspect a function but found no edit
in it, leave it out.
