Payment apps have received duplicate cancellation requests for abandoned checkouts, and a checkout completed during cleanup has lost its authorization. Fix automatic transaction fund release in `/app` across the Celery worker, checkout completion API and synchronous payment-webhook delivery.

An eligible checkout is older than its channel's release TTL, automatically refundable, and still has an authorized or charged transaction not owned by an order. A release sends one cancellation request for an authorization or one refund request for a charge; the app's successful answer is recorded once as `CANCEL_SUCCESS` or `REFUND_SUCCESS`. Two overlapping workers must create only one request event for each transaction and must not send a second independently keyed app request; retries of that single request may result in multiple attempts. Completion and release must be mutually exclusive across API and worker processes: an order-owned transaction is never released, and `checkoutComplete` on a checkout whose release has been claimed returns no order and a distinct `FUNDS_RELEASE_IN_PROGRESS` error code. A completion racing a release must never both transfer the transaction to an order and request its cancellation or refund.

For an unreachable payment app, connection refusal, timeout or HTTP 5xx must be retried without creating a new request event: every attempt has the same event identity and idempotency key. The first retry occurs within 10 seconds; retry an outage lasting 20 seconds, and record a successful response within 30 seconds of recovery. The release beat cadence is configurable in seconds with `CHECKOUT_RELEASE_FUNDS_INTERVAL_SECONDS` (default 600; a value of 2 means two seconds). A checkout younger than the TTL or with `automatically_refundable=False` is untouched. Preserve existing checkout completion, transaction event, webhook names and payload fields.

Work in the Saleor repository at `/app`; source code and migrations are the deliverable. PostgreSQL and Redis are installed locally and can be started with `sudo service postgresql start` and `sudo service redis-server start`; the app database URL is `postgres://saleor:saleor@localhost/saleor`. Python dependencies are installed in `/app/.venv`. Run application commands from `/app` using `/app/.venv/bin/python`. The system must work with two independent workers and two API instances sharing the database and broker, not just within one process.
