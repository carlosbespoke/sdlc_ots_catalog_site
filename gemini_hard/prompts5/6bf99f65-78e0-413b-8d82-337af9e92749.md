# Ticket: ordered, resumable LiveQuery objects

Dashboard subscribers can finish on stale values: Redis pub/sub can drop messages and updates from different API processes can arrive out of order. Give PostgreSQL-backed `Dashboard` objects a committed per-object `revision` (a positive JavaScript-safe integer on creation, increasing with each committed update). `POST /classes/Dashboard`, `PUT /classes/Dashboard/:objectId`, and `GET /classes/Dashboard/:objectId` return that revision; a LiveQuery create or update carries the revision of the state it shows; a delete event carries a revision greater than the deleted state. A subscriber must not receive a lower revision after a higher one for the same object.

## What we need

- Writes through separate API processes share the same revision history, regardless of which process handles each write.
- If a writing API process loses its Redis link and dies immediately after its write commits, an existing subscriber sees the committed final value within 30 seconds, without restarting that subscriber.
- After a LiveQuery process restarts, a subscriber may supply `lastRevisions` on its `subscribe` frame: a map from object ID to last seen revision. Within 30 seconds it receives the final state of objects changed while offline, without replaying duplicate or older states.
- Events retain the existing `create`, `update`, `enter`, `leave`, and `delete` event names; an ACL-revocation `leave` does not expose the newly private value. Existing rows with no revision remain readable and receive a revision on their first update. Revision-less messages from old publishers (no `revision` field) still reach subscribers while no revisioned state of that object has been delivered; once one has, revision-less messages for that object are no longer delivered, so they cannot roll back a newer state.

## Keep working

Existing REST class creation and object reads, raw WebSocket `connect` / `subscribe` frames and create / update events; query-match changes still generate `enter` and `leave`.

## Setup

The application is at `/app`; build there with `npm run build`. PostgreSQL and Redis are installed locally. As `agent`, start them with `sudo service postgresql start` and `sudo service redis-server start`. PostgreSQL accepts `postgres:postgres` at localhost:5432 and Redis at localhost:6379. The solution runs against the PostgreSQL adapter and a standalone LiveQuery process; no Docker daemon is available inside the container.
