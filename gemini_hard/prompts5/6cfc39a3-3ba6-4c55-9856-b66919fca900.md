# nano: nineteen quiet regressions to diagnose without a test suite

I moved my realtime game backend onto a recent checkout of this framework — it is what brings my listening ports up, keeps track of who is playing, and carries calls from one running copy of my game to another — and almost everything I touch now answers slightly wrong. Nothing about my own code changed, so I wrote down exactly what I did and what came back. The repository has received 19 separate undocumented edits.

Bringing the thing up, and getting a call through to the code meant to answer it, both fail now. A setup that used to come up fine aborts before serving anything, complaining that an address it is supposed to advertise is empty. When one running copy passes a request along to another, the step that obtains the outbound link hands back nothing at all even after that link has been opened successfully, and the caller falls over on the nothing it was given. After I register an object so its request entry points become callable, those entry points are no longer recognised as such: calls that used to work are turned away as unknown, while functions never meant to be reachable get exposed. Work I ask the running game to do later does not settle either — I arrange a thousand one-shot callbacks a millisecond out, wait until well past the deadline, then let the periodic sweep run, and what that sweep does with the final outstanding entry is wrong, so the number of times my callback actually ran, and the sweep's own tally of outstanding and finishing work, never come back to where they started.

Keeping track of who has arrived is the worst of it. I make a named collection of live players and add a hundred of them from a hundred goroutines at once, and not one lands: the collection insists it has already been torn down, though I had just made it and never tore it down, and the number it holds stays at zero. Forcing entries in by another path and then asking the collection whether a player it is holding is one of its own gets me no, while players it has never seen are reported as its own. Two separate tallies of attached clients are each wrong in the same two ways: a freshly made one claims one client is already there before anything has arrived, and every arrival raises it by two, so after a batch of simultaneous arrivals the figure is roughly double what I attached plus the phantom it began with. One of those two also hands out identifiers in steps of two and begins the run one higher than it should, so the very first identifier it offers is already past where the sequence ought to start and after a hundred handouts the next it offers is nowhere near a hundred and one; the other's identifiers are at least all distinct.

Turning a value into bytes and reading it back no longer round-trips. Asking for the highest-numbered of the recognised frame kinds over an eleven-byte payload is refused with an error saying that kind is unsupported, while the lowest-numbered kind over the same payload is produced without complaint; numbers outside the recognised range are still turned away, as before. Handing a reader one complete frame and nothing else yields no frames at all — it gives a frame up only once extra bytes have piled up behind it, so a stream ending exactly on a frame boundary reads as empty. That same highest-numbered kind, once read back, is rejected for carrying a kind number outside the permitted range, though the lowest-numbered one of the same shape is accepted. For a call whose destination text appears in the shared shorthand table, the bytes written out carry the literal text where the numeric shorthand belongs and the shorthand where the text belongs, so what I read back names a destination bearing no relation to the one I sent. For a destination absent from that table, reading back picks the text up one byte too early, so it arrives shifted and the payload behind it no longer lines up; items carrying only an identifier and a payload, with no destination at all, still survive unchanged.

Checking my own code against a stand-in that records everything it was asked to send is no help either, because it misreports its own recording. Asking it for the identifier of the most recent item it was handed gives the wrong number — it does not actually track identifiers, and a freshly made one, which is meant to report the fixed value one, now reports something else. Asking for the most recently recorded reply gives back an earlier one rather than the one that just went out. And looking a recorded reply up by the destination it was sent to returns an item that went somewhere else entirely, while lookups for destinations that really were used come back empty.

It worked before a set of undocumented edits to the source of nano. The repository has
no test suite to run: finding out what is wrong, and convincing yourself you have fixed
it, is part of the task.

Restore the behavior described above.

Record the functions that contain those edits in `/app/rca.json`, one entry each:

```json
{
  "causes": [
    {
      "file": "benchmark/io/connector.go",
      "function": "enclosing_function_name"
    },
    {
      "file": "benchmark/io/connector.go",
      "function": "Type.method_name"
    }
  ]
}
```

`file` is the path of the file relative to the repository root, written exactly as it
appears in the tree. A file inside a directory keeps its directory prefix: the example
above is `benchmark/io/connector.go`, not `connector.go`.

`function` is the function name. A class or receiver prefix, written `Type.name`, is
accepted anywhere and is required when two functions in the same file share a name: the
bare name cannot tell them apart. When an edit sits inside a function nested in another
function, either name is accepted. Name every function one of the undocumented edits is
in, and only those. Where you wrote the fix does not matter: if you restored the behavior
from a caller or from a helper of your own, name the function the edit is in rather than
the one you wrote. If you suspect a function but found no edit in it, leave it out.


Before you edit any code, write your research and your plan to /app/RESEARCH_AND_PLANNING.md. Cover what you learned about the existing code and the constraints that shape the change, then how you intend to carry it out and why, including how you will know it works. Be concrete - the files, names and decisions specific to this codebase, not generalities. Complete the document before you touch any code: it is the record of your up-front investigation and decisions, and it should not be rewritten to match whatever the implementation turns into afterwards. Once it is done, implement the plan.
