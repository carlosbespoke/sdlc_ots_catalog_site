# Fenced processing for WebODM tasks

Our mapping clusters run multiple workers against several NodeODM processing nodes. We need a task to remain consistent when a worker pauses or a node disappears, without losing a user's commands or accepting results from an obsolete run.

Requirements:
- A committed task with images processes on an assigned node, reaches completion, and makes that node's downloaded assets available once.
- At most one current worker may change a task's processing status, progress, or assets. If one worker stops responding for more than 8 seconds, another can take over; a resumed worker cannot publish older results or release its successor's ownership. A current worker renews its ownership while active.
- `POST /api/projects/{project}/tasks/{task}/cancel`, then `/restart` retain their submission order, and the node receives each command once even with two active workers. Cancel changes the task to canceled; restart starts it again.
- `POST /api/projects/{project}/tasks/{task}/remove` removes the node task once and deletes the WebODM task, including when requested during processing. Workers still process a task through the existing `worker.tasks.process_task(<task id>)` Celery task: one call for a task that is not owned elsewhere applies its pending cancel, restart or remove without any other scheduling step. A `process_task` call that has returned leaves the task unowned, so the next call acts immediately; a task row with no current lease (for example inserted directly by an existing integration, even with status RUNNING) is not owned elsewhere either.
- If an automatically assigned processing node goes offline while its task is running, clear that assignment when the outage is detected; a subsequent processing pass assigns another available node. Cancel the former node task when it becomes reachable again, never accept its late completion, and publish only the new node's assets. Tasks assigned to a healthy node continue without migration.
- Keep task creation, retrieval, command responses, node discovery, and normal asset download compatible with existing clients; command requests return `{"success": true}`. Existing integrations also insert tasks using the current database columns; any new required task columns must allow those inserts (be nullable or have database-level defaults).

The repository is at `/app`. PostgreSQL/PostGIS and Redis are installed locally; start them as the `agent` user with `sudo service postgresql start` and `sudo service redis-server start`. The Django database uses `WO_DATABASE_HOST=localhost`, `WO_DATABASE_NAME=sd`, `WO_DATABASE_USER=app`, `WO_DATABASE_PASSWORD=app`; the broker is `WO_BROKER=redis://localhost:6379/0`. Initialize the schema with `python manage.py migrate --noinput`. NodeODM servers use their existing HTTP protocol. Docker is unavailable inside the agent container.
