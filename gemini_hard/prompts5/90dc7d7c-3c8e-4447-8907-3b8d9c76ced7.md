# keploy-regen

We moved to a fresh build of the tool we use to capture the traffic an application makes and replay it back later, and a great many small things came back wrong at once. Nothing about the observed applications changed and nothing about the protocols changed. The repository has received 30 separate undocumented edits. Below is everything we managed to pin down.

Trouble shows up before any traffic moves. Invoked with a settings file on disk and switches typed on the command line, almost every command dies while preparing where its diagnostic output should go, and it dies before noting which switches were actually present, so a value written in the file and a value typed on the command line can no longer be told apart. Putting interception in place outside a container hands back an all-zero v6 address where the v4-mapped loopback ::ffff:127.0.0.1 used to appear, both with v6 interception switched on and with it switched off but an explicit port override supplied; the port in the same answer is right either way. Handing a child process the list of configured side channels through a single environment string fails at both ends: a list holding exactly one channel encodes to the empty string and that channel is silently lost, an empty or absent list, which used to produce nothing at all, now produces a non-empty string, and parsing such a string back fails even on output the encoder beside it just produced. Switching off one of the built-in rules that let telemetry traffic bypass capture, by naming its identifier, does nothing whatsoever — the export route that rule covers still bypasses capture — though switching that one off does correctly leave a second telemetry route bypassing capture, as intended.

Once traffic is flowing through, secrets are no longer hidden. A form-encoded body of api_key=supersecretvalue123&token=<a real token>&order=42 comes back with both the secret and the token in plain text, only the harmless order=42 left alone as it always was; it now takes a suspicious name and a suspicious-looking value together before anything is masked, where either one used to be enough. A single call made over the multiplexed binary protocol no longer yields one finished exchange stamped with the moment its bytes arrived: the stamps on the outgoing side and on the reply are not the arrival times of the chunks that carried them, and in some runs no finished exchange comes out at all. Pushing captured response bytes through the hand-off queue and pulling them out again is wrong twice over — the time attributed to the piece just consumed is not that piece's own but runs ahead to the next one still waiting, and a chunk written and then closed just before the reader gets to it comes back empty instead of intact. Stall handling misfires in both directions: when a run is judged stalled the status and the fall-through decision still come back as they should, but the teardown callback the caller registered is never invoked at all, while a run that keeps signalling activity every twenty milliseconds against an eighty-millisecond budget is now judged stalled instead of finishing normally. Reporting of dropped byte chunks is inverted for two of the three reasons: a chunk refused because the per-link byte budget is used up no longer raises the one-time notice that capture has fallen out of step, and a chunk dropped during a deliberate pause — which is asked for at teardown — now raises that notice spuriously, while a chunk dropped under memory pressure still reports exactly once per link and does not repeat. Reading from a database link that immediately reports end-of-stream with no bytes no longer spends the bounded retry window before giving up; the call still ends in end-of-stream with an empty buffer, but the time it takes no longer lines up with the retry budget. Capturing two prepared-statement exchanges in quick succession on a database link, with a teardown right after the second, now yields at most one of them, and at least two independent edits feed that single symptom, so repairing one place does not bring it back. While a link is deliberately held before dispatch, a byte sent by the server side reaches the client application straight away instead of being withheld until the hold is released, and the parser side of the stream does not see it either.

Writing what was captured down and reading it back has its own set of failures. A capture session that ends cleanly reports the wrong summary figures: the tallies for items that could not be tied back to a case and for items that had to be dropped are both off, and the single case whose item could not be serialised is no longer withdrawn, so that case stays on disk with an incomplete pool while everything captured after the failure is still kept. Handing saved column values between processes in binary form is broken in both directions — writing a plain unsigned 16-bit value out fails outright, and reading a geometric circle value back in fails too, so whole captured exchanges disappear rather than being kept — and writing a full-text search vector out to a file and loading it again returns something that is no longer of the type that went in, though the other value shapes still survive the trip. Opening a saved suite whose settings file is missing hands back nothing useful: the secrets file lying beside it, holding token: abc123, never reaches the returned structure, and the same read against a truncated, unparsable settings file behaves the same way; two distinct things are wrong on that one path, one showing up with either state of the settings file and the other only when there is no settings file at all and an empty holder has to be conjured from nothing. Naming the next captured case in a folder that already holds one numbered three no longer produces four — the sequential naming either restarts or gives up with an error. Asking for body.request_id to be treated as noise never reaches the disk: the saved file has no noise section in it at all and nothing comes back on the next read, though an unrelated captured exchange in the same file is at least left untouched. Uploading a group of captured exchanges over the streaming endpoint is no longer taken as having worked — a success reply is read as a failure and the client retries the whole corpus through the older one-shot route it should never have needed — and when the receiver genuinely refuses the stream, the retry bookkeeping comes out wrong as well. Assembling a file path underneath a folder it is meant to stay inside now refuses perfectly ordinary inputs: a nested name such as assets/body.json and a bare dot are both rejected as though they had escaped, while absolute paths and ones containing .. are still rejected, as they should be.

Replaying against what was saved goes wrong as well. A body of {"id":"{{int .id}}"} used to lose the quotation marks around the non-string placeholder and come back as {"id":{{int .id}}}; it now comes back byte for byte unchanged, while a string placeholder still keeps its quotes as before, and separately, resolving a lone {{int .id}} against a saved integer of 123 now reports an error instead of handing back 123. Comparing a live call against a saved one under a profile that marks a URL parameter as free to change no longer matches: with cursor=999 live against cursor=1 saved and page=2 on both sides, the comparison is refused, even though the only parameter that differs is the one marked as changing freely. Reading back a single-column textual result from a database server's text protocol gives the wrong value — a result holding REPEATABLE-READ does not decode to that string, so a stand-in reply to a session-variable lookup no longer survives an encode-then-decode trip — and decoding a length-prefixed count from that same protocol gets the widest form wrong too, a nine-byte sequence beginning with 0xFE yielding both the wrong number and the wrong count of bytes consumed, while the one-, three- and four-byte forms, the null marker, an empty input and every truncated input behave exactly as before. Finally, when a replay finds nothing to match and a report is produced, the advice paragraph attached to it carries the wrong text: for a case where only a value inside the request body drifted, the advice fails to point at the request-body noise bucket and instead suggests a sub-command that does not exist, while everything else in the same report — the protocol, the summary line, the number of candidates considered, the closest candidate, and the listed field differences — is fine.

It worked before a set of undocumented edits to the source of keploy. The repository has
no test suite to run: finding out what is wrong, and convincing yourself you have fixed
it, is part of the task.

Restore the behavior described above.

Record the functions that contain those edits in `/app/rca.json`, one entry each:

```json
{
  "causes": [
    {
      "file": "pkg/agent/cgroup_mount_linux.go",
      "function": "enclosing_function_name"
    },
    {
      "file": "pkg/agent/cgroup_mount_linux.go",
      "function": "Type.method_name"
    }
  ]
}
```

`file` is the path of the file relative to the repository root, written exactly as it
appears in the tree. A file inside a directory keeps its directory prefix: the example
above is `pkg/agent/cgroup_mount_linux.go`, not `cgroup_mount_linux.go`.

`function` is the function name. A class or receiver prefix, written `Type.name`, is
accepted anywhere and is required when two functions in the same file share a name: the
bare name cannot tell them apart. When an edit sits inside a function nested in another
function, either name is accepted. Name every function one of the undocumented edits is
in, and only those. Where you wrote the fix does not matter: if you restored the behavior
from a caller or from a helper of your own, name the function the edit is in rather than
the one you wrote. If you suspect a function but found no edit in it, leave it out.


Before you edit any code, write your research and your plan to /app/RESEARCH_AND_PLANNING.md. Cover what you learned about the existing code and the constraints that shape the change, then how you intend to carry it out and why, including how you will know it works. Be concrete - the files, names and decisions specific to this codebase, not generalities. Complete the document before you touch any code: it is the record of your up-front investigation and decisions, and it should not be rewritten to match whatever the implementation turns into afterwards. Once it is done, implement the plan.
