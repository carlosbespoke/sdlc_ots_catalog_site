# Convergent SES engagement through SQS

Plunk operators need a reliable campaign view of what happened to each recipient, including SES engagement notifications. Extend the existing SES SNS integration with an SNS-subscribed SQS queue consumed by worker processes; the signed HTTP SNS endpoint remains available for existing installations.

## What we need

- Consume SES `Delivery`, `Open`, `Click`, `Bounce`, and `Complaint` notifications from `SES_EVENTS_QUEUE_URL`. SNS notification envelopes carry the SES JSON in `Message` and an SNS `MessageId`; notifications can be duplicated, reordered, or processed by two workers. Use the SES payload's `eventId` when present as the event identity, so publishing the same SES event in different SNS envelopes or sending it through both the queue and HTTP does not count it twice. Persist that identity and commit its effects before deleting an SQS message. An event already committed before a worker crash must have no second effect on redelivery, including any following delivery event.
- Include `X-SES-MESSAGE-TAGS: plunkEmailId=<stored email ID>` on outgoing SES messages and stamp their SES `messageId` on the email row. Match events by SES `mail.messageId` or the `mail.tags.plunkEmailId` value. Notifications arriving before the send stamps `messageId` remain durable and converge after the stamp, including tagged sends whose message ID is not yet available.
- An email's final status follows `COMPLAINED > BOUNCED > CLICKED > OPENED > DELIVERED > SENT`, regardless of delivery order. `opens` and `clicks` count distinct event identities, not deliveries. A transient bounce does not mark the email bounced or suppress a contact; a permanent bounce or complaint suppresses it once, clearing any snooze. The first open timestamp stays set when later opens arrive. Campaign `GET /campaigns/:id/stats` returns 200 with clicked, bounced, and complained counts consistent with persisted email timestamps. Queue-driven email projections and send stamping should converge within 45 seconds; an unmatched notification should be acknowledged from SQS within 30 seconds while remaining durably available for later matching.

## Keep working

- Signed `POST /webhooks/sns` accepts SNS `Notification` envelopes and shares queue idempotency, including when both paths see one event. Invalid signatures still return 403. The API `GET /health` still returns 200 with `status: "ok"`.

## Setup

Work under `/app`; build with `node .yarn/releases/yarn-4.9.1.cjs turbo build --filter=api...` from `/app`. PostgreSQL (`postgres:5432`), Redis (`redis:6379`), and LocalStack SES/SNS/SQS (`localstack:4566`) are available on the internal network. `DATABASE_URL`, `DIRECT_DATABASE_URL`, `REDIS_URL`, `AWS_ENDPOINT_URL`, and `SES_EVENTS_QUEUE_URL` are set. Use Prisma migrations for persisted schema changes; the worker starts from `apps/api/dist/jobs/worker.js`, the API from `apps/api/dist/app.js`.
