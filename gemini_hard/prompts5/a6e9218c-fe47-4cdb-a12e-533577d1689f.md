# code-generator-regen

The repository has received 30 separate undocumented edits. What follows is everything we noticed while using it; we have not looked for the cause of any of it.

We use this tool to read annotated declarations in a project and write helper source beside them, and we also rely on the helper source it wrote for us earlier. Both halves now misbehave. Nothing about the annotations changed, nothing about the values we hand in changed, and the same inputs that used to be handled correctly are handled wrongly now — in several places an input that used to be accepted is refused outright.

Telling it what to work on fails before any work starts. A well-formed input such as foo/bar/v1, passed on the command line, is reported back as unreadable. Supplying that same input flag more than once keeps only the last occurrence, and the defaults supplied alongside are still folded into the result. A two-segment input such as foo/v1 is cut in the wrong place, so the two names taken out of it are no longer foo and v1 as they used to be.

Asking which folders of declarations the duplication helpers will be written for gives three wrong answers. A folder carrying the whole-folder opt-in marker and holding one ordinary record is skipped and yields nothing. A folder with no such marker, but with a single type asking for helpers on its own, is skipped too. A folder carrying the marker but holding no types at all is now chosen, which would leave an empty file behind; the opt-out marker is still honoured and unmarked folders are still passed over. Asking instead which folders should have their wiring code written, a folder that declares its family name in the comment above it is no longer offered at all — neither on its own, nor when a marker belonging to some unrelated tool sits in the same comment block — while folders that opt out, or declare nothing, are passed over as always. Asking where a folder's type declarations should be read from now answers backwards: a folder with no such marker, and a folder naming one absolute location, are both refused with an error, while a location written relative to the current or the parent directory, and the same marker repeated twice with different values, are all accepted silently.

Checking a marker against what it declares has soured as well. A marker carrying a single unnamed value whose form matches the declaration is now rejected as wrong, though markers with named values still pass. When a value is left out entirely, the two messages are swapped: omitting the unnamed one yields the wording about a missing named parameter, and omitting a named one yields the wording about a missing required positional parameter. Turning decimal text into a whole number that may be negative refuses everything that ought to convert — zero, 100, -1, and the exact lowest and highest representable values at 8, 16, 32 and 64 bits — while out-of-range text, hexadecimal, leading zeros, floating point and whitespace are still refused. The companion conversion for numbers that may not be negative still handles 8, 16 and 64 bits, but asking for 32 now refuses even "0" and 4294967295, as though that width were not supported. And the complaint that insists a member carrying checks must also declare whether it is required now fires on a member reached by name whose lookup type is marked as not to be looked into, and on one where lookup type and held type are both so marked, even though either marking ought to silence it; marking only the held type still silences it.

Duplicating a record whose by-name member is declared through a named type no longer yields an independent value: change an entry in the original afterwards and the duplicate changes with it. Records built from plain lists, pointers, nested records and interfaces still duplicate independently. Separately, when we ask whether a type already supplies its own hand-written duplication method, a method taking nothing and returning exactly one result of the right type is judged the wrong shape, while a method returning two results is accepted as usable.

Handing a value in for checking brings back the wrong complaints in many places. A record whose true-or-false member holds the one value it must not hold, together with the pointer form and the named-type form beside it, no longer yields all three expected objections — the returned list comes back incomplete. Putting disallowed strings into a list whose element type is a named string type yields the wrong objections for that list, while the plain string list, the by-name collection of strings, its names and the nested records beside it are reported as before. In a list where one element is singled out by a combination of a text value, a number and a true-or-false value, the two forced failures land on the wrong element: the entry whose text differs from the one asked for is flagged instead of the exact match, though the variants of the same list that single an element out through a pointer, or through a mixture of forms, still flag the right one.

By-name members whose rules are switched by a feature gate fare no better. A record of text-to-text members no longer produces what it should when the gate is on — not for the member itself, not for its names, and not for its held values — although with the gate off the switched-off members are still reported. A record with two text-named members, one holding plain text and one holding a named text type, each entry carrying a forced failure, no longer produces the objection for each of the four entries.

Limits on how much a member may hold have drifted too. A by-name member required to hold at least ten entries is reported as holding too few when it holds exactly ten; nine entries are still reported and eleven still pass. A member whose type is a named list with a ceiling of zero elements now accepts a one-element value in silence, while the member that declares the same zero ceiling inline is still reported as holding too many.

Records whose inner parts decide what is allowed misreport in both directions. An all-zero record with two nested descriptive members whose inner rules depend on a feature gate no longer reports the switched-off inner member when the gate is off; with the gate on, the other inner member is still reported. A record carrying a selector member that names which of two alternatives may be filled goes wrong both ways: with the feature off, the expected refusal against the switched-off alternative's member does not come back, and with the feature on, the expected refusal against the switched-on alternative's member does not either. A second record of that shape, where the selector and its alternatives sit one level down inside a nested member, goes wrong for all four combinations we tried — including the two where the selector and the filled member agree and nothing at all should be reported. A parent whose nested member holds a pointer that may be left empty fails both ways: leaving it empty produces an objection where none is expected, and providing it no longer produces the single forced failure for the inner member. The parents with a required inner member, a forbidden one, one restricted on change and the two size-limited ones all behave as they did. Checking values of a type that is no more than a name for another named type produces results that no longer match the expectations recorded for those types.

Submitting a change to something that already exists goes wrong three more ways. Re-submitting a record unchanged, where the earlier state is identical and already carried the over-long lists, now reports those lists as too long; creating the same record fresh still reports them once. A record holding four by-name members — plain text values, named-type values, comparable record values and non-comparable record values — returns fewer than the four per-entry objections expected, though submitting it again unchanged is still accepted. And lowering any of the numbers that are meant never to decrease — the plain whole number, the 64-bit one, the never-negative one, the pointer one and the named-type one — no longer raises the objections it should; nor does dropping those members to zero, nor clearing a pointer member that may not be cleared. Creating a record with those same lowered numbers is still accepted, and a value beneath a declared floor is still reported.

It worked before a set of undocumented edits to the source of code-generator. The repository has
no test suite to run: finding out what is wrong, and convincing yourself you have fixed
it, is part of the task.

Restore the behavior described above.

Record the functions that contain those edits in `/app/rca.json`, one entry each:

```json
{
  "causes": [
    {
      "file": "cmd/client-gen/args/args.go",
      "function": "enclosing_function_name"
    },
    {
      "file": "cmd/client-gen/args/args.go",
      "function": "Type.method_name"
    }
  ]
}
```

`file` is the path of the file relative to the repository root, written exactly as it
appears in the tree. A file inside a directory keeps its directory prefix: the example
above is `cmd/client-gen/args/args.go`, not `args.go`.

`function` is the function name. A class or receiver prefix, written `Type.name`, is
accepted anywhere and is required when two functions in the same file share a name: the
bare name cannot tell them apart. When an edit sits inside a function nested in another
function, either name is accepted. Name every function one of the undocumented edits is
in, and only those. Where you wrote the fix does not matter: if you restored the behavior
from a caller or from a helper of your own, name the function the edit is in rather than
the one you wrote. If you suspect a function but found no edit in it, leave it out.
