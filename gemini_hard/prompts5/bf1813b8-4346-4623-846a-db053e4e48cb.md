# A research-article processing toolkit misbehaving across the board, without a test suite

I use this package to pull research articles in from the outside world, tidy them up, ask a model about them, and keep the results somewhere I can find them again. Since the last sync it gets a startling number of unrelated things wrong. The repository has received 30 separate undocumented edits. Below is everything I have been able to pin down from the outside.

Asking an item I have kept a simple question about itself now misfires. How much time has elapsed since its timestamp fails outright when I let the reference moment default, and when I pass a moment exactly three days after the item's timestamp I do not get three days back. The same items report their origin backwards: one I assembled by hand claims a model run produced it, and one carrying the record of the model run that produced it claims it was made by hand.

Getting material in from outside is worse in several ways. Tidying text taken out of a PDF now collapses only byte-identical repeated rows, so a row reading "Page 3" and the same words with two spaces in front and two behind survive as two rows instead of one. Scanning a parsed file for its section headings, where the file has an all-caps running header on every page, a contents listing first and numbered sections after, gets the detected headings, the identified contents page and the computed offset between printed and physical page numbers all wrong. Pulling an identifier out of a preprint web address yields nothing at all, for both the abstract-page form and the PDF form of a link whose identifier looks like 2401.12345, with or without a version suffix. Looking an article up by an identifier of the 10.1234/example.2024.001 form is nearly right — journal, publisher, authors, landing URL and publication date all map through — but the title comes back empty every time. Reading a syndication feed is broken outright in both common XML dialects: feed and entry titles, entry ids, links, timestamps and body HTML come back missing or taken from the wrong element. Two time-window checks have gone soft identically: requesting wire-service press releases for a window whose end instant equals its start begins doing work instead of complaining that the end must come after the start, though a start timestamp with no timezone is still refused up front as it should be, and assembling a settings object holding a start and an end for press items likewise accepts two equal endpoints rather than rejecting them with the same complaint.

Keeping things and finding them again is the worst of it. Splitting an already-parsed PDF into segments without supplying splitting settings of my own raises instead of falling back to defaults, so I cannot get as far as asking about the segments, and a request whose text is nothing but spaces is accepted rather than rejected. With no restriction to a particular article hierarchy, every entry belonging to one vanishes from the hit list, and restricting a request to a single hierarchy returns nothing at all; on a prebuilt collection where six entries should match a broad request I get far fewer. When I keep a multi-section article and then reword exactly one section, the wrong set of texts is embedded again — the single reworded section is not what gets recomputed. Asking about that same article confuses which hit stands for the item as a whole and which for its sections, and the matched text carried on each hit is not the text that was embedded for it. Hits that ought to name the segment they came from do not name it, so resolving a hit back to its segment fails. After shutting the collection and opening it again over the same file, the saved vectors are not brought back into play, so requests against the reopened one come back empty, and the guard that notices a stored row's text no longer agreeing with its hash stays silent when I edit that row behind its back. And shutting it down has no effect at all: afterwards a lookup by id keeps working instead of refusing on the grounds that it is shut.

Asking a model for things goes wrong in a whole cluster of ways. When the model refuses a rigid output format and the looser retry path takes over, both when I ask for evidence to be picked out of a section tree and when I ask for a section hierarchy to be drafted for an article, the second attempt goes out with a prompt that no longer carries the wording about the final output format, so the fallback never delivers a parsed answer even though the model happily replies. A refusal that has nothing to do with output formats — a quota-exhaustion complaint, say — is now treated as a format problem and quietly retried instead of being raised to me after one attempt. Asking for a section hierarchy for a PDF hands back the wrong kind of result entirely: a failure inside the drafting step never reaches me and what I get is not the tree I asked for, although the parse step does still run once per call. When a drafted hierarchy is judged too poor to use and the fallback ordering by source order takes over, the entries directly under the root are not the two ordered entries I expect. Asking for the text of a section id that really is present in the tree fails instead of returning that section's content. Summarising a long article by fanning groups of segments out to parallel workers dispatches the wrong groups, so with a group size of one over a three-segment article the number of worker calls no longer equals the number of segments, and a run given a very small time limit raises something other than the summarisation failure it used to raise. Producing a summary starting from a preprint identifier, with the download stubbed out to return a fixture PDF, no longer yields a record whose stored identifier, origin kind, title and content hash line up with what was downloaded. And asking for a readable description of a data shape is wrong twice over: for a shape accepting several alternative inputs the rendering no longer lists the alternatives, and for a plain builtin such as the integer one it returns something other than that builtin's textual repr.

Running work and watching it run is off as well. Putting five inputs through one pipeline with a concurrency limit of two reports progress wrongly: the running tally handed to my callback begins at one rather than zero and the last callback announces six completed out of five, though I am still called exactly five times. Handing a run exactly one observer object to receive lifecycle callbacks gets me something wrapped around it rather than the object I passed reaching whatever actually carries out the run, so identity checks against my own object fail. Declaring a pipeline function whose settings parameter is annotated as a plain integer is accepted at registration time instead of being refused as invalid. The roll-up of model-call statistics for a run no longer labels its per-step entries with the name of the enclosing agent, though the request count, the token totals and the recorded model names still match what I expect. And in a run with two overlapping calls of four and two seconds, the summed busy time no longer adds up to the sum of how long the two calls took.

It worked before a set of undocumented edits to the source of quant-mind. The repository has
no test suite to run: finding out what is wrong, and convincing yourself you have fixed
it, is part of the task.

Restore the behavior described above.

Record the functions that contain those edits in `/app/rca.json`, one entry each:

```json
{
  "causes": [
    {
      "file": "quantmind/configs/paper.py",
      "function": "enclosing_function_name"
    }
  ]
}
```

`function` is the function name. A class prefix is ignored if you include one. When an
edit sits inside a function nested in another function, either name is accepted. Name
every function one of the undocumented edits is in, and only those. Where you wrote the
fix does not matter: if you restored the behavior from a caller or from a helper of your
own, name the function the edit is in rather than the one you wrote. If you suspect a
function but found no edit in it, leave it out.


Before you edit any code, write your research and your plan to /app/RESEARCH_AND_PLANNING.md. Cover what you learned about the existing code and the constraints that shape the change, then how you intend to carry it out and why, including how you will know it works. Be concrete - the files, names and decisions specific to this codebase, not generalities. Complete the document before you touch any code: it is the record of your up-front investigation and decisions, and it should not be rewritten to match whatever the implementation turns into afterwards. Once it is done, implement the plan.
