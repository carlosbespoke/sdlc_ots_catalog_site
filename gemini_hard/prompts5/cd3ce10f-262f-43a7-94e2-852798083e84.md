# Versioned flag publication

We need v2 environment feature versions to support concurrent editing and scheduled releases without losing another editor's work or replaying a release. Implement this across the version API, version model and task processor in `/app/api`.

- A draft records the live version it was created from as `base_version` in its version-list representation. Publishing a draft makes its environment flag live and exposes the published version in the version list and `/api/v1/flags/` with `X-Environment-Key`.
- If another version has become live since the draft's base, publishing returns HTTP 409 with a `conflicts` list containing `environment_default` for the changed environment default; the rejected draft remains editable. `POST /api/v1/environments/{environment_id}/features/{feature_id}/versions/{uuid}/rebase/` explicitly rebases a draft. Publishing it afterward preserves both the draft's edits and independent fields changed by the other publisher (such as the default's enabled state and value). This holds across separate API processes.
- Scheduled version change sets become eligible at `live_from` and go live when a processor is available. Duplicate or crash-retried task deliveries across processors create at most one version per change set. A task that runs after a newer API publication must not silently revert that publication; rejecting the stale change set is acceptable. Keep publication history ordered by actual publication, including the version served to SDK clients; published versions expose their monotonically increasing `publish_sequence` in the version list.
- Each published version sends one `NEW_VERSION_PUBLISHED` environment webhook; duplicate scheduled deliveries do not send another. Keep the existing draft create, feature-state edit, publish, version list and SDK flag-read flows working; repeating publish for an already-published draft does not create another version.

The repository is in `/app`; run application commands from `/app/api`. A base-commit stale-draft reproducer is available at `/opt/flagsmith-reproduce.py` (`python /opt/flagsmith-reproduce.py` from `/app/api` after starting PostgreSQL). PostgreSQL runs locally with `DATABASE_URL=postgresql://app:app@localhost:5432/sd` and `DJANGO_SETTINGS_MODULE=app.settings.test` (`sudo service postgresql start`). The API and task processor can run as separate processes against that database; the container has no Docker daemon or network access.
