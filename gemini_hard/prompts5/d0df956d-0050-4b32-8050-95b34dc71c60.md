# napalm: diagnosing broken drivers and helpers without a test suite

Everyday work through this library — pointing it at a piece of network equipment, asking that equipment what state it is in, and pushing settings at it — now comes back with wrong answers or fails outright. The repository has received 20 separate undocumented edits. The equipment did not change and neither did the programs asking it things, many kinds of gear are affected, and in a couple of places one question I ask is wrong in two independent ways at once.

Even with no equipment involved, turning text a device printed into something a program can use is wrong. Handing over a human-readable running-time phrase and asking for the equivalent plain number gives totals that do not match the input, for every style of phrase: the comma-separated words ("24 days, 11 hours, 25 minutes", "1 year, 2 weeks, 5 minutes"), the days-plus-clock shorthand ("114 days, 22:27:32") and the compact letter run ("7w6d5h4m3s"). Handing over a small block of aligned text — a heading, a line of dashes, a line of data — along with its column widths no longer yields one group of column texts per line, but a far longer run of nearly empty groups, as though the input had been chewed through a character at a time.

Rehearsing offline against a stand-in fed from files of recorded replies is unusable, because the sequencing runs one slot too far. The first ask takes the recording that follows the first rather than the first itself, the next takes the one after that, and the first recording is never served, so a query that should hand back the first canned reply hands back the wrong one or reports nothing available, and the message saying where to drop recorded data names a sequence number one higher than the file actually sought — the same skew on replayed command output, on a load, compare and commit sequence, and on a replayed failure. Argument checking on those stand-in operations is inverted too: a keyword name the operation does not accept is no longer refused with the expected complaint about an unexpected keyword argument, and instead slips through to fail later in some unrelated way, if at all.

Asking equipment which addresses sit on its ports is wrong on every kind of gear I tried, differently each time. On gear queried over HTTP the per-port listing drops the IPv6 part of the answer entirely as soon as a port carries IPv6, whether the port has one IPv6 address, several, or the ordinary mixture of both families. On gear queried over a text command session the same listing loses the IPv4 part for ports that do have IPv4 addressing, so addresses the equipment reported are missing. On gear queried over the structured remote-settings protocol it omits the port's primary IPv4 address, and over that same protocol asking for the learned hardware-address forwarding listing aborts with a type error rather than returning anything. Asking what the far end of each link says it is, in the fuller form of that question, reports the wrong remote chassis identifier across several sets of equipment output, because the tidying-up that belongs on hardware-address-shaped identifiers is applied to exactly the wrong set of link partners; the short form is fine.

Asking about the sessions a device holds with its peers goes wrong in several separate ways. Over a text command session the per-peer rows are misread, so entries arrive with fields taken from the wrong place or go missing entirely — on plain IPv4 output, on output where a peer is down, and on layer-2 overlay output — and on that same gear a section for one address family or one isolated instance whose overview is a heading line with no peers beneath it is no longer recognised as empty, which pollutes the answer for setups with several isolated instances and IPv6 families. On other gear the peer listing records the wrong remote peer address for peers whose connection runs over IPv4. The peer settings a device reports come back with the per-address-family cap-on-advertised-prefixes options and the ordinary peer and group options sorted into each other's slots, in the plain case and in the next-hop-self case alike. And looking up how a particular destination is reached returns wrong extra properties for destinations learned from a peer, across several equipment output styles, in exact and non-exact lookups and including the default forwarding instance.

Asking a device to run something and report back fares no better. Following the path to a destination hop by hop gives nothing usable: the per-hop attempt structure that should come back is empty or nonsensical, for both the normal and the alternative output styles and on gear reached either way. Repeated reachability measurements a device collects against a target come back with wrong figures, the per-test numbers not matching what the equipment printed, as if a value were read from the wrong position in the samples.

Everything that travels over HTTP is affected twice over. The endpoint address built for a device is malformed: a plain IPv4 device address ends up wrapped in square brackets and a literal IPv6 one ends up without them, so neither result reads back as the address passed in plus the chosen port, and both front ends suffer for it. Reply handling on that transport is inverted as well — ordinary successful asks, whether for the equipment's name, for its release identity in structured or raw form, for a list of show commands, or for pushing one or a list of setting commands, now all blow up complaining of an invalid status code on the POST, while an ask that really does come back with a failing status no longer produces that complaint, and errors reported against individual commands inside an otherwise accepted reply stop being surfaced as command errors.

Two remaining troubles are about failures and about comparisons. Error paths from gear reached over the low-level session no longer raise what they should: an attempt to take an exclusive hold on a settings store that is already held does not surface as the specific already-held failure, and a remote invocation that never receives a usable reply does not surface as a timeout. In both cases something else goes wrong first while the failure is being built, so what arrives is a mangled error rather than the specific one. Finally, comparing two release identifiers is unreliable at the sameness end: an identifier compared against an identical copy of itself is reported as different, and "no greater than" against itself likewise comes out false, while strict ordering between two genuinely different releases is still right in both directions.

It worked before a set of undocumented edits to the source of napalm. The repository has
no test suite to run: finding out what is wrong, and convincing yourself you have fixed
it, is part of the task.

Restore the behavior described above.

Record the functions that contain those edits in `/app/rca.json`, one entry each:

```json
{
  "causes": [
    {
      "file": "napalm/base/base.py",
      "function": "enclosing_function_name"
    }
  ]
}
```

`function` is the function name. A class prefix is ignored if you include one. When an
edit sits inside a function nested in another function, either name is accepted. Name
every function one of the undocumented edits is in, and only those. Where you wrote the
fix does not matter: if you restored the behavior from a caller or from a helper of your
own, name the function the edit is in rather than the one you wrote. If you suspect a
function but found no edit in it, leave it out.
