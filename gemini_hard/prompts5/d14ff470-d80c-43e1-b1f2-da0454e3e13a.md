# Goal

Support durable deletion of published local vector datasets in `/app`. GeoNode, GeoServer, GeoFence and PostGIS must converge on deletion even when a dependency or cleanup worker fails; an older deletion must not erase a subsequent upload with the same name. The seeded failure can be reproduced from `/app` with `python reproduce_dataset_delete.py` after the application and datastore migrations; the script holds background dispatch to inspect the DELETE acceptance boundary.

# Requirements

1. `DELETE /api/v2/resources/{id}/delete` accepts a local vector deletion with HTTP 202 and `status: "deleting"`, hides the resource (GET returns 403 or 404), and retains its deletion intent and external identities. `GET /api/v2/resource-service/execution-status/{uuid}`, where `{uuid}` is the deleted dataset's resource UUID, returns HTTP 200 with `status: "deleting"` until all cleanup finishes, then returns 404.
2. Before destructive cleanup, stop both anonymous and owner WFS GetFeature access as soon as GeoServer is reachable. After completion, the former GeoServer layer, feature type, unused store and non-shared style, GeoFence rules, and PostGIS table are gone; the store is removed with GeoServer REST `DELETE /rest/workspaces/geonode/datastores/{name}.json`.
3. Accept deletion while GeoServer is unavailable for 60 seconds; recover without another DELETE or operator action, with no successful WFS request after GeoServer recovers. Complete cleanup within 120 seconds after GeoServer recovers or a killed worker restarts (within 90 seconds when a blocked cleanup call is released). Continue unfinished cleanup after a worker SIGKILL following layer removal but before store and table removal; repeated work leaves the same final result.
4. A GeoJSON upload via `POST /uploads/upload` during pending deletion either returns HTTP 201 and succeeds intact after the old cleanup finishes or fails atomically with HTTP 400 or 409 and a clear `name pending deletion` error. If the upload returns 201, the old deletion still finishes (its execution status returns 404) without touching the replacement, which keeps its GeoServer publication, rules, styles, table and WFS features even if old work runs again.
5. `python manage.py sweep_deleted_datasets` reports older orphaned vector publications (catalog entries and PostGIS tables with no GeoNode dataset); `python manage.py sweep_deleted_datasets --remove` reclaims them while leaving live vector publications untouched.

# Keep compatible

A live resource remains readable through `GET /api/v2/resources/{id}`, and its GeoServer feature type and PostGIS table remain present. An unknown UUID still returns 404 at `GET /api/v2/resource-service/execution-status/{uuid}`. Other resource types are outside this local vector deletion change.

# Environment

PostgreSQL/PostGIS, Redis and GeoServer with GeoFence are available through the compose service hostnames. Run Django commands from `/app` using `python manage.py ...`; the standard validation command is `bash /app/test.sh new` from `/app` when the verifier patch is installed. The solver container cannot run Docker.
