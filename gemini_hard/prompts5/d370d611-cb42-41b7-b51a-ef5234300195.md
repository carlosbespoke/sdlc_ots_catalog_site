# A multi-syntax assembler without a test suite

The repository has received 30 separate undocumented edits.

This program takes assembly source, written in either of the two input dialects it accepts, and emits machine code for a range of targets and output flavours, and it now gets a long list of things wrong. Source that used to assemble now assembles to different bytes, source that used to be accepted is turned away outright, and output that used to describe what was assembled no longer does.

Trouble starts before any source is read. Passing an option the program itself accepts prints a warning claiming the option is unrecognized and bumps the warning count, so an entirely ordinary command line ends with complaints attached to it. Breaking a backslash-separated location into the part naming the directory and the part naming the item puts the boundary between the two in the wrong place, and joining a directory onto a relative location made of such pieces gives a result whose separator sits in the wrong place.

Reading the text of a source has become unreliable in its own right. A quoted string containing hexadecimal escapes comes back with any escape whose digits include letters turned into characters other than the ones written. A constant whose magnitude is too small to be represented in the requested floating-point size is converted with no complaint about the conversion, and constants of that size assemble to wrong bytes.

Lines that are plainly legal are now refused. In source that writes memory operands inside brackets, statements are rejected with a syntax error quoting a token the line genuinely contains, several of the accepted bracketed address forms are refused in the same manner, and input that should have assembled while reporting a warning instead stops with a hard error and no output at all. Where the source uses the prefixed-register notation instead, expressions built with certain operators fail with the same spurious syntax error on a token that is present, words mixing letters and digits are cut short at the first digit so the text reaching assembly is not the text written, and some lines lose one further character before assembly and produce wrong bytes. In the dialect that compares symbol names without regard to letter case, a reference written in a different case from its definition no longer resolves and the symbol is reported undefined.

Turning statements into bytes goes wrong in several directions at once. An instruction whose operand must be one particular control register now accepts any register in that position and encodes to the wrong bytes rather than being reported as an unsupported combination of operands. A memory reference that uses a vector register as its index also encodes wrongly. Padding emitted to bring code up to an alignment boundary is filled with multi-byte do-nothing patterns belonging to the wrong processor flavour. A declaration of initialised storage that carries a repeat count occupies only a single copy's worth of room, so everything placed after it lands at the wrong offset, and asking for the raw contents of something stored on disk to be dropped into the output adds no length at all, leaving the result short by that amount and displacing what follows.

Asking for a plain headerless image, from source whose sections are placed relative to one another, never reaches the point of writing anything out: it gives up while a section's placement is being resolved. Where such a layout does get written, sections that were never given a start address are treated as though one had been supplied, so the image comes out with sections at wrong addresses.

What finally gets emitted is wrong in a different way for nearly every output flavour that can be asked for. Object output for the 64-bit target that uses 32-bit pointers begins with header bytes, and offsets derived from them, that do not describe the rest of what follows. Section-relative references in 32-bit Windows object output are recorded under the relocation kind meant for plain absolute addresses. Source using the 64-bit Windows exception-unwind directives produces unwind data whose stated total length falls short of the entries written into it, and the bytes of some unwind entries carry a wrong number in their leading field. Output for 64-bit Darwin targets writes a one where a zero belongs in one of its fields, so the result does not match the assembled content. Requesting the relocatable dynamic object output always ends in a failure to rewind the output being written, with nothing produced. In the extended dynamic object output, symbols defined inside a section come out with the wrong section number and without the offset of the place they were defined, while other runs stop with an internal error about a section not being understood, and declaring a section with attributes in that same output yields section records that do not reflect what was written. Declaring a section whose attributes are given as a string of flag letters produces a section carrying permissions that none of the letters asked for, and those permissions are what is recorded in the output.

Asking for debugging information fares no better. Debugging data produced for 64-bit output refers to the wrong part of what was emitted, so what is recorded does not describe the program. The directive that records a source location ignores the flag saying whether the location begins a statement and stores the value given for another of its parameters in that place instead. One of the selectable debugging output formats always announces zero entries in the summary it writes, however many entries it goes on to emit.

It worked before a set of undocumented edits to the source of yasm. This checkout has
no test suite.

Restore the behavior described above.

Record the functions that contain those edits in `/app/rca.json`, one entry each:

```json
{
  "causes": [
    {
      "file": "/workspace/repo/frontends/yasm/yasm-plugin.c",
      "function": "enclosing_function_name"
    },
    {
      "file": "/workspace/repo/frontends/yasm/yasm-plugin.c",
      "function": "Type.method_name"
    }
  ]
}
```

Each entry is an object with a `file` and a `function`; anything in `causes` that is not
an object counts as a wrong entry. `file` is the absolute path of the file, in the
repository checked out at `/workspace/repo`, written exactly as it appears in the tree.
A file inside a directory keeps its directories: the example above is
`/workspace/repo/frontends/yasm/yasm-plugin.c`, not `yasm-plugin.c`. The same path
relative to the repository root, such as `frontends/yasm/yasm-plugin.c`, is accepted
too. A path outside `/workspace/repo`, or a path with a `..` segment, does not name a
file in the repository and counts as a wrong entry.

`function` is the function name. A class or receiver prefix, written `Type.name`, is
accepted anywhere and is required when two functions in the same file share a name, since
the bare name cannot tell them apart; a function with no class or receiver has no prefix to
add, and its bare name names it. When an edit sits inside a function nested in another
function, name the innermost function that directly contains it; the enclosing function's
name is accepted in its place, except when that function holds another edit too, where only
the innermost names tell them apart. Name every function one of the undocumented edits is
in, and only those, once each: an entry for an edit another entry already names, such as
the same function written twice, with and without its prefix, or by its enclosing function
beside its innermost one, counts as a wrong entry. Where you wrote the fix does not matter:
if you restored the behavior from a caller or from a helper of your own, name the function
the edit is in rather than the one you wrote. If you suspect a function but found no edit
in it, leave it out.
