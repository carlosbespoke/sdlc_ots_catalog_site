Squidex content-change webhook rules currently enqueue a flow job before the event consumer's checkpoint is committed. A worker crash can replay the change and send it again; two workers can enqueue the same change; a temporary worker-side database failure can strand the consumer. Make content-change webhook delivery replay-safe across these conditions without changing the existing content API, rule API or webhook payload.

For each matching rule, a content create, update or delete through `/api/content/{app}/{schema}/` must result in one successful webhook delivery, in change order per content item. Each (change, rule) has a distinct nonempty `X-Delivery-Id`; retries of the same delivery retain that ID. If a receiver responds 503, its next successful attempt must have the same ID, original payload and `X-Signature`. A worker killed after enqueue but before the `RuleEnqueuer` checkpoint is saved must not generate another delivery on replay, including when new content is written while the worker is down. Two workers sharing PostgreSQL must not generate duplicate deliveries. API nodes must keep accepting content changes while the worker's database role cannot log in for 20 seconds; every change must reach the receiver within 20 seconds of restored access, without duplicates. An event consumer must be active in at most one worker process at a time and recover from a transient failure without losing events.

Keep webhook event names, payloads and optional `X-Signature` unchanged. Rule creation and listing at `/api/apps/{app}/rules`, consumer listing at `/api/event-consumers`, and `RuleEnqueuer` stop/start at `/api/event-consumers/RuleEnqueuer/{stop|start}` must continue to work. The deliverable is source changes under `/app/backend`; build with `cd /app && dotnet build backend/src/Squidex -c Debug -p:NuGetAudit=false`. This environment uses PostgreSQL for store, event store and messaging (`STORE__TYPE=Sql`, `EVENTSTORE__TYPE=Sql`, `MESSAGING__TYPE=Sql`); start it as the `agent` user with `sudo service postgresql start`. PostgreSQL's local admin role is `postgres` with password `postgres`; Docker is not available inside the container.
