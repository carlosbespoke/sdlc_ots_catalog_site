The workbench cluster at `/app/samples/extensions/workbench/Elsa.Server.Web` uses a shared PostgreSQL database and Redis locks, but MassTransit's transport is process-local. A successful `POST /elsa/api/workflow-definitions/{definitionId}/dispatch` can leave a Running instance stranded when its accepting process dies before execution; a failed heartbeat can also make an active instance look abandoned, and a node that has lost its lock keeps executing. Make accepted dispatches recoverable and make sure an instance only ever advances on one node. Keep the existing API response shape and single-node behaviour.

With three independently running nodes, 50 accepted dispatches each finish with exactly one observable execution. If the accepting process dies right after responding and before execution begins, another node finishes that instance once within 45 seconds. This includes dispatches with a caller-supplied `instanceId` while the Redis execution lock `workflow-instance:{instanceId}` is already held: accept and durably record the dispatch, then execute it once that lock is free. If a node dies mid-execution, another resumes the instance within 45 seconds without repeating completed steps, and the same holds when that node dies mid-step too. Ten interrupted instances recovered concurrently by three nodes each run on only one node.

A node that freezes mid-step (stops running without exiting) is taken over: another node finishes the instance within 90 seconds of the freeze, and once the frozen node resumes it runs no further step of that instance and leaves its persisted state alone. If Redis loses all of its data and is down for 30 seconds while instances are mid-step on several nodes, dispatches sent meanwhile are still accepted, and every running or newly accepted instance finishes within 60 seconds of Redis returning, each later step running once. A 20-second PostgreSQL interruption during a 40-second step must not make a second node replay prior steps; after connectivity returns, the workflow finishes once. If one PostgreSQL heartbeat write fails during a running step, heartbeat updates resume within 29 seconds while that step is still active. If Redis revokes an active instance lock during a 40-second step, the former owner does not run the next step, even when that step eventually returns. Existing `dispatch`, workflow-instance `GET`, `execute` and cancel routes and responses stay compatible.

Build with `dotnet build /app/samples/extensions/workbench/Elsa.Server.Web/Elsa.Server.Web.csproj -f net10.0 -p:NuGetAudit=false` from `/app`. PostgreSQL and Redis are local services (`sudo service postgresql start; sudo service redis-server start`); use `DatabaseProvider=PostgreSql`, `Runtime__DistributedLocking__Provider=Redis` and the host's `ConnectionStrings__PostgreSql` and `ConnectionStrings__Redis` settings. The image has no Docker daemon; suites requiring Testcontainers cannot run there.
