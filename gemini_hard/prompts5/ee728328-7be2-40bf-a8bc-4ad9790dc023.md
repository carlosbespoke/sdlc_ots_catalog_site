# Connector-scoped SCIM provisioning

Add a SCIM 2.0 provisioning surface to enterprise SSO connectors so an IdP can manage Logto users and organization-role groups across multiple core instances.

- Add management API routes under `/api/scim/v2/connectors/:connectorId`: `POST /Users`, `GET /Users/:id`, `PATCH /Users/:id`, `DELETE /Users/:id`, `POST /Groups`, `GET /Groups/:id`, and `PATCH /Groups/:id`. Unknown connectors and resources return 4xx. User IDs are Logto user IDs; group IDs are connector-scoped external IDs. Return JSON resources with `externalId` and `meta.version`; include an `ETag` header on resource reads, creates and PATCH responses. Successful creates return 201, user deletion returns 204.
- Repeated user creates with the same `externalId` on one connector resolve to one Logto user, even through separate instances; repeating a group create keeps its existing membership. A user create with only `externalId` (no `userName` or `emails`) is valid. A first create with a verified email matching an existing user links that user; an unverified email with the same address does not claim that existing identity. Emails are supplied as `emails: [{"value":"<email>","verified":true}]` (or `false` for unverified). External IDs on different connectors remain independent.
- Groups carry `externalId`, `displayName`, `organizationId`, `organizationRoleId`, and `members` (`[{"value":"<user id>"}]`). Membership changes update the corresponding organization role. Apply SCIM PATCH `Operations` for the `members` path in their given order (`add`, `replace`, `remove`), including back-to-back requests through separate instances whose first response precedes the second request. A response and subsequent read reflect the final membership.
- User PATCH `Operations` can replace `active` with a boolean. When `active` becomes false, remove that user's persisted refresh tokens, access tokens, sessions and grants before returning success; after deletion, a refresh token previously usable on another instance is rejected there and the user is suspended. Preserve existing management user creation, connector creation, and organization-role membership APIs.

The checkout is `/app`. A reproducible cross-instance create workload is at `/home/agent/scim-repro.cjs` (`node /home/agent/scim-repro.cjs` after starting services); it should complete with one Logto user for the repeated external ID. PostgreSQL (`postgres://app:app@localhost:5432/logto`) and Redis (`redis://localhost:6379`) are installed locally; start them with `sudo service postgresql start` and `sudo service redis-server start`. Run core from `/app/packages/core` with `DB_URL` and `REDIS_URL` set, `NODE_ENV=development`, and unique `PORT` and `ADMIN_PORT` for each instance. Build and type-check offline with `pnpm --filter @logto/core build` and `pnpm --filter @logto/core check` from `/app`. Grading rebuilds only `@logto/core` this way and runs it against the already-seeded `logto` database as role `app` (which owns that database): other workspace packages such as `@logto/schemas` are not rebuilt and no alteration or seed command runs, so core must not depend on new `@logto/schemas` exports and must create any new tables it needs itself (the seeded tables belong to another role and cannot be altered).
