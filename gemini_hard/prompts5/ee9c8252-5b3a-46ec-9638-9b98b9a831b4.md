# Lefthook misbehaves from hook wiring to file narrowing, without a test suite

The repository has received 29 separate undocumented edits.

This tool wires per-project hooks into a working copy and then, when one of those hooks fires, works out what has to happen and makes it happen. Nothing about the projects it is pointed at changed and nothing about the yaml declaring the work changed, yet the same projects that used to be set up and served correctly are now handled wrongly, and in several places work that should have happened is skipped or fails outright.

Setting the hooks up in a project whose yaml also declares hooks for AI assistants now stops halfway through: two of the assistant files it should generate never appear, the fingerprint it should leave behind is missing, and when a provider is dropped from the yaml the file written for that provider earlier stays behind. Doing the same wiring where one such assistant file is in place beforehand goes wrong differently — the managed entry is never merged into it and the file comes back byte for byte as the user left it — though generating that same file from nothing, when none is there, works. An assistant file whose entries sit directly under the event name rather than in groups has the same trouble when one is in place beforehand, while the one that is rewritten wholesale comes out as asked. Re-syncing a project whose yaml carries an old modification time but unchanged contents now decides the hooks are out of date and writes two hook files that should have been left absent; with a fresh timestamp the same unchanged project is still left alone. Refreshing hook definitions that come from another project over the network at a pinned revision gives up right after the clone: the fetch and the switch to that revision never happen, the stale directory of the older revision is never dropped, and the call ends in an error, while an unpinned source clones as before.

Taking the tool's own assistant entries back out again leaves both shapes of file wrong. Where an event holds groups that each hold entries, the file that comes back is not the one holding only the hand-written entry, and the shape that lists entries directly under the event ends up wrong in the same way. The one file that is deleted outright rather than edited does vanish as it should.

Firing a hook in a project that asks for a minimum release of the tool takes that requirement backwards: a yaml demanding something far newer than what is in use goes ahead quietly, and a yaml demanding something older aborts with an error. The comparison itself also trips on a leading v — needing 1.0.0 while on v1.0.1 is refused as not covered, though needing v1.0.0 while on 1.0.1 is accepted.

Deciding which declared pieces of work fire, and in what order, goes wrong in several ways. A hook whose pieces are piped one after another cuts the sequence short and comes back without complaint: such a hook containing a piece that does not succeed no longer yields any error to the caller. A hook with parallel pieces of which some are marked interactive loses track of one of them, so the successes and failures handed back do not match what was declared. Rules keyed on the name the working copy currently sits on stopped matching at all: with HEAD pointing at main, a rule that skips main does its work anyway and a rule limited to main does nothing, while rules keyed on a merge or rebase being underway still behave. A rule that decides by invoking a shell snippet is ignored as well: a piece carrying such a rule is no longer skipped when the snippet succeeds, while plain true/false rules and name patterns work. Pieces narrowed by a file pattern are picked by the opposite rule — with only a markdown file changed, the piece limited to *.md was dropped and the piece limited to *.txt, which matched nothing, was invoked in its place. The order in which pieces taken from shell files in the source directory get queued is wrong when only some of them carry a priority: the ones with a priority no longer come ahead of the ones without, and names like 2_test.sh and 10_test.sh no longer keep their numeric order among the rest. Pieces written inline under names in the yaml are misordered as well: one whose priority is 1 is placed as though it had none.

Working out which of the changed files a piece of work should see is off too. Narrowing a list by pattern turned case sensitive: *.rb no longer picks 2.RB out of a list and *.rb? no longer picks 1.rBs, though lowercase names in the same list still match. Exclusion patterns are off as well: excluding *.a, *.b and *.cn from four files leaves more than the single file that should survive, and excluding **/*.rb with the default matcher yields a set that does not follow the patterns given. Judging whether a file's opening bytes are text now calls ordinary text binary — the opening bytes of a plain toml file and of a markdown document are both judged non-text — although a real binary blob is still judged non-text. When a piece's own settings are folded into the narrowing it will use, its glob list, environment pairs, custom listing line, root directory and inherited file-type entries all arrive intact, but a single exclusion pattern written on that piece vanishes. Gathering the files for a push from a name with no upstream yet, where the fallback is a listing of all tracked paths, hands back the wrong set: what comes out is not just the one listed path that really exists in the working tree, while a push where a fallback is found still yields the changed file it should.

Building the text that finally gets invoked is wrong in three ways. A placeholder wrapped in single quotes loses its contents: echoing a single-quoted placeholder standing for the staged files over two staged files yields two pairs of empty quotes instead of the quoted names, while the same placeholder in double quotes substitutes fine. Mixing a user-defined template with that staged-file placeholder in one line also produces the wrong text — a file name containing spaces no longer comes out quoted, and the user-defined fragment no longer comes through verbatim. When an argument list is too long for a single invocation of the underlying tool and has to be split, the pieces are wrong: with a tight length limit and four arguments, the output repeats some arguments and leaves others out instead of showing each once.

Invoking the work and handling its streams fails as well. A piece that takes its input from the standard input stream fails outright: piping a line of text into cat ends in an error and the text never reaches the captured output. Several interactive pieces started at once likewise end in errors, and the buffer each one wrote to no longer holds all the lines it printed. An input stream meant to be replayable is not: consuming it to the end a second and a third time does not give back the same bytes the first pass gave. The stand-in stream that should be permanently empty yields a byte of content, so consuming it to the end returns a byte where it should return nothing.

Asking the tool about itself is wrong too. Asking it to print its own release string gives the two forms swapped — the plain request comes back with the build commit tacked on and the detailed request comes back without it. Asking it to replace its own binary with the latest release now gives up saying no digest list was published even when the release publishes one; a release whose digest genuinely mismatches no longer yields the mismatch complaint, and the binary on disk is never replaced.

It worked before a set of undocumented edits to the source of lefthook. The repository has
no test suite to run: finding out what is wrong, and convincing yourself you have fixed
it, is part of the task.

Restore the behavior described above.

Record the functions that contain those edits in `/app/rca.json`, one entry each:

```json
{
  "causes": [
    {
      "file": "internal/command/add.go",
      "function": "enclosing_function_name"
    }
  ]
}
```

`function` is the function name. A class prefix is ignored if you include one. When an
edit sits inside a function nested in another function, either name is accepted. Name
every function one of the undocumented edits is in, and only those. Where you wrote the
fix does not matter: if you restored the behavior from a caller or from a helper of your
own, name the function the edit is in rather than the one you wrote. If you suspect a
function but found no edit in it, leave it out.


Before you edit any code, write your research and your plan to /app/RESEARCH_AND_PLANNING.md. Cover what you learned about the existing code and the constraints that shape the change, then how you intend to carry it out and why, including how you will know it works. Be concrete - the files, names and decisions specific to this codebase, not generalities. Complete the document before you touch any code: it is the record of your up-front investigation and decisions, and it should not be rewritten to match whatever the implementation turns into afterwards. Once it is done, implement the plan.
