# Bounded-staleness registry snapshots

Support coherent, bounded-fresh registry snapshots for SQL-backed feature-serving fleets. Give SQL-backed feature servers a committed registry revision and a positive `feature_server.registry_staleness_seconds` setting.

## What we need

- Each SQL registry change committed by `feast apply` or the registry server advances a monotonically increasing revision; a rolled-back change does not advance it. Keep that revision in a `registry_revision` table holding one row with `id = 1` and an integer `revision` column, updated in the same transaction as the registry change it counts. The registry server makes its current revision and registry available through a public `GetRegistrySnapshot` gRPC call. The call takes `google.protobuf.Empty` and returns `feast.core.Registry`, with the committed revision encoded as a decimal integer string in its existing `version_id` field.
- With `feature_server.registry_staleness_seconds: 3` (or `FEAST_REGISTRY_STALENESS_SECONDS=3` when the YAML setting is absent), a newly applied feature view becomes readable on each of two running feature servers within 15 seconds, without restarting them. Each online request resolves its feature service and feature view from one coherent registry snapshot. During a feature rename, every online request succeeds with HTTP 200 and reflects either the old or the new schema, never both.
- After the budget, a deleted feature view no longer accepts `/push` writes on either server; schema changes likewise stop accepting pushes using the old schema. A revoked `READ_ONLINE` permission on a feature service denies the affected user on both servers within 15 seconds.
- If PostgreSQL is unreachable for longer than the budget, online requests and pushes fail with HTTP 503 rather than using unverified metadata. After connectivity returns, normal responses resume within 20 seconds.

## Keep working

- `/get-online-features` returns its existing JSON `metadata.feature_names`, `results` and statuses for unchanged SQL metadata; `/push` still accepts valid online writes. File-backed registries still serve online requests without SQL version checks. The existing registry-server `Proto` RPC remains available, and `/health` remains HTTP 200 even during a registry outage.

## Setup

The repository is at `/app`. PostgreSQL is installed locally; start it with `sudo service postgresql start` as `agent`. SQL registry URLs use `postgresql+psycopg://app:app@localhost:5432/sd` in the integration setup. Implement the change in Feast's registry, registry-server and feature-server code; use the normal Feast CLI and HTTP/gRPC interfaces to check it.
