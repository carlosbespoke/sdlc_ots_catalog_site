Our simulation service is moving from the JVM to Go, and the last Java dependency we still lean on is the core module of Apache Commons RNG. I need a Go port of `commons-rng-core`. The Java source is in `/app/java_reference/`. The Go package is already laid out in `/app/port/`: every type and function our code calls is there with its final signature, but the bodies are stubs. Could you implement it so it behaves exactly like the Java library?
The main thing is that the generators must produce exactly the same sequences as the Java ones for the same seeds. Our saved simulations depend on that. When you're done I'll run the module's own test suite, ported to Go, against `/app/port`. I'm not including those tests here, so please work from the Java source and match it closely: seeding, state handling, edge cases, error cases and numeric precision.
A few things that will save you some pain:
- Please keep the signatures and the package name in `/app/port` as they are, since our callers use them as-is. Edit the existing files in place and declare each type and function once; don't add files that declare them again.
- `mig-check` (on the PATH, works from any directory) compares `/app/port` with the original stubs, runs `go build` and `go vet`, and makes sure the package initialises without panicking. If any of that fails, the ported tests won't even compile, so run it often. `cd /app/port && go build ./...` is the quick version.
- Go's `regexp` is RE2, so Java-only syntax such as the `(?u)` flag, back-references, look-around and `\u{...}` escapes makes a package-level `regexp.MustCompile` panic at start-up.
- The ported tests live in the same package and define their own helpers named `mig` or `Mig` followed by an upper-case letter or `_` (like `migHelper`), so please avoid package-level names of that shape. `mig-check` lists any you have.
- This package ends up inside a sandboxed service, so it can't import `os`, `os/exec`, `syscall`, `runtime`, `plugin`, `net`, `net/http`, `net/rpc`, `io/ioutil`, `embed`, `unsafe`, `flag` or `testing` (or anything under `testing/`). It also can't use cgo (`import "C"`) or the `//go:linkname` and `//go:embed` directives. That goes for every non-test `.go` file under `/app/port`, so keep any scratch programs outside it. The rest of the standard library is fine (`math/bits`, `encoding/binary`, `math/big`, `reflect`, ...); for bit casts, `math.Float64bits` and friends do what `unsafe` would.
- Please write the logic yourself rather than calling out to another program.
- Our test machine has 2 vCPUs. Each test runs on its own, gets 60 seconds and a 2 GB address-space limit (the Go runtime reserves about 0.7 GB of that, so about 1.3 GB of heap), so keep things reasonably efficient.
