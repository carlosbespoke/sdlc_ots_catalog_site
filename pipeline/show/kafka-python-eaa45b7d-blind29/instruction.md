# python-broker-client: repairing wide-ranging misbehaviour without a test suite

This is the library an application leans on to hand messages to a broker and to read them back again, and it is getting both halves of that wrong now in a lot of small ways. The repository has received 29 separate undocumented edits. What follows is everything I have been able to observe from the outside, written up by what I was doing rather than by where I guess the problem lives.

Starting with getting messages out. Building a publishing client that asks for duplicate suppression and gives its acknowledgement level as the spelled-out word is now refused as a contradictory setup, even though that word names exactly the level duplicate suppression requires; giving the same level as a number is what I have to do instead. Once a client is up, publishing a message that carries a key behaves as if it had none: the hook that tells the placement strategy to start a fresh batch fires, and the payload reaches the outgoing batch queue more than once for a single call. Keyless messages go wrong the other way — consecutive ones no longer stay on the shard chosen first, each call wanders somewhere else, and after I explicitly rotate the choice for one feed the pinned choice for an unrelated feed moves as well. When a rotation does happen it frequently lands back on the very shard it was told to move off, even with nine others free. And a client set up for duplicate suppression claims, before it has ever spoken to a broker, that it already holds a broker-issued publisher identity, so it never asks for one on the first turn of its outbound loop and pushes data instead; the identity never advances out of its initial condition, neither through setup nor through the later bump of its generation counter.

On the reading side, asking to follow feeds by handing in a single plain string where a sequence of feed names belongs is now quietly accepted instead of being refused as a type error, though a one-element list still works. When the broker answers a request for data with the marker meaning "stop using the follower I suggested earlier and go back to the one in charge", the earlier follower choice for that shard is not cleared and keeps being reported. Enlisting a reader in a cohort is troubled too: against a broker that deliberately holds an enlistment request open, a short-timeout attempt used to come back promptly with a negative answer and then wait on the already-outstanding attempt rather than issuing a second one, and that sequence now misbehaves. Two unrelated edits show through it — one in how a running average folds its very first value, which I come to below, and one in how a freshly built holder for outgoing message batches sets itself up when no publisher identity has been handed to it yet.

Working out which participant handles which slice of a feed is off in both directions. On a first-ever allotment, where nobody declares prior ownership of anything, the plan hands out fewer shards than the feed has and holds the rest back for no reason. When participants do declare prior ownership and the balanced outcome needs a shard to move from one of them to another, the first-round plan no longer withholds the moving shard. Part of that is that reading back what a participant declared when it enlisted reports it as owning nothing at all, even when it explicitly listed two shards; the feed names in the same payload still come back fine. Separately, the bookkeeping that answers whether a run of moves amounted to pointless shuffling now says yes after I move one shard from A to B and then a second one from B back to A.

The numbers the client reports about itself are wrong in several ways. After feeding the values zero through nine into one collector, the reported average comes back as 4.6 rather than 4.5 — one value too many has been folded in ahead of the samples — while the maximum, minimum, tally and rate over the same samples are all still right. Percentile readings are worse than merely skewed: feeding in zero through ninety-nine and asking for the quarter, half and three-quarter points gives numbers nowhere near twenty-five, fifty and seventy-five. Building a named identifier out of a name and a family name yields one with those two transposed, so the readout the client publishes ends up keyed under the wrong label, and registering a quantity under such an identifier attaches the identifier and the quantity to each other the wrong way round, so a published snapshot no longer holds the entries under the heading they were registered with, and detaching a registered entry by its identifier does not work either.

Driving the broker from the management side brings its own complaints. Erasing two cohort ids in a single call should ask the broker exactly once which node owns both of them and then come back with a per-cohort result; that one pooled ownership question is no longer asked and the call does not return a result for each of them. Evicting participants from a cohort passes their ids and instance identifiers through untouched but drops the per-participant reason text at the version just below the newest, although that version carries the field. When I ask to discard messages up to a position and I pin the node to talk to, an answer saying that node is not the one in charge of the shard is retried anyway instead of being raised straight back to me. Worse, when the broker keeps answering that way, neither discarding messages nor listing the available positions of a shard ever gives up: with a two-hundred-millisecond request timeout configured, both calls simply keep going instead of eventually surfacing the error. Asking the broker to describe its capability flags gives back a mapping in which the settled generation number is no longer reported in the place it belongs. And turning the request that erases feed entries into bytes at the newest supported version and reading it straight back yields something other than what went in; the older versions still round-trip.

Finally, the machinery underneath all that. Asking a freshly built client which node is carrying the lightest load, before it has learned about any brokers at all, now hands back a node rather than nothing. Asking how many requests are outstanding to a node answers zero for one with three of them in progress, and something other than zero for a name with no link at all. Tearing a broker link down with an error to pass along does not push that error to the byte stream underneath, which is never aborted. Pushing bytes into a byte stream that has already been torn down is quietly accepted instead of raising. Scheduling a callback for an absolute point ten milliseconds out on the steadily advancing clock the loop keeps never fires it, even after two seconds of waiting. Stopping the background loop while a caller on another thread is blocked on something that will never resolve leaves that caller hanging forever rather than releasing it with an error. Constructing the object that manages links to brokers with the host-lookup mode that turns the seed entries into their official names fails outright instead of simply keeping that setting. One more: in the token-based authentication exchange the outgoing opening payload is still produced, but a non-empty reply from the broker is refused — it is never stored, and the exchange is never reported as finished or authenticated.

Restore the behavior described above.

Record the functions that contain those edits in `/app/rca.json`, one entry each:

```json
{
  "causes": [
    {
      "file": "kafka/admin/_acls.py",
      "function": "enclosing_function_name"
    }
  ]
}
```

`function` is the function name. A class prefix is ignored if you include one. When an
edit sits inside a function nested in another function, either name is accepted. Name
every function one of the undocumented edits is in, and only those. Where you wrote the
fix does not matter: if you restored the behavior from a caller or from a helper of your
own, name the function the edit is in rather than the one you wrote. If you suspect a
function but found no edit in it, leave it out.
