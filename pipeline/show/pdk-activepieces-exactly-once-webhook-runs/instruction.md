# Webhook deliveries can run their actions twice
Sender retries get a new `x-webhook-id` and a new run, a webhook worker that resubmits the same trigger output starts fresh runs, and a run whose worker dies starts over, repeating actions that already ran. Payment and GitHub webhook flows must not run their actions twice for one delivery.
## What we need
- Published `POST /api/v1/webhooks/:flowId` and `/api/v1/webhooks/:flowId/sync` honour an `Idempotency-Key` per flow across API instances. Equal requests return the original `x-webhook-id`; sync repeats return the original status, headers and body, also when they arrive while the original is still running. Reusing a key with a different body returns 422 without another run, also when it races the original.
- Concurrent identical requests, even across two API processes, create one flow run per trigger payload and execute its actions once.
- The worker's `submitPayloads` RPC request (`SubmitPayloadsRequest`) gains `webhookRequestId` and the worker's retry `attempt`. Repeating a submission with the same `webhookRequestId` (later, after a worker restart, or concurrently) returns the same runs in the same order and starts none.
- If a worker is killed during a run, a replacement worker finishes the run as `SUCCEEDED` within 120 seconds of starting, without repeating actions that had completed. Only an action cut off mid-call may be sent again.
- If Redis is unavailable for up to 20 seconds, an accepted delivery creates its runs exactly once within 45 seconds of recovery; otherwise return a 5xx and leave no runs for that delivery. A retry with the same key after a failed delivery works.
## Keep working
- Unkeyed webhooks stay independent deliveries; they and accepted keyed async deliveries return 200 with `x-webhook-id`. Disabled flows return 404 and missing flows 410, both with `x-webhook-id`. Successful sync flows return their Return Response body, completed runs show as `SUCCEEDED` in `GET /api/v1/flow-runs`, and an existing run still executes its actions once when the worker restarts.

The repository is at `/app` with PostgreSQL and Redis installed and the webhook, HTTP and store pieces built. Build from `/app` with `bun x turbo run build --filter=api --filter=worker --filter=@activepieces/engine --filter=@activepieces/piece-webhook --filter=@activepieces/piece-http --filter=@activepieces/piece-store`. Start dependencies with `sudo service postgresql start` and `sudo service redis-server start`; PostgreSQL is `postgres:postgres@localhost:5432`. The API and worker run as separate processes; Docker is unavailable here.
