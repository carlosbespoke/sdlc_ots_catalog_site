We run `DbConform.apply_changes()` at startup against SQLite databases full of data. The latest models change column types, make some columns NOT NULL, loosen others and change defaults, yet `compare()` says the database is up to date and every table keeps its old shape. A copy of one production database is in /data/shop.sqlite, with the models it should match in /data/shop_models.py.

On SQLite, existing columns should end up with the model's type, nullability and default, keeping every row. A column made NOT NULL that still holds NULLs needs `allow_not_null_backfill=True` and gets them filled from the same sources, in the same order, as a new NOT NULL column on a table with rows; without NULLs it needs no flag. A new NOT NULL column filled from another column or an expression has to work too. Shrinking still needs `allow_shrink_column=True`. When NULLs can't be filled, or with `allow_sqlite_table_rebuild=False`, `compare()` returns a ConformError, `apply_changes()` raises it, and the database stays as it was. Tables whose columns already match stay exactly as they are, and a second run plans no steps.

Bringing a table up to date must not lose or break anything else in the database, and an id handed out before must never be handed out again. `AsyncDbConform` should behave the same.

The SQLite tests in /app/tests/integration/test_integration_column_types.py that expect these changes to be ignored are out of date. The rest of /app/tests and `ruff check /app/src` must keep passing, and new code keeps the repo's docstring and type hint rules. There's no network.
