Arbeidsflate relies on `dialogEvents(dialogId)` to refresh open dialogs. Today a successful dialog write can be followed by a lost notification: the producer sends to Redis after saving and merely logs a send failure. There is no way to recover events missed during a disconnect.

Make committed updates and deletions durable as `DIALOG_UPDATED` and `DIALOG_DELETED` notifications with a positive, strictly increasing `sequence` payload field per dialog in commit order. For each dialog, the first update or deletion notification has sequence 1; each subsequent notification increments it by 1 (creation does not consume a notification sequence). Multiple WebApi writers and GraphQL instances should see the same per-dialog order, without duplicate or older events arriving after newer ones, including when an earlier delivery is retried. Changes committed while Redis is unavailable for 20 seconds must reach subscribers on every GraphQL instance within 30 seconds of recovery, in order; the same applies when a WebApi process is killed just after a successful write, and to writes through a WebApi instance started during the outage. Open subscriptions must also survive a PostgreSQL restart of up to 10 seconds: changes committed after the database is back reach them within 30 seconds, in order. Add optional `afterSequence` to `dialogEvents(dialogId)`: a reconnecting client receives exactly the committed notifications after that sequence in order and then live changes, even when delivery overlaps reconnection. Resuming must also work while Redis is unavailable, including on a GraphQL instance started during the outage. Keep the existing `dialogEvents(dialogId)` field and its `id` and `type` payload fields; subscriptions without `afterSequence` continue to receive new updates.

Work in `/app`. PostgreSQL and Redis are available locally; development configuration enables local Altinn stand-ins and the in-memory MassTransit transport. Run `sudo service postgresql start` and `sudo service redis-server start` when needed; use `app:app` for database connections. Docker is unavailable inside the solver container. Build with `dotnet build Digdir.Domain.Dialogporten.slnx -p:NuGetAudit=false` from `/app`.
