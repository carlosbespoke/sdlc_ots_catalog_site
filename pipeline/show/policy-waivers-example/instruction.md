# Bring GGJam's production stack and its exceptions register into line with the platform policy pack

The security team has finished its quarterly review of GGJam's exceptions register, and the platform policy pack now runs in CI with the register as its only source of approved exceptions. The register has drifted from the stack since the last review, and the pack fails across the stack. You own the change that brings both into line before the next release.

`/workspace/infra` is the Terraform configuration of GGJam's production AWS stack, a Ghost-backed Gatsby publishing platform (Terraform 1.16.4, AWS provider 5.100.0): about 270 resources across API Gateway, Auto Scaling, Certificate Manager, CloudWatch Logs, CloudWatch alarms, DynamoDB, EC2, ECS, Elastic Load Balancing, IAM, KMS, Lambda, RDS, S3, SNS, SQS, SSM Parameter Store, Secrets Manager, VPC networking and security groups. `terraform.tfstate` is the recorded production state. `policies/` is the platform policy pack: OPA/Rego rules, one package per rule, that conftest evaluates on the JSON form of the plan (`policies/README.md` lists every rule and what it requires; `policies/lib/tf.rego` holds the helpers they share). `policies/GUARDRAILS.md` specifies the deploy-stage guardrails the platform also evaluates on every production plan, after CI; CI does not run them and their code is not in the repository. `exceptions/register.json` is the team's exceptions register, which CI loads as data; `policies/EXCEPTIONS.md` defines a valid entry and which findings may be waived. CI runs `scripts/ci-plan.sh`: an offline `terraform init`, `terraform validate`, a plan against the recorded state without refreshing AWS (`-refresh=false`), and `conftest test --all-namespaces --policy policies --data exceptions` on the plan. The plan has no changes today, but the policy pack fails.

Change the configuration so that CI passes, as a change the team could apply to production as it is. There is no AWS access here; everything runs offline against the recorded state, exactly as CI does.

## Requirements

1. **CI passes.** Planned against the recorded production state (offline, `-refresh=false`), your configuration initializes, validates and plans without errors, and the policy pack reports no failures. Nothing in the configuration may need an AWS API call at plan time.
2. **The deploy-stage guardrails pass.** `policies/GUARDRAILS.md` specifies the guardrails (`IAM-002`, `IAM-003`, `KMS-003`, `KMS-004`, `KMS-005`, `CW-002`, `S3-002` and `S3-005`) that the platform's deploy stage evaluates on the same plan after CI. CI does not run them and their code is not in this repository, so that document is their whole specification; the grader evaluates its own implementation of every one of them on your plan, and none may report a violation.
3. **The exceptions register is exact.** `exceptions/register.json` is the team's register of approved exceptions; CI honours its valid entries (`policies/EXCEPTIONS.md` defines a valid entry and which findings may be waived; `EXC-001` reports invalid entries). After your change the register holds a valid entry for exactly the findings that cannot be fixed in place - a finding of a waivable rule on a resource and argument that `EXCEPTIONS.md` lists as replacement-only - and no other entry: every other finding is fixed, and an entry that is invalid or no longer waives such a finding is corrected or removed. The grader compares the rule and address of every entry with that set of findings, and runs CI's checks with your register on every plan it makes.
4. **Production resources are only updated in place.** Every resource instance recorded in `terraform.tfstate` stays managed at the address it has now and is planned either unchanged or as an in-place update: nothing is destroyed, replaced, forgotten or moved to a new address. Do not use `moved`, `removed` or `import` blocks.
5. **Updates change only what the policies are about.** An in-place update may change only the arguments listed for its resource type in the table below (a nested block counts as one argument: changing anything inside `metadata_options` is a change of `metadata_options`). Every other argument of every recorded resource - names, tags, descriptions, sizes, settings - plans to its recorded value, and resource types missing from the table must not change at all. 6. **New resources only of these types:** `aws_db_parameter_group`, `aws_flow_log`, `aws_s3_bucket_ownership_controls`, `aws_s3_bucket_policy`, `aws_s3_bucket_public_access_block`, `aws_s3_bucket_server_side_encryption_configuration` and `aws_s3_bucket_versioning`. A new resource of any other type fails, however harmless; in particular, use the stack's existing KMS keys rather than new ones.
7. **Fixes are general.** The `site_components`, `delivery_channels` and `build_lanes` variables are how the team adds, removes and changes a site component, a delivery channel and a build lane: such a change must need no other edit. This is graded with hidden changes of these variables, each made through a `-var-file` (for `site_components`, keys added and removed; for `delivery_channels`, keys added and changed; for `build_lanes`, keys added and removed). An added key has a name that appears nowhere in the repository and an entry with any values the variable's type, validation and description allow; a removed key is one of today's keys; a changed entry keeps its key and gets new values for some of its fields. Each plan is made against a copy of the production state in which everything the *current* configuration creates for the added keys already exists, exactly as the current configuration creates it, as if the team had made the change before yours. Requirements 1 to 6 must hold for each of these plans, with two exceptions that follow from the change itself: the recorded resources of a removed key are destroyed exactly as the current configuration destroys them when that key is removed (nothing else is destroyed), and an argument the current configuration itself updates in place for the change may change too. Each change is graded twice, with different hidden values each time (other added keys, another of today's keys removed, other new values for the changed fields); this statement shows none of them.
   A delivery channel's dead-letter queue keeps the visibility timeout of the channel's entry: in the plan of such a change, every `aws_sqs_queue` whose address matches `^aws_sqs_queue\.channel_dlq\["webhook"\]$` must then have `visibility_timeout_seconds` equal to the channel's new `visibility_seconds`.
8. **SSH only from the admin ranges.** Every security group ingress rule that opens TCP port 22 must take its sources from `var.admin_cidr_blocks` and nothing else. This is graded by planning with a different value of `var.admin_cidr_blocks` against the recorded state, twice, with two different hidden settings that this statement does not show: every security group ingress rule that opens TCP port 22 must then admit exactly the CIDR ranges of that value (no other CIDR, IPv6 range, security group or prefix list), and `aws_security_group.jumpbox` and `aws_security_group.release_runner` must each have such a rule. Requirements 1 to 6 must hold for those plans as well.
9. **Database backups and the content key's deletion window follow their inputs.** The Ghost database keeps automated backups for `var.ghost_db_backup_days` days, raised to the pack's minimum when the input is lower, and the content key's deletion window is `var.content_key_deletion_window_days` days, raised to the pack's minimum when the input is shorter. This is graded by planning with different values of `var.ghost_db_backup_days` and `var.content_key_deletion_window_days` against the recorded state, twice, with two different hidden settings that this statement does not show: every `aws_db_instance` whose address matches `^aws_db_instance\.ghost$` must then have `backup_retention_period` equal to the requested `ghost_db_backup_days`, since it meets the pack's 7-day minimum; every `aws_kms_key` whose address matches `^aws_kms_key\.content$` must then have `deletion_window_in_days` equal to the pack's 30-day minimum, since the requested window is shorter. Requirements 1 to 6 must hold for those plans as well.
10. **The root module's variables stay as declared.** Every variable declared in the root module keeps its name, `type`, `default`, `validation` blocks and its `nullable`, `sensitive` and `ephemeral` settings exactly as they are (only its `description` may be reworded), and gets no other value (for example from a `.tfvars` file). You may add variables (with defaults) and locals, and change the variables of child modules.
11. **CI itself and the toolchain wiring stay as they are.** `providers.tf`, `versions.tf`, `scripts/ci-plan.sh` and every file under `policies/` stay byte for byte as they are (no file added there either), and the repository gets no conftest configuration file (`conftest.toml`). The grader uses its own copies of the policy pack, of the production state and of the lock file, so editing `terraform.tfstate` or `.terraform.lock.hcl` has no effect.
12. **Configuration hygiene**, anywhere in the repository: the configuration stays in Terraform's native HCL syntax, in `.tf` files: a file in Terraform's JSON syntax (`*.tf.json`) fails this requirement even when Terraform would accept it (the team's tooling and reviews read HCL only). Also no override files (`override.tf`, `*_override.tf`), no `lifecycle` `ignore_changes` or `replace_triggered_by`, no provisioners, no `backend` or `cloud` blocks, no `provider` blocks outside `providers.tf`, and no `external`, `http` or `terraform_remote_state` data sources.

## How it is graded

In a separate container with no network, the grader copies `/workspace/infra` (ignoring state files, plan files, `.terraform/`, `.git/`, symbolic links and the lock file), runs `terraform init`, `validate` and a `-refresh=false` plan against its own copy of the production state as an unprivileged user, checks requirements 4, 5, 6 and the last three on the configuration and the plan, and runs conftest with its own copy of `policies/` and its own implementation of the deploy-stage guardrails on the plan JSON (with your `exceptions/register.json` as data), and compares the register's entries with the findings that cannot be fixed in place. It then runs the plans of requirements 7, 8 and 9 and checks them the same way. The reward is 1 when every requirement holds and 0 otherwise.
