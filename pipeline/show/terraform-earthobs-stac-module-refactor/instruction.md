The Terraform for our earth observation STAC API sandbox stack in `/workspace/infra` has grown into one flat root module: everything is declared at the top level, the per-AZ resources are `count`-indexed by list position, and names, settings and tags are hard-coded all over the files. Split it into three local modules (network, data and services) without touching the running infrastructure: against the current state, the plan has to come out as nothing but moves.

There is no AWS access from this machine. `terraform init` works offline from the local provider mirror, `terraform.tfstate` is a copy of the production state, and `scripts/ci-plan.sh` runs what CI runs: a `terraform plan -refresh=false` against the state followed by the guardrail policies in `policies/`.

## Detailed Constraints

**How CI judges the change.** CI takes the repository alone and plans it with `terraform plan -refresh=false` against its own copy of the production state. Local `terraform state` commands and edits to `terraform.tfstate` never reach it, so the whole migration has to be expressed in the configuration. That plan must:
- still manage every resource that is in the state today, and
- contain no create, update, replace, destroy or forget: only resources moving to new addresses.

The guardrail policies in `policies/` must pass on that plan, and `providers.tf` and everything in `policies/` stay exactly as they are, byte for byte.

**Layout.**
- The root module calls `module "network"`, `module "data"` and `module "services"`, with sources `./modules/network`, `./modules/data` and `./modules/services` and one instance each, calls no other module and declares no resources of its own.
- Which module owns what (every instance of the resources described, wherever they are declared today):
  - network: the VPC, internet gateway, public and workbench subnets, Elastic IPs and NAT gateways, public and workbench route tables, routes and associations, the S3 gateway endpoint and all of its route table associations, every workbench profile and bootstrap parameter, the parameters that record the primary workbench subnet, diagnostics workbench and all-workbench manifest, the primary workbench launch template, and the VPC flow log together with its log group, IAM role and inline policy;
  - data: both KMS keys and aliases, the data bucket and all of its ownership, access, versioning, encryption and policy resources, the data consumer policy, the PgSTAC EFS file system, security group, self and egress rules, mount targets and consumer policy, and every processing-stage S3 marker, queue, dead-letter queue, queue policy, topic, topic subscription, log group, backlog alarm, configuration parameter and runtime parameter together with the pipeline order, manifest, routes, primary queue and replay queue parameters;
  - services: both ECR repositories with their lifecycle and repository policies, both ECS clusters and task definitions, both internal load balancers, target groups and listeners, all service and load-balancer security groups and their rules including the PgSTAC-to-EFS rule, both task and task-execution roles with their inline policies and managed attachments, and both service log groups, Secrets Manager secrets and secret versions.
- Each of these modules declares the resources it owns itself and calls no other module.
- Modules get each other's IDs and ARNs through module outputs and variables. Never paste an ID, ARN, IP address or DNS name of an existing resource, or any part of one (such as an ARN suffix), into the `.tf` files or templates. A name the configuration itself chooses (a bucket, role or parameter name, and an ARN built from that name alone, such as `arn:aws:s3:::<bucket>`) may also be derived from the same root inputs in the module that needs it, as long as no module spells today's value. The configuration reads files only through literal paths inside its own module (such as `"${path.module}/templates/..."`; in a child module a path starts with `${path.module}/`, because Terraform resolves any other relative path from the root directory, not from the module): no computed paths, no `terraform_remote_state` data sources, and never the state or a plan file.

**Keys.**
- Everything that exists once per availability zone today is a `for_each` resource keyed by the AZ name (for example `["us-east-1a"]`), including each instance of a list that also holds things that belong to no single availability zone (its associations with the workbench route tables; its association with the public route table is not per AZ).
- The legacy EFS mount targets and S3 endpoint associations were created in orders different from the subnet list, so derive each old instance's key from what it actually references. The primary workbench subnet parameter and primary workbench launch template always select the entry with the lowest `route_priority`; when an add, removal or update changes that winner, both update in place. The diagnostics workbench parameter selects the lexicographically first entry whose `diagnostics` flag is true, falling back to the lexicographically first remaining AZ when none is true. It must likewise follow add, removal and update changes, in addition to the collector updates described below.
- Everything that exists once per processing stage today is a `for_each` resource keyed by the stage name (for example `["raw"]`), including each instance of a list that also holds things that belong to no single processing stage.
- The primary stage queue parameter always selects the entry with the lowest `priority`; when an add, removal or update changes that winner, it updates in place. The replay stage queue parameter selects the lexicographically first entry whose `replay_source` flag is true, falling back to the lexicographically first remaining stage when none is true. It must likewise follow add, removal and update changes, in addition to the collector updates described below.
- Don't use `count` anywhere. Other repeated resources use `for_each` with string keys that are not numbers (a name such as `["assets"]`, never `["0"]`).
- Each existing availability zone's entry in `availability_zones` is the only source of its values: changing an entry changes, for that availability zone alone, exactly the settings the entry provides, and changes nothing else.
- Adding an availability zone to `availability_zones` must plan only the creation of that availability zone's resources, each configured exactly like its counterparts in the existing availability zones apart from the availability zone itself and the values its entry in `availability_zones` gives it (same settings, names and tags), and removing one only the destruction of that availability zone's resources. Beyond that, the only change either may plan is an in-place update of the settings that collect something from every availability zone today (wherever a setting holds a part of every availability zone: their names, IDs, ARNs, subnets or CIDRs, say, in a list, a policy document or an environment value): each of them must take in, or drop, exactly that availability zone's part where it belongs, in the same form as today (today's parts keep their order, except inside an IAM policy document, where the order of statements, actions and resources means nothing to AWS; where a new part goes is up to you), and change nothing else. No other resource may be created, updated, replaced or destroyed.
- Each existing processing stage's entry in `processing_stages` is the only source of its values: changing an entry changes, for that processing stage alone, exactly the settings the entry provides, and changes nothing else.
- Adding a processing stage to `processing_stages` must plan only the creation of that processing stage's resources, each configured exactly like its counterparts in the existing processing stages apart from the processing stage itself and the values its entry in `processing_stages` gives it (same settings, names and tags), and removing one only the destruction of that processing stage's resources. Beyond that, the only change either may plan is an in-place update of the settings that collect something from every processing stage today (wherever a setting holds a part of every processing stage: their names, IDs, ARNs, subnets or CIDRs, say, in a list, a policy document or an environment value): each of them must take in, or drop, exactly that processing stage's part where it belongs, in the same form as today (today's parts keep their order, except inside an IAM policy document, where the order of statements, actions and resources means nothing to AWS; where a new part goes is up to you), and change nothing else. No other resource may be created, updated, replaced or destroyed.

**Root variables.** Declare these in the root module, each defaulting to today's value:
- `project` (`string`, `"earthobs"`): every whole-word occurrence of `earthobs` in a resource name, identifier or tag value today, and the `PROJECT=` line in the primary workbench launch template's user data, comes from it (whole word: not part of a longer run of letters and digits, so `earthobs-api`, `earthobs_key` and `/earthobs/` count, while a longer word that merely contains `earthobs` stays as it is), and so does every mention of those names elsewhere in the configuration (for example a resource name inside a policy); inside documents such as policies, container definitions and environment values, every whole-word occurrence of `earthobs` that stands for it comes from it too; this also includes every free-text description whose `earthobs` token identifies this project.
- `environment` (`string`, `"sandbox"`): every whole-word occurrence of `sandbox` in a resource name, identifier or tag value today, and the `ENVIRONMENT=` line in the primary workbench launch template's user data, comes from it (whole word: not part of a longer run of letters and digits, so `sandbox-api`, `sandbox_key` and `/sandbox/` count, while a longer word that merely contains `sandbox` stays as it is), and so does every mention of those names elsewhere in the configuration (for example a resource name inside a policy); inside documents such as policies, container definitions and environment values, every whole-word occurrence of `sandbox` that stands for it comes from it too; this also includes every free-text description whose `sandbox` token identifies this environment.
- `vpc_cidr` (`string`, `"10.1.0.0/16"`): the VPC's CIDR block; subnet CIDRs remain controlled by `availability_zones`.
- `availability_zones`: `map(object({ public_cidr = string, workload_cidr = string, route_priority = number, instance_type = string, root_volume_gb = number, bootstrap_channel = string, maintenance_window = string, telemetry_port = number, diagnostics = bool }))`, keyed by AZ name, defaulting to today's three AZs, their public and workload subnet CIDRs, routing priorities, workbench instance types, root-volume sizes, bootstrap channels, maintenance windows, telemetry ports and diagnostics flags. It is the only source of AZ names and all nine per-AZ settings; every profile and bootstrap parameter records all of its applicable entry settings. Lower `route_priority` values come first wherever a setting collects the workbench subnets or workbench records, and the lowest-priority entry supplies both the primary workbench subnet parameter and every AZ-specific setting in the primary workbench launch template, including its user data.
- `processing_stages`: `map(object({ priority = number, visibility_timeout_seconds = number, message_retention_seconds = number, delivery_delay_seconds = number, backlog_threshold = number, archive_prefix = string, receive_wait_seconds = number, alarm_evaluation_periods = number, severity = string, retry_limit = number, batch_size = number, routing_class = string, replay_source = bool }))`, keyed by stage name, defaulting to today's four stages and their priority, queue visibility timeout, queue and dead-letter retention, delivery delay, backlog threshold, archive prefix, receive-wait time, alarm evaluation periods, severity, retry limit, batch size, routing class and replay-source flag. It is the only source of stage names and those settings. Each stage's configuration and runtime parameters record all of their applicable entry settings. Lower `priority` values come first in ordered pipeline collectors, and the lowest-priority entry supplies the primary stage queue parameter.
- `tags` (`map(string)`, `{ Owner = "geospatial-platform", CostCenter = "cc-4821", ManagedBy = "terraform", Compliance = "internal" }`): the shared tags (`Owner`, `CostCenter`, `ManagedBy` and `Compliance`) that tagged resources carry today. Wherever the configuration writes them out today, in any form, they come from this variable, so that a different map (other keys, other values) reaches every one of those places; a resource's other tags stay as they are, and resources that are untagged today stay untagged.
- `service_cpu` (`number`, `1024`): the CPU of both ECS task definitions and both container definitions.
- `service_memory` (`number`, `2048`): the memory of both ECS task definitions and both container definitions.
- `log_retention_days` (`number`, `30`): the retention of every CloudWatch log group.
- `efs_throughput_mode` (`string`, `"bursting"`): the PgSTAC EFS file system's throughput mode.
- `flow_log_aggregation_interval` (`number`, `600`): the VPC flow log's maximum aggregation interval.
- `kms_deletion_window_days` (`number`, `30`): the deletion window of both customer-managed KMS keys.
- `alarm_period_seconds` (`number`, `300`): the period of every processing-stage backlog alarm.
- `lb_health_check_interval` (`number`, `60`): the health-check interval of both service target groups.
- Changing `vpc_cidr`, `service_cpu`, `service_memory`, `log_retention_days`, `efs_throughput_mode`, `flow_log_aggregation_interval`, `kms_deletion_window_days`, `alarm_period_seconds` and `lb_health_check_interval` changes only what each one's line above says it controls: every other setting keeps today's value, including a setting that merely has the same value today.

**Root outputs.** Keep `vpc_id`, `primary_workbench_launch_template_id`, `pipeline_manifest_parameter_name`, `data_bucket_name`, `pgstac_efs_id`, `stacapi_load_balancer_dns`, `pgstac_task_role_arn` and `pipeline_order_parameter_name` with their current values. Add `workbench_manifest_parameter_name`: the `name` of `aws_ssm_parameter.workbench_manifest`. Add `diagnostics_workbench_parameter_name`: the `name` of `aws_ssm_parameter.diagnostics_workbench`. Add `pipeline_routes_parameter_name`: the `name` of `aws_ssm_parameter.pipeline_routes`. Add `replay_stage_queue_parameter_name`: the `name` of `aws_ssm_parameter.replay_stage_queue`. `public_subnet_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_subnet.public`. `workbench_subnet_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_subnet.workbench`. `workbench_profile_parameter_names` becomes a map from the AZ name to the `name` of that availability zone's `aws_ssm_parameter.workbench_profile`. `efs_mount_target_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_efs_mount_target.pgstac`. `stage_queue_urls` becomes a map from the stage name to the `url` of that processing stage's `aws_sqs_queue.stage`. `stage_topic_arns` becomes a map from the stage name to the `arn` of that processing stage's `aws_sns_topic.stage`. `stage_config_parameter_names` becomes a map from the stage name to the `name` of that processing stage's `aws_ssm_parameter.stage_config`. `stage_backlog_alarm_arns` becomes a map from the stage name to the `arn` of that processing stage's `aws_cloudwatch_metric_alarm.stage_backlog`. `workbench_bootstrap_parameter_names` is a new output: a map from the AZ name to the `name` of that availability zone's `aws_ssm_parameter.workbench_bootstrap`. `stage_runtime_parameter_names` is a new output: a map from the stage name to the `name` of that processing stage's `aws_ssm_parameter.stage_runtime`. Each output passes through outputs of the module that owns the resource (network for `vpc_id`, `public_subnet_ids`, `workbench_subnet_ids`, `workbench_profile_parameter_names`, `primary_workbench_launch_template_id`, `workbench_bootstrap_parameter_names`, `workbench_manifest_parameter_name` and `diagnostics_workbench_parameter_name`; data for `efs_mount_target_ids`, `stage_queue_urls`, `stage_topic_arns`, `stage_config_parameter_names`, `stage_backlog_alarm_arns`, `pipeline_manifest_parameter_name`, `data_bucket_name`, `pgstac_efs_id`, `pipeline_order_parameter_name`, `stage_runtime_parameter_names`, `pipeline_routes_parameter_name` and `replay_stage_queue_parameter_name`; services for `stacapi_load_balancer_dns` and `pgstac_task_role_arn`): the root output is a plain reference to an output of that module, and that module output is a plain reference to the resource. A plain reference is a reference such as `module.network.<output>` or `<resource type>.<name>.<attribute>`, a local that holds one, or a `for` expression that only re-keys one (`{ for k, v in <reference> : k => v.id }`) or iterates a plain reference and looks each key up in one (`{ for k, v in var.<map> : k => <reference>[k].id }`); no literals, function calls, conditionals or string templates anywhere along the way, except inside the key that picks one instance of a resource (`<reference>[sort(keys(var.<map>))[0]].id` is a plain reference).

**Not allowed anywhere in the configuration:** `ignore_changes`, `prevent_destroy` and `replace_triggered_by`, `removed` and `import` blocks, provisioners, `external` data sources, backend or cloud blocks, provider blocks other than the one in `providers.tf`, override files and `.tf.json` files.
