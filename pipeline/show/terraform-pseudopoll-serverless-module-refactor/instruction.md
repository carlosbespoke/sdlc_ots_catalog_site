The Terraform for our PseudoPoll production serverless stack in `/workspace/infra` has grown into one flat root module: everything is declared at the top level, the per-service resources are `count`-indexed by list position, and names, settings and tags are hard-coded all over the files. Split it into five local modules (network, data, compute, events and api) without touching the running infrastructure: against the current state, the plan has to come out as nothing but moves.

There is no AWS access from this machine. `terraform init` works offline from the local provider mirror, `terraform.tfstate` is a copy of the production state, and `scripts/ci-plan.sh` runs what CI runs: a `terraform plan -refresh=false` against the state followed by the guardrail policies in `policies/`.

## Detailed Constraints

**How CI judges the change.** CI takes the repository alone and plans it with `terraform plan -refresh=false` against its own copy of the production state. Local `terraform state` commands and edits to `terraform.tfstate` never reach it, so the whole migration has to be expressed in the configuration. That plan must:
- still manage every resource that is in the state today, and
- contain no create, update, replace, destroy or forget: only resources moving to new addresses.

The guardrail policies in `policies/` must pass on that plan, and `providers.tf` and everything in `policies/` stay exactly as they are, byte for byte.

**Layout.**
- The root module calls `module "network"`, `module "data"`, `module "compute"`, `module "events"` and `module "api"`, with sources `./modules/network`, `./modules/data`, `./modules/compute`, `./modules/events` and `./modules/api` and one instance each, calls no other module and declares no resources of its own.
- Which module owns what (every instance of the resources described, wherever they are declared today):
  - network: the VPC and every microservice's security group and dependency egress rule;
  - data: the application KMS key and alias, the Terraform state bucket and all of its settings, both DynamoDB tables, the shared service-events SNS topic, the API Gateway logging policy, and every microservice and notification-channel configuration parameter;
  - compute: every microservice's Lambda function, IAM role, runtime policy and attachment, CloudWatch log group, SQS queue and queue policy, SNS subscription, plus the service catalog and service registry parameters; it does not own the microservice error alarms or per-service configuration parameters;
  - events: the application EventBridge bus; every choreography rule and target, its Lambda permission, dead-letter queue, failed-invocations alarm and event parameter; the event catalog and registry parameters and the event-rule catalog policy; every microservice error alarm and the policy that catalogs all service queues; and every notification channel's SNS topic, SQS queue, subscription and queue policy, EventBridge rule and target, log group and queue-depth alarm, plus the channel registry parameter and all-channels publish policy;
  - api: the API Gateway account, REST API, deployment and stage, its logging IAM role and policy attachment and log group; every operation's API resource, request validator, method, integration, response, Lambda permission, method settings and operation parameter; the operation registry parameter; and every notification channel's individual publish policy.
- Each of these modules declares the resources it owns itself and calls no other module.
- Modules get each other's IDs and ARNs through module outputs and variables. Never paste an ID, ARN, IP address or DNS name of an existing resource, or any part of one (such as an ARN suffix), into the `.tf` files or templates. The configuration reads files only through literal paths inside its own module (such as `"${path.module}/templates/..."`; in a child module a path starts with `${path.module}/`, because Terraform resolves any other relative path from the root directory, not from the module): no computed paths, no `terraform_remote_state` data sources, and never the state or a plan file.

**Keys.**
- Everything that exists once per microservice today is a `for_each` resource keyed by the microservice name (for example `["poll-manager"]`), including each instance of a list that also holds things that belong to no single microservice.
- Every service name referenced by another configuration map must be a key in this map. Registries that record a primary microservice use the first still-present microservice in today's deployment order; if it is removed, the next still-present one is promoted.
- Everything that exists once per choreography event today is a `for_each` resource keyed by the event name (for example `["vote-counted"]`), including each instance of a list that also holds things that belong to no single choreography event.
- Each target_service must name a microservice from `services`. Registries that record a primary choreography event use the first still-present event in today's deployment order; if it is removed, the next still-present one is promoted.
- Everything that exists once per API operation today is a `for_each` resource keyed by the operation name (for example `["create-poll"]`), including each instance of a list that also holds things that belong to no single API operation.
- Each target_service must name a microservice from `services`. Registries that record a primary API operation use the first still-present operation in today's deployment order; if it is removed, the next still-present one is promoted.
- Everything that exists once per notification channel today is a `for_each` resource keyed by the channel name (for example `["public-results"]`), including each instance of a list that also holds things that belong to no single notification channel.
- Registries that record a primary notification channel use the first still-present channel in today's deployment order; if it is removed, the next still-present one is promoted.
- Don't use `count` anywhere. Other repeated resources use `for_each` with string keys that are not numbers (a name such as `["assets"]`, never `["0"]`).
- Each existing microservice's entry in `services` is the only source of its values: changing an entry changes, for that microservice alone, exactly the settings the entry provides, and changes nothing else.
- Adding a microservice to `services` must plan only the creation of that microservice's resources, each configured exactly like its counterparts in the existing microservices apart from the microservice itself and the values its entry in `services` gives it (same settings, names and tags), and removing one only the destruction of that microservice's resources. Beyond that, the only change either may plan is an in-place update of the settings that collect something from every microservice today (wherever a setting holds a part of every microservice: their names, IDs, ARNs, subnets or CIDRs, say, in a list, a policy document or an environment value): each of them must take in, or drop, exactly that microservice's part where it belongs, in the same form as today (today's parts keep their order, except inside an IAM policy document, where the order of statements, actions and resources means nothing to AWS; where a new part goes is up to you), and change nothing else. No other resource may be created, updated, replaced or destroyed.
- Each existing choreography event's entry in `events` is the only source of its values: changing an entry changes, for that choreography event alone, exactly the settings the entry provides, and changes nothing else.

Beyond that, the only change either may plan is an in-place update of the settings that collect something from every choreography event today (wherever a setting holds a part of every choreography event: their names, IDs, ARNs, subnets or CIDRs, say, in a list, a policy document or an environment value): each of them must take in, or drop, exactly that choreography event's part where it belongs, in the same form as today (today's parts keep their order, except inside an IAM policy document, where the order of statements, actions and resources means nothing to AWS; where a new part goes is up to you), and change nothing else. **Root variables.** Declare these in the root module, each defaulting to today's value:
- `project` (`string`, `"pseudopoll"`): every whole-word occurrence of `pseudopoll` in a resource name, identifier or tag value today comes from it (whole word: not part of a longer run of letters and digits, so `pseudopoll-api`, `pseudopoll_key` and `/pseudopoll/` count, while a longer word that merely contains `pseudopoll` stays as it is), and so does every mention of those names elsewhere in the configuration (for example a resource name inside a policy); inside documents such as policies, container definitions and environment values, every whole-word occurrence of `pseudopoll` that stands for it comes from it too; in ordinary free-text resource descriptions too, every whole-word occurrence of `pseudopoll` that denotes the project comes from this variable.
- `environment` (`string`, `"prod"`): every whole-word occurrence of `prod` in a resource name, identifier or tag value today comes from it (whole word: not part of a longer run of letters and digits, so `prod-api`, `prod_key` and `/prod/` count, while a longer word that merely contains `prod` stays as it is), and so does every mention of those names elsewhere in the configuration (for example a resource name inside a policy); inside documents such as policies, container definitions and environment values, every whole-word occurrence of `prod` that stands for it comes from it too; in ordinary free-text resource descriptions too, every whole-word occurrence of `prod` that denotes the environment comes from this variable.
- `services`: `map(object({ memory_size = number, timeout = number, queue_retention_seconds = number, error_threshold = number, egress_cidr = string, egress_port = number }))`, keyed by microservice name, defaulting to today's five microservices and their Lambda memory and timeout, queue retention, error-alarm threshold, and dependency-egress CIDR and port. It is the only source of microservice names and those per-microservice settings.
- `events`: `map(object({ detail_type = string, target_service = string, alarm_threshold = number, dlq_retention_seconds = number, maximum_event_age_seconds = number, maximum_retry_attempts = number }))`, keyed by event name, defaulting to today's five events and their detail type, target microservice, failed-invocation threshold, dead-letter retention, maximum event age and retry attempts. It is the only source of event names and those per-event settings.
- `operations`: `map(object({ path_part = string, http_method = string, target_service = string, validate_body = bool, burst_limit = number, rate_limit = number }))`, keyed by operation name, defaulting to today's seven routes and their path part, HTTP method, target microservice, request-body validation setting, burst limit and rate limit. It is the only source of operation names and those per-operation settings.
- `channels`: `map(object({ detail_type = string, visibility_timeout_seconds = number, message_retention_seconds = number, delivery_delay_seconds = number, alarm_threshold = number, evaluation_periods = number }))`, keyed by notification-channel name, defaulting to today's four channels and their event detail type, queue visibility timeout, message retention, delivery delay, queue-depth threshold and alarm evaluation periods. It is the only source of channel names and those per-channel settings.
- `tags` (`map(string)`, `{ Owner = "platform-team", CostCenter = "cc-7421", ManagedBy = "terraform" }`): the shared tags (`Owner`, `CostCenter` and `ManagedBy`) that tagged resources carry today. Wherever the configuration writes them out today, in any form, they come from this variable, so that a different map (other keys, other values) reaches every one of those places; a resource's other tags stay as they are, and resources that are untagged today stay untagged.
- `log_retention_days` (`number`, `30`): the retention of every CloudWatch log group.
- `service_queue_visibility_timeout` (`number`, `90`): the visibility timeout of every microservice queue.
- `event_queue_visibility_timeout` (`number`, `90`): the visibility timeout of every choreography dead-letter queue.
- `alarm_period_seconds` (`number`, `300`): the metric period of every microservice, choreography-event and notification-channel CloudWatch alarm.
- `lambda_runtime` (`string`, `"python3.12"`): the runtime of every microservice Lambda function.
- `lambda_handler` (`string`, `"index.handler"`): the handler of every microservice Lambda function.
- `lambda_architectures` (`list(string)`, `["x86_64"]`): the architectures of every microservice Lambda function.
- `kms_deletion_window_days` (`number`, `30`): the deletion window in days of the application KMS key.
- `kms_rotation_enabled` (`bool`, `true`): whether key rotation is enabled for the application KMS key.
- `state_bucket_force_destroy` (`bool`, `true`): the force-destroy setting of the Terraform state bucket.
- `api_metrics_enabled` (`bool`, `true`): whether CloudWatch metrics are enabled in every API operation's method settings.
- `api_logging_level` (`string`, `"INFO"`): the logging level in every API operation's method settings.
- `api_throttling_burst_limit` (`number`, `0`): an increment added to each API operation's own burst_limit when setting that operation's throttling burst limit.
- `api_throttling_rate_limit` (`number`, `0`): an increment added to each API operation's own rate_limit when setting that operation's throttling rate limit.
- `queue_receive_wait_seconds` (`number`, `0`): the long-poll receive wait time of every microservice queue, choreography dead-letter queue and notification-channel queue.
- Changing `log_retention_days`, `service_queue_visibility_timeout`, `event_queue_visibility_timeout`, `alarm_period_seconds`, `lambda_runtime`, `lambda_handler`, `lambda_architectures`, `kms_deletion_window_days`, `kms_rotation_enabled`, `state_bucket_force_destroy`, `api_metrics_enabled`, `api_logging_level`, `api_throttling_burst_limit`, `api_throttling_rate_limit` and `queue_receive_wait_seconds` changes only what each one's line above says it controls: every other setting keeps today's value, including a setting that merely has the same value today.

**Root outputs.** Keep `rest_api_id`, `rest_api_stage_name`, `single_table_name`, `state_bucket_name` and `vpc_id` with their current values. `service_function_arns` becomes a map from the microservice name to the `arn` of that microservice's `aws_lambda_function.service`. `service_queue_urls` becomes a map from the microservice name to the `url` of that microservice's `aws_sqs_queue.service`. `service_security_group_ids` becomes a map from the microservice name to the `id` of that microservice's `aws_security_group.service`. `event_rule_arns` becomes a map from the event name to the `arn` of that choreography event's `aws_cloudwatch_event_rule.event`. `event_dlq_urls` is a new output: a map from the event name to the `url` of that choreography event's `aws_sqs_queue.event_dlq`. `operation_resource_ids` becomes a map from the operation name to the `id` of that API operation's `aws_api_gateway_resource.operation`. `channel_topic_arns` becomes a map from the channel name to the `arn` of that notification channel's `aws_sns_topic.channel`. `channel_queue_urls` becomes a map from the channel name to the `url` of that notification channel's `aws_sqs_queue.channel`. Each output passes through outputs of the module that owns the resource (network for `vpc_id` and `service_security_group_ids`; data for `single_table_name` and `state_bucket_name`; compute for `service_function_arns` and `service_queue_urls`; events for `event_rule_arns`, `event_dlq_urls`, `channel_topic_arns` and `channel_queue_urls`; api for `rest_api_id`, `rest_api_stage_name` and `operation_resource_ids`): the root output is a plain reference to an output of that module, and that module output is a plain reference to the resource. A plain reference is a reference such as `module.api.<output>` or `<resource type>.<name>.<attribute>`, a local that holds one, or a `for` expression that only re-keys one (`{ for k, v in <reference> : k => v.id }`) or iterates a plain reference and looks each key up in one (`{ for k, v in var.<map> : k => <reference>[k].id }`); no literals, function calls, conditionals or string templates anywhere along the way.

**Not allowed anywhere in the configuration:** `ignore_changes`, `prevent_destroy` and `replace_triggered_by`, `removed` and `import` blocks, provisioners, `external` data sources, backend or cloud blocks, provider blocks other than the one in `providers.tf`, override files and `.tf.json` files.
