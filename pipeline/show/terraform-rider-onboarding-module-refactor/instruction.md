The Terraform for our ride-hailing user-onboarding production stack in `/workspace/infra` has grown into one flat root module: everything is declared at the top level, the per-stage resources are `count`-indexed by list position, and names, settings and tags are hard-coded all over the files. Split it into four local modules (identity, messaging, workflow and edge) without touching the running infrastructure: against the current state, the plan has to come out as nothing but moves.

There is no AWS access from this machine. `terraform init` works offline from the local provider mirror, `terraform.tfstate` is a copy of the production state, and `scripts/ci-plan.sh` runs what CI runs: a `terraform plan -refresh=false` against the state followed by the guardrail policies in `policies/`.

## Detailed Constraints

**How CI judges the change.** CI takes the repository alone and plans it with `terraform plan -refresh=false` against its own copy of the production state. Local `terraform state` commands and edits to `terraform.tfstate` never reach it, so the whole migration has to be expressed in the configuration. That plan must:
- still manage every resource that is in the state today, and
- contain no create, update, replace, destroy or forget: only resources moving to new addresses.

The guardrail policies in `policies/` must pass on that plan, and `providers.tf` and everything in `policies/` stay exactly as they are, byte for byte.

**Layout.**
- The root module calls `module "identity"`, `module "messaging"`, `module "workflow"` and `module "edge"`, with sources `./modules/identity`, `./modules/messaging`, `./modules/workflow` and `./modules/edge` and one instance each, calls no other module and declares no resources of its own.
- Which module owns what (every instance of the resources described, wherever they are declared today):
  - identity: the Cognito user pool and client, and the Lambda execution IAM role with its base policy and policy attachment;
  - messaging: the audience profile DynamoDB tables, notification SNS topics and topic policies, event SQS queues and subscriptions, queue-depth alarms, audience registry parameters, and the operations topic, audit queue and their subscription;
  - workflow: the stage Lambda functions, their log groups, dead-letter queues, queue policies, alarms, inline IAM policies and registry parameters, plus the workflow log group, audience access IAM policies, and workflow execution IAM policy and attachment;
  - edge: the API Gateway REST API, resource, method, integration, responses, deployment and stage, the API Gateway IAM role, policy and attachment, every API Gateway Lambda permission, the KMS content key and alias, and the onboarding S3 bucket with all of its settings and policy.
- Each of these modules declares the resources it owns itself and calls no other module.
- Modules get each other's IDs and ARNs through module outputs and variables. Never paste an ID, ARN, IP address or DNS name of an existing resource, or any part of one (such as an ARN suffix), into the `.tf` files or templates. The configuration reads files only through literal paths inside its own module (such as `"${path.module}/templates/..."`; in a child module a path starts with `${path.module}/`, because Terraform resolves any other relative path from the root directory, not from the module): no computed paths, no `terraform_remote_state` data sources, and never the state or a plan file.

**Keys.**
- Everything that exists once per workflow stage today is a `for_each` resource keyed by the stable stage name (for example `["validate-user-data"]`), including each instance of a list that also holds things that belong to no single workflow stage (the stage-specific registry parameters; the parameter containing the ordered registry of all stages is not per stage).
- The API entry-worker selection is the sole exception to the workflow-stage add/remove isolation rule below: whenever adding or removing a stage changes which active stage has the lowest `entry_priority`, the API Gateway IAM policy's Lambda resource, the API integration URI and the request template's `entryWorker` must all update in place to that newly selected stage.
- Everything that exists once per audience today is a `for_each` resource keyed by the stable audience name (for example `["driver-partner"]`), including each instance of a list that also holds things that belong to no single audience (the audience-specific registry parameters; the parameter containing the ordered registry of all audiences is not per audience).
- Don't use `count` anywhere. Other repeated resources use `for_each` with string keys that are not numbers (a name such as `["assets"]`, never `["0"]`).
- Each existing workflow stage's entry in `workflow_stages` is the only source of its values: changing an entry changes, for that workflow stage alone, exactly the settings the entry provides, and changes nothing else.
- Adding a workflow stage to `workflow_stages` must plan only the creation of that workflow stage's resources, each configured exactly like its counterparts in the existing workflow stages apart from the workflow stage itself and the values its entry in `workflow_stages` gives it (same settings, names and tags), and removing one only the destruction of that workflow stage's resources. Beyond that, the only change either may plan is an in-place update of the settings that collect something from every workflow stage today (wherever a setting holds a part of every workflow stage: their names, IDs, ARNs, subnets or CIDRs, say, in a list, a policy document or an environment value): each of them must take in, or drop, exactly that workflow stage's part where it belongs, in the same form as today (today's parts keep their order, except inside an IAM policy document, where the order of statements, actions and resources means nothing to AWS; where a new part goes is up to you), and change nothing else. No other resource may be created, updated, replaced or destroyed.
- Each existing audience's entry in `audiences` is the only source of its values: changing an entry changes, for that audience alone, exactly the settings the entry provides, and changes nothing else.
- Adding an audience to `audiences` must plan only the creation of that audience's resources, each configured exactly like its counterparts in the existing audiences apart from the audience itself and the values its entry in `audiences` gives it (same settings, names and tags), and removing one only the destruction of that audience's resources. Beyond that, the only change either may plan is an in-place update of the settings that collect something from every audience today (wherever a setting holds a part of every audience: their names, IDs, ARNs, subnets or CIDRs, say, in a list, a policy document or an environment value): each of them must take in, or drop, exactly that audience's part where it belongs, in the same form as today (today's parts keep their order, except inside an IAM policy document, where the order of statements, actions and resources means nothing to AWS; where a new part goes is up to you), and change nothing else. No other resource may be created, updated, replaced or destroyed.

**Root variables.** Declare these in the root module, each defaulting to today's value:
- `project` (`string`, `"ridenroll"`): every whole-word occurrence of `ridenroll` in a resource name, identifier or tag value today comes from it (whole word: not part of a longer run of letters and digits, so `ridenroll-api`, `ridenroll_key` and `/ridenroll/` count, while a longer word that merely contains `ridenroll` stays as it is), and so does every mention of those names elsewhere in the configuration (for example a resource name inside a policy); inside documents such as policies, container definitions and environment values, every whole-word occurrence of `ridenroll` that stands for it comes from it too.
- `environment` (`string`, `"prod"`): every whole-word occurrence of `prod` in a resource name, identifier or tag value today comes from it (whole word: not part of a longer run of letters and digits, so `prod-api`, `prod_key` and `/prod/` count, while a longer word that merely contains `prod` stays as it is), and so does every mention of those names elsewhere in the configuration (for example a resource name inside a policy); inside documents such as policies, container definitions and environment values, every whole-word occurrence of `prod` that stands for it comes from it too.
- `workflow_stages`: `map(object({ memory_size = number, timeout = number, log_retention = number, queue_visibility = number, error_threshold = number, entry_priority = number }))`, keyed by stable stage name, defaulting to today's five stages and their worker memory, timeout, log retention, queue visibility, alarm threshold and API entry priority. It is the only source of active stage names and those settings. The API entry worker is the stage with the lowest `entry_priority`; ties are resolved by lexicographically smallest stage name.
- `audiences`: `map(object({ message_retention_seconds = number, alarm_threshold = number, delivery_window = string }))`, keyed by stable audience name, defaulting to today's three audiences and their queue message retention, queue-depth alarm threshold and delivery window. It is the only source of active audience names and those settings.
- `tags` (`map(string)`, `{ Owner = "onboarding-platform", CostCenter = "cc-2741", ManagedBy = "terraform" }`): the shared tags (`Owner`, `CostCenter` and `ManagedBy`) that tagged resources carry today. Wherever the configuration writes them out today, in any form, they come from this variable, so that a different map (other keys, other values) reaches every one of those places; a resource's other tags stay as they are, and resources that are untagged today stay untagged.
- `stage_queue_message_retention_seconds` (`number`, `1209600`): the message retention of every workflow-stage dead-letter queue.
- `audience_queue_visibility_timeout` (`number`, `45`): the visibility timeout of every audience event queue.
- `workflow_log_retention_days` (`number`, `90`): the retention of the central workflow log group.
- `audit_queue_message_retention_seconds` (`number`, `1209600`): the message retention of the operations audit queue.
- `user_pool_minimum_password_length` (`number`, `12`): the onboarding user pool's minimum password length.
- `kms_deletion_window_in_days` (`number`, `30`): the onboarding content KMS key's deletion window in days.
- `api_response_status_code` (`string`, `"202"`): the success status code on both the onboarding API method response and integration response.
- Changing `stage_queue_message_retention_seconds`, `audience_queue_visibility_timeout`, `workflow_log_retention_days`, `audit_queue_message_retention_seconds`, `user_pool_minimum_password_length`, `kms_deletion_window_in_days` and `api_response_status_code` changes only what each one's line above says it controls: every other setting keeps today's value, including a setting that merely has the same value today.

**Root outputs.** Keep `api_invoke_url` and `user_pool_id` with their current values. Add `help_bucket_name`: the `bucket` of `aws_s3_bucket.user_onboarding`. Add `operations_topic_arn`: the `arn` of `aws_sns_topic.operations`. `stage_function_names` is a new output: a map from the stable stage name to the `function_name` of that workflow stage's `aws_lambda_function.stage`. `stage_log_group_names` is a new output: a map from the stable stage name to the `name` of that workflow stage's `aws_cloudwatch_log_group.stage`. `audience_table_names` is a new output: a map from the stable audience name to the `name` of that audience's `aws_dynamodb_table.audience`. `audience_topic_arns` is a new output: a map from the stable audience name to the `arn` of that audience's `aws_sns_topic.audience`. Each output passes through outputs of the module that owns the resource (identity for `user_pool_id`; messaging for `audience_table_names`, `audience_topic_arns` and `operations_topic_arn`; workflow for `stage_function_names` and `stage_log_group_names`; edge for `api_invoke_url` and `help_bucket_name`): the root output is a plain reference to an output of that module, and that module output is a plain reference to the resource. A plain reference is a reference such as `module.edge.<output>` or `<resource type>.<name>.<attribute>`, a local that holds one, or a `for` expression that only re-keys one (`{ for k, v in <reference> : k => v.id }`) or iterates a plain reference and looks each key up in one (`{ for k, v in var.<map> : k => <reference>[k].id }`); no literals, function calls, conditionals or string templates anywhere along the way.

**Not allowed anywhere in the configuration:** `ignore_changes`, `prevent_destroy` and `replace_triggered_by`, `removed` and `import` blocks, provisioners, `external` data sources, backend or cloud blocks, provider blocks other than the one in `providers.tf`, override files and `.tf.json` files.
