The Terraform for our Terraform Enterprise air-gap production stack in `/workspace/infra` has grown into one flat root module: everything is declared at the top level, the per-AZ resources are `count`-indexed by list position, and names, settings and tags are hard-coded all over the files. Split it into three local modules (network, platform and compute) without touching the running infrastructure: against the current state, the plan has to come out as nothing but moves.

There is no AWS access from this machine. `terraform init` works offline from the local provider mirror, `terraform.tfstate` is a copy of the production state, and `scripts/ci-plan.sh` runs what CI runs: a `terraform plan -refresh=false` against the state followed by the guardrail policies in `policies/`.

## Detailed Constraints

**How CI judges the change.** CI takes the repository alone and plans it with `terraform plan -refresh=false` against its own copy of the production state. Local `terraform state` commands and edits to `terraform.tfstate` never reach it, so the whole migration has to be expressed in the configuration. That plan must:
- still manage every resource that is in the state today, and
- contain no create, update, replace, destroy or forget: only resources moving to new addresses.

The guardrail policies in `policies/` must pass on that plan, and `providers.tf` and everything in `policies/` stay exactly as they are, byte for byte.

**Layout.**
- The root module calls `module "network"`, `module "platform"` and `module "compute"`, with sources `./modules/network`, `./modules/platform` and `./modules/compute` and one instance each, calls no other module and declares no resources of its own.
- Which module owns what (every instance of the resources described, wherever they are declared today):
  - network: the VPC, internet gateway, three subnet tiers, NAT gateways and Elastic IPs, route tables, routes and associations, the S3 gateway endpoint and its route table associations, the Terraform Enterprise security group and rules, the bootstrap-AZ and network-inventory parameters, and the VPC flow log with its log group and IAM role policy;
  - platform: the KMS key and alias, both S3 buckets and their settings, air-gap artifact objects, checksum, destination, metadata, manifest, registry and preferred-artifact parameters, intake queues, per-artifact logs and backlog alarms, the artifact audit table, and PostgreSQL with its subnet and parameter groups;
  - compute: the SSH key pair, application load balancer, target groups and listeners, application log group, instance IAM role, profile and policies, launch template, Auto Scaling group, and capacity alarm.
- Each of these modules declares the resources it owns itself and calls no other module.
- Modules get each other's IDs and ARNs through module outputs and variables. Never paste an ID, ARN, IP address or DNS name of an existing resource, or any part of one (such as an ARN suffix), into the `.tf` files or templates. The configuration reads files only through literal paths inside its own module (such as `"${path.module}/templates/..."`; in a child module a path starts with `${path.module}/`, because Terraform resolves any other relative path from the root directory, not from the module): no computed paths, no `terraform_remote_state` data sources, and never the state or a plan file.

**Keys.**
- Everything that exists once per availability zone today is a `for_each` resource keyed by the AZ name (for example `["us-east-1a"]`), including each instance of a list that also holds things that belong to no single availability zone (the S3 endpoint's associations with private route tables are per AZ; its association with the public route table is not).
- Collector lists preserve today's AZ order among surviving entries. The bootstrap-AZ parameter always stores the AZ name whose `bootstrap_priority` is lowest; a tie is resolved to the lexicographically smallest AZ name.
- Everything that exists once per air-gap artifact today is a `for_each` resource keyed by the stable artifact kind (for example `["license"]`), including each instance of a list that also holds things that belong to no single air-gap artifact.
- Collector documents and manifest values preserve today's artifact order among surviving entries. The preferred-artifact parameter always stores the artifact kind whose `install_priority` is lowest; a tie is resolved to the lexicographically smallest artifact kind.
- Don't use `count` anywhere. Other repeated resources use `for_each` with string keys that are not numbers (a name such as `["assets"]`, never `["0"]`).
- Each existing availability zone's entry in `availability_zones` is the only source of its values: changing an entry changes, for that availability zone alone, exactly the settings the entry provides, and changes nothing else.
- Adding an availability zone to `availability_zones` must plan only the creation of that availability zone's resources, each configured exactly like its counterparts in the existing availability zones apart from the availability zone itself and the values its entry in `availability_zones` gives it (same settings, names and tags), and removing one only the destruction of that availability zone's resources. Beyond that, the only change either may plan is an in-place update of the settings that collect something from every availability zone today (wherever a setting holds a part of every availability zone: their names, IDs, ARNs, subnets or CIDRs, say, in a list, a policy document or an environment value): each of them must take in, or drop, exactly that availability zone's part where it belongs, in the same form as today (today's parts keep their order; where a new part goes is up to you), and change nothing else. No other resource may be created, updated, replaced or destroyed.
- Each existing air-gap artifact's entry in `artifacts` is the only source of its values: changing an entry changes, for that air-gap artifact alone, exactly the settings the entry provides, and changes nothing else.
- Adding an air-gap artifact to `artifacts` must plan only the creation of that air-gap artifact's resources, each configured exactly like its counterparts in the existing air-gap artifacts apart from the air-gap artifact itself and the values its entry in `artifacts` gives it (same settings, names and tags), and removing one only the destruction of that air-gap artifact's resources. Beyond that, the only change either may plan is an in-place update of the settings that collect something from every air-gap artifact today (wherever a setting holds a part of every air-gap artifact: their names, IDs, ARNs, subnets or CIDRs, say, in a list, a policy document or an environment value): each of them must take in, or drop, exactly that air-gap artifact's part where it belongs, in the same form as today (today's parts keep their order; where a new part goes is up to you), and change nothing else. No other resource may be created, updated, replaced or destroyed.

**Root variables.** Declare these in the root module, each defaulting to today's value:
- `project` (`string`, `"tfeairgap"`): every whole-word occurrence of `tfeairgap` in a resource name, identifier or tag value today, and the `TFE_PROJECT` line in the launch template user data, comes from it (whole word: not part of a longer run of letters and digits, so `tfeairgap-api`, `tfeairgap_key` and `/tfeairgap/` count, while a longer word that merely contains `tfeairgap` stays as it is), and so does every mention of those names elsewhere in the configuration (for example a resource name inside a policy); inside documents such as policies, container definitions and environment values, every whole-word occurrence of `tfeairgap` that stands for it comes from it too; the PostgreSQL database name concatenates project and environment without a separator and follows both variables. Configured deployment values in the network inventory, artifact metadata, manifest and registry, IAM policies, alarm namespaces and dimensions, and user data follow this variable too.
- `environment` (`string`, `"prod"`): every whole-word occurrence of `prod` in a resource name, identifier or tag value today, and the `TFE_ENVIRONMENT` line in the launch template user data, comes from it (whole word: not part of a longer run of letters and digits, so `prod-api`, `prod_key` and `/prod/` count, while a longer word that merely contains `prod` stays as it is), and so does every mention of those names elsewhere in the configuration (for example a resource name inside a policy); inside documents such as policies, container definitions and environment values, every whole-word occurrence of `prod` that stands for it comes from it too; the PostgreSQL database name concatenates project and environment without a separator and follows both variables. Configured deployment values in the network inventory, artifact metadata, manifest and registry, IAM policies, alarm namespaces and dimensions, and user data follow this variable too.
- `vpc_cidr` (`string`, `"10.72.0.0/16"`): the VPC CIDR and the PostgreSQL security-group rule's source range; subnet CIDRs do not follow this variable.
- `availability_zones`: `map(object({ public_cidr = string, private_cidr = string, database_cidr = string, bootstrap_priority = number }))`, keyed by AZ name, defaulting to today's three AZs and their public, private, and database subnet CIDRs plus bootstrap priority. It is the only source of AZ names, those subnet CIDRs, and bootstrap priorities.
- `artifacts`: `map(object({ object_key = string, checksum = string, destination = string, media_type = string, queue_delay_seconds = number, backlog_threshold = number, install_priority = number }))`, keyed by stable artifact kind, defaulting to today's license, bootstrap, and air-gap package with each one's object key, checksum, destination, media type, queue delay, backlog threshold, and install priority. It is the only source of artifact kinds and all seven of those per-artifact values.
- `tags` (`map(string)`, `{ Owner = "tfe-platform", CostCenter = "cc-7240", ManagedBy = "terraform" }`): the shared tags (`Owner`, `CostCenter` and `ManagedBy`) that tagged resources carry today. Wherever the configuration writes them out today, in any form, they come from this variable, so that a different map (other keys, other values) reaches every one of those places; a resource's other tags stay as they are, and resources that are untagged today stay untagged.
- `tfe_ami_id` (`string`, `"ami-0a12bc345de678f90"`): the launch template's AMI.
- `tfe_instance_type` (`string`, `"t3.xlarge"`): the launch template's instance type.
- `root_volume_size` (`number`, `50`): the launch template root volume size in GiB.
- `asg_min_size` (`number`, `2`): the Auto Scaling group's minimum size.
- `asg_max_size` (`number`, `5`): the Auto Scaling group's maximum size.
- `asg_desired_capacity` (`number`, `2`): the Auto Scaling group's desired capacity.
- `db_instance_class` (`string`, `"db.t3.large"`): the PostgreSQL instance class.
- `db_allocated_storage` (`number`, `50`): the PostgreSQL instance's allocated storage in GiB.
- `log_retention_days` (`number`, `30`): the retention period of every CloudWatch log group.
- `queue_visibility_timeout` (`number`, `300`): the visibility timeout of every artifact intake queue.
- `alarm_period` (`number`, `300`): the period of every CloudWatch metric alarm.
- `load_balancer_idle_timeout` (`number`, `60`): the application load balancer's idle timeout.
- Changing `vpc_cidr`, `tfe_ami_id`, `tfe_instance_type`, `root_volume_size`, `asg_min_size`, `asg_max_size`, `asg_desired_capacity`, `db_instance_class`, `db_allocated_storage`, `log_retention_days`, `queue_visibility_timeout`, `alarm_period` and `load_balancer_idle_timeout` changes only what each one's line above says it controls: every other setting keeps today's value, including a setting that merely has the same value today.

**Root outputs.** Keep `vpc_id`, `load_balancer_dns_name`, `data_bucket_name`, `software_bucket_name`, `database_endpoint`, `artifact_manifest_name`, `kms_key_arn`, `artifact_registry_name` and `network_inventory_name` with their current values. `public_subnet_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_subnet.public`. `private_subnet_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_subnet.private`. `artifact_queue_urls` becomes a map from the stable artifact kind to the `url` of that air-gap artifact's `aws_sqs_queue.artifact_intake`. `artifact_log_group_arns` becomes a map from the stable artifact kind to the `arn` of that air-gap artifact's `aws_cloudwatch_log_group.artifact`. `database_subnet_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_subnet.database`. `nat_gateway_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_nat_gateway.nat`. `private_route_table_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_route_table.private`. `artifact_object_arns` becomes a map from the stable artifact kind to the `arn` of that air-gap artifact's `aws_s3_object.artifact`. `artifact_checksum_parameter_arns` becomes a map from the stable artifact kind to the `arn` of that air-gap artifact's `aws_ssm_parameter.artifact_checksum`. `artifact_metadata_parameter_arns` becomes a map from the stable artifact kind to the `arn` of that air-gap artifact's `aws_ssm_parameter.artifact_metadata`. `artifact_queue_arns` becomes a map from the stable artifact kind to the `arn` of that air-gap artifact's `aws_sqs_queue.artifact_intake`. Each output passes through outputs of the module that owns the resource (network for `vpc_id`, `public_subnet_ids`, `private_subnet_ids`, `database_subnet_ids`, `nat_gateway_ids`, `private_route_table_ids` and `network_inventory_name`; platform for `data_bucket_name`, `software_bucket_name`, `database_endpoint`, `artifact_manifest_name`, `artifact_queue_urls`, `artifact_log_group_arns`, `artifact_object_arns`, `artifact_checksum_parameter_arns`, `artifact_metadata_parameter_arns`, `artifact_queue_arns`, `kms_key_arn` and `artifact_registry_name`; compute for `load_balancer_dns_name`): the root output is a plain reference to an output of that module, and that module output is a plain reference to the resource. A plain reference is a reference such as `module.network.<output>` or `<resource type>.<name>.<attribute>`, a local that holds one, or a `for` expression that only re-keys one (`{ for k, v in <reference> : k => v.id }`) or iterates a plain reference and looks each key up in one (`{ for k, v in var.<map> : k => <reference>[k].id }`); no literals, function calls, conditionals or string templates anywhere along the way.

**Not allowed anywhere in the configuration:** `ignore_changes`, `prevent_destroy` and `replace_triggered_by`, `removed` and `import` blocks, provisioners, `external` data sources, backend or cloud blocks, provider blocks other than the one in `providers.tf`, override files and `.tf.json` files.
