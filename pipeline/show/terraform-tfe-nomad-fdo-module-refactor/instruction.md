The Terraform for our Terraform Enterprise FDO production stack on Nomad in `/workspace/infra` has grown into one flat root module: everything is declared at the top level, the per-AZ resources are `count`-indexed by list position, and names, settings and tags are hard-coded all over the files. Split it into four local modules (network, data, identity and compute) without touching the running infrastructure: against the current state, the plan has to come out as nothing but moves.

There is no AWS access from this machine. `terraform init` works offline from the local provider mirror, `terraform.tfstate` is a copy of the production state, and `scripts/ci-plan.sh` runs what CI runs: a `terraform plan -refresh=false` against the state followed by the guardrail policies in `policies/`.

## Detailed Constraints

**How CI judges the change.** CI takes the repository alone and plans it with `terraform plan -refresh=false` against its own copy of the production state. Local `terraform state` commands and edits to `terraform.tfstate` never reach it, so the whole migration has to be expressed in the configuration. That plan must:
- still manage every resource that is in the state today, and
- contain no create, update, replace, destroy or forget: only resources moving to new addresses.

The guardrail policies in `policies/` must pass on that plan, and `providers.tf` and everything in `policies/` stay exactly as they are, byte for byte.

**Layout.**
- The root module calls `module "network"`, `module "data"`, `module "identity"` and `module "compute"`, with sources `./modules/network`, `./modules/data`, `./modules/identity` and `./modules/compute` and one instance each, calls no other module and declares no resources of its own.
- Which module owns what (every instance of the resources described, wherever they are declared today):
  - network: the VPC, internet gateway, all subnets, NAT gateways and NAT Elastic IPs, route tables, routes and associations, the S3 gateway endpoint and its associations, the private Route 53 zone, the Nomad security group and all of its rules, and the VPC flow log with its log group, IAM role and inline policy;
  - data: the KMS data key and alias, all TFE S3 buckets and bucket settings, the PostgreSQL instance with its subnet and parameter groups, the Redis cluster and subnet group, the DynamoDB lock table, and the bootstrap secret and its version;
  - identity: the Nomad TLS private key, EC2 IAM role and instance profile, managed policy attachments, and inline TFE data-access policy;
  - compute: the EC2 key pair, per-node-group network interfaces, launch templates, Auto Scaling Groups, service Elastic IPs, log groups, alarms, SSM node parameters and DNS records, plus the cluster inventory parameter.
- Each of these modules declares the resources it owns itself and calls no other module.
- Modules get each other's IDs and ARNs through module outputs and variables. Never paste an ID, ARN, IP address or DNS name of an existing resource, or any part of one (such as an ARN suffix), into the `.tf` files or templates. The configuration reads files only through literal paths inside its own module (such as `"${path.module}/templates/..."`; in a child module a path starts with `${path.module}/`, because Terraform resolves any other relative path from the root directory, not from the module): no computed paths, no `terraform_remote_state` data sources, and never the state or a plan file.

**Keys.**
- Everything that exists once per availability zone today is a `for_each` resource keyed by the AZ name (for example `["us-east-1a"]`), including each instance of a list that also holds things that belong to no single availability zone (the S3 endpoint's associations with the private route tables are per AZ; its association with the public route table is not).
- The existing AZ order in every collector is the production order visible in the legacy lists; surviving AZs keep that order when a key is removed.
- Everything that exists once per Nomad node group today is a `for_each` resource keyed by the node-group name (for example `["server"]`), including each instance of a list that also holds things that belong to no single Nomad node group.
- The existing node-group order in every collector is the production order visible in the legacy lists; surviving node groups keep that order when a key is removed.
- Don't use `count` anywhere. Other repeated resources use `for_each` with string keys that are not numbers (a name such as `["assets"]`, never `["0"]`).
- Each existing availability zone's entry in `availability_zones` is the only source of its values: changing an entry changes, for that availability zone alone, exactly the settings the entry provides, and changes nothing else.
- Adding an availability zone to `availability_zones` must plan only the creation of that availability zone's resources, each configured exactly like its counterparts in the existing availability zones apart from the availability zone itself and the values its entry in `availability_zones` gives it (same settings, names and tags), and removing one only the destruction of that availability zone's resources. Beyond that, the only change either may plan is an in-place update of the settings that collect something from every availability zone today (wherever a setting holds a part of every availability zone: their names, IDs, ARNs, subnets or CIDRs, say, in a list, a policy document or an environment value): each of them must take in, or drop, exactly that availability zone's part where it belongs, in the same form as today (today's parts keep their order; where a new part goes is up to you), and change nothing else. No other resource may be created, updated, replaced or destroyed.
- Each existing Nomad node group's entry in `node_groups` is the only source of its values: changing an entry changes, for that Nomad node group alone, exactly the settings the entry provides, and changes nothing else.
- Adding a Nomad node group to `node_groups` must plan only the creation of that Nomad node group's resources, each configured exactly like its counterparts in the existing Nomad node groups apart from the Nomad node group itself and the values its entry in `node_groups` gives it (same settings, names and tags), and removing one only the destruction of that Nomad node group's resources. Beyond that, the only change either may plan is an in-place update of the settings that collect something from every Nomad node group today (wherever a setting holds a part of every Nomad node group: their names, IDs, ARNs, subnets or CIDRs, say, in a list, a policy document or an environment value): each of them must take in, or drop, exactly that Nomad node group's part where it belongs, in the same form as today (today's parts keep their order; where a new part goes is up to you), and change nothing else. No other resource may be created, updated, replaced or destroyed.

**Root variables.** Declare these in the root module, each defaulting to today's value:
- `project` (`string`, `"tfefdo"`): every whole-word occurrence of `tfefdo` in a resource name, identifier or tag value today comes from it (whole word: not part of a longer run of letters and digits, so `tfefdo-api`, `tfefdo_key` and `/tfefdo/` count, while a longer word that merely contains `tfefdo` stays as it is), and so does every mention of those names elsewhere in the configuration (for example a resource name inside a policy); inside documents such as policies, container definitions and environment values, every whole-word occurrence of `tfefdo` that stands for it comes from it too; the PostgreSQL database name and bootstrap document join this token directly to the environment token, so that joined value changes too.
- `environment` (`string`, `"prod"`): every whole-word occurrence of `prod` in a resource name, identifier or tag value today, and the `TFE_ENV` value every Nomad launch template's user data writes, comes from it (whole word: not part of a longer run of letters and digits, so `prod-api`, `prod_key` and `/prod/` count, while a longer word that merely contains `prod` stays as it is), and so does every mention of those names elsewhere in the configuration (for example a resource name inside a policy); inside documents such as policies, container definitions and environment values, every whole-word occurrence of `prod` that stands for it comes from it too; the PostgreSQL database name and bootstrap document join this token directly to the project token, so that joined value changes too.
- `vpc_cidr` (`string`, `"10.72.0.0/16"`): the VPC CIDR block and every internal-only ingress rule in the Nomad security group; subnet CIDRs remain controlled only by `availability_zones`.
- `availability_zones`: `map(object({ public_cidr = string, private_cidr = string, database_cidr = string }))`, keyed by AZ name, defaulting to today's three AZs and their public, private and database subnet CIDRs. It is the only source of AZ names and subnet CIDRs; the service-interface private IPs remain at their configured host numbers within those public CIDRs.
- `node_groups`: `map(object({ instance_type = string, private_ip_host = number, volume_size = number, subnet_key = string }))`, keyed by node-group name, defaulting to today's client, worker and server groups and each group's instance type, private-IP CIDR host index, root-volume size and subnet AZ key. The host index is passed directly to `cidrhost` for the selected public subnet. This map is the only source of node-group names and those per-group settings.
- `tags` (`map(string)`, `{ Owner = "platform-engineering", CostCenter = "cc-7421", ManagedBy = "terraform" }`): the shared tags (`Owner`, `CostCenter` and `ManagedBy`) that tagged resources carry today. Wherever the configuration writes them out today, in any form, they come from this variable, so that a different map (other keys, other values) reaches every one of those places; a resource's other tags stay as they are, and resources that are untagged today stay untagged.
- `node_ami_id` (`string`, `"ami-0009de7aaac3fdbb1"`): the AMI in every Nomad launch template.
- `db_instance_class` (`string`, `"db.t3.medium"`): the PostgreSQL instance class.
- `db_allocated_storage` (`number`, `50`): the PostgreSQL instance allocated storage in GiB.
- `cache_node_type` (`string`, `"cache.t3.small"`): the Redis cache node type.
- `log_retention_days` (`number`, `30`): the retention in days of the VPC flow log group and every Nomad node-group log group.
- `alarm_period` (`number`, `120`): the period in seconds of every Nomad node-group health alarm.
- Changing `vpc_cidr`, `node_ami_id`, `db_instance_class`, `db_allocated_storage`, `cache_node_type`, `log_retention_days` and `alarm_period` changes only what each one's line above says it controls: every other setting keeps today's value, including a setting that merely has the same value today.

**Root outputs.** Keep `vpc_id`, `state_bucket_name`, `database_endpoint`, `redis_cluster_id` and `internal_zone_id` with their current values. `public_subnet_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_subnet.public`. `private_subnet_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_subnet.private`. `database_subnet_ids` becomes a map from the AZ name to the `id` of that availability zone's `aws_subnet.database`. `nat_public_ips` becomes a map from the AZ name to the `public_ip` of that availability zone's `aws_eip.nat`. `node_public_ips` becomes a map from the node-group name to the `public_ip` of that Nomad node group's `aws_eip.nomad`. `node_group_names` becomes a map from the node-group name to the `name` of that Nomad node group's `aws_autoscaling_group.nomad`. Each output passes through outputs of the module that owns the resource (network for `vpc_id`, `public_subnet_ids`, `private_subnet_ids`, `database_subnet_ids`, `nat_public_ips` and `internal_zone_id`; data for `state_bucket_name`, `database_endpoint` and `redis_cluster_id`; compute for `node_public_ips` and `node_group_names`): the root output is a plain reference to an output of that module, and that module output is a plain reference to the resource. A plain reference is a reference such as `module.network.<output>` or `<resource type>.<name>.<attribute>`, a local that holds one, or a `for` expression that only re-keys one (`{ for k, v in <reference> : k => v.id }`) or iterates a plain reference and looks each key up in one (`{ for k, v in var.<map> : k => <reference>[k].id }`); no literals, function calls, conditionals or string templates anywhere along the way.

**Not allowed anywhere in the configuration:** `ignore_changes`, `prevent_destroy` and `replace_triggered_by`, `removed` and `import` blocks, provisioners, `external` data sources, backend or cloud blocks, provider blocks other than the one in `providers.tf`, override files and `.tf.json` files.
